# 第四课：采购穿行与票据核验系统｜课程设计底稿

> 文档类型：第二个公共项目的课程设计底稿  
> 当前版本：v0.1｜2026-09-19  
> 建议课时：3 小时，含 10 分钟休息  
> 对应总体规划：第二阶段第 4 次课“公共项目二”  
> 后续产物：老师版完整讲义、项目案例与作业材料包、老师授课安排、完整 PPT  
> 案例声明：本课中的公司、供应商、采购单、入库单、发票、ERP 记录、规则和审核结果均为教学模拟数据。

## 一、本课在第二阶段中的位置

第一个公共项目训练的是“对话中的任务推进”：系统需要理解用户表达，查询业务数据，调用流程，并在不确定或无权限时转人工。

第二个公共项目转向“材料中的风险核验”：系统面对的不是一段对话，而是一组格式不同、质量不同、彼此存在业务关系的材料。产品经理需要把文档识别、字段提取、业务关联、确定性规则、风险证据和人工复核组织成一条可以运行、可以评测、可以追责的链路。

本课不把项目讲成“上传发票，让大模型判断有没有问题”。真正要训练的是：

1. 先还原业务和单据关系，再决定 AI 放在哪里；
2. 区分“原文是什么”“字段提取成什么”“业务规则怎样比较”“审核人员最终怎样确认”；
3. 让每个风险结论都能返回原始证据；
4. 把识别错误、规则命中和真实业务风险分开；
5. 用分层评测判断系统到底错在哪一层。

## 二、公共项目定义

### 1. 项目名称

采购穿行与票据核验系统。

### 2. 目标用户

- 主要用户：企业内审、财务审核或采购合规人员；
- 协作用户：采购、仓储、应付会计；
- 项目决策者：财务负责人或审计负责人。

### 3. 核心业务问题

审核人员需要从 ERP 采购记录、采购申请单、入库单和发票中确认同一笔采购是否材料齐全、主体一致、数量合理、金额一致，并对异常项保留证据和处理记录。

人工方式通常需要逐份打开材料、抄录字段、寻找对应关系、进行计算和登记差异。材料多时只能抽样，且容易把“看不清”“没有匹配到”和“确认存在风险”混在一起。

### 4. 项目价值

系统先处理机械但高耗时的识别、关联和比较工作，把异常项与证据集中给审核人员；人负责处理低置信度、业务例外和最终风险结论。

本课不承诺自动替代审计，也不以“发现多少舞弊”作为教学项目的直接效果。项目首先证明能提高材料覆盖率、缩短单笔初审时间、降低机械核对遗漏，并形成可追溯的审核记录。

## 三、业务范围与 MVP 边界

### 1. 本轮 MVP 支持的输入

1. 一份 ERP 采购交易 CSV；
2. 采购申请单；
3. 入库单；
4. 增值税发票；
5. 人工补充的审核备注。

### 2. 本轮 MVP 的核心能力

- 识别三类业务单据；
- 提取有限的关键字段和字段证据位置；
- 通过采购单号、供应商、日期等信息关联同一笔业务；
- 使用确定性规则比较供应商、数量、金额和时间顺序；
- 区分通过、异常、待确认、材料缺失和系统失败；
- 展示原始材料与差异证据；
- 允许人工修正字段、确认或驳回风险；
- 保存操作人、时间、修改前后值和处理意见；
- 导出差异汇总表。

### 3. 本轮不做

- 完整采购管理或付款审批系统；
- 合同全文审核；
- 供应商准入与工商风险调查；
- 银行流水核验；
- 税务真伪查验接口；
- 自动认定舞弊或自动给出最终审计结论；
- 覆盖企业全部票据版式与全部例外规则；
- 无人工确认地直接修改 ERP 或阻断付款。

### 4. 项目完成的判断

项目完成不以“上传后出现一段 AI 分析”为准，而以一组材料能否走完以下闭环为准：

```text
导入业务记录与材料
→ 识别单据
→ 提取字段并定位证据
→ 建立材料关联
→ 执行核验规则
→ 展示差异与不确定项
→ 人工修正或确认
→ 保存审核记录
→ 导出结果
```

## 四、统一教学案例

### 1. 模拟企业与固定日期

| 项目 | 固定设定 |
|---|---|
| 企业 | 教学模拟企业“启明智造” |
| 审核任务 | 2026 年 8 月采购业务穿行核验 |
| 固定审核日 | 2026-09-15 |
| 币种 | 人民币 |
| 数量单位 | 件 |
| 税价口径 | 发票价税合计与 ERP 含税金额比较 |
| 未提供的信息 | 记为未知，不允许模型补造 |

### 2. 单据清单

| 材料编号 | 类型 | 关键作用 |
|---|---|---|
| ERP-202608.csv | ERP 交易数据 | 提供采购单号、供应商、含税金额和业务状态 |
| PR-260801.pdf | 采购申请单 | 提供申请部门、物料、申请数量、预算金额和审批信息 |
| GR-260801.pdf | 入库单 | 提供实际收货数量、入库日期和仓库签收信息 |
| INV-260801.pdf | 增值税发票 | 提供销售方、购买方、开票日期、数量和价税合计 |

### 3. 第一版字段字典

| 标准字段 | ERP | 采购申请单 | 入库单 | 发票 | 类型 |
|---|---|---|---|---|---|
| purchase_id | 有 | 有 | 有 | 备注栏可能有 | 字符串 |
| supplier_name | 有 | 有 | 有 | 销售方名称 | 字符串 |
| material_name | 有 | 有 | 有 | 货物名称 | 字符串 |
| requested_qty | 无 | 有 | 无 | 无 | 数值 |
| received_qty | 无 | 无 | 有 | 无 | 数值 |
| invoiced_qty | 无 | 无 | 无 | 有 | 数值 |
| budget_amount | 无 | 有 | 无 | 无 | 金额 |
| erp_gross_amount | 有 | 无 | 无 | 无 | 金额 |
| invoice_gross_amount | 无 | 无 | 无 | 价税合计 | 金额 |
| request_date | 无 | 有 | 无 | 无 | 日期 |
| receipt_date | 无 | 无 | 有 | 无 | 日期 |
| invoice_date | 无 | 无 | 无 | 有 | 日期 |
| approval_status | 无 | 有 | 无 | 无 | 枚举 |

字段结果必须同时保留：标准化值、原始文本、来源材料、页码或区域、识别置信度、是否被人工修改。不能只保留一个最终字符串。

### 4. 第一版关联规则

1. ERP 与采购申请单优先按 `purchase_id` 精确关联；
2. 入库单按 `purchase_id` 关联，缺失时只能进入候选匹配，不自动确认为同一业务；
3. 发票备注栏存在 `purchase_id` 时优先使用；不存在时依据供应商、物料、金额和日期生成候选；
4. 一个材料同时匹配多笔业务时标记“关联待确认”；
5. 没有匹配到材料时标记“材料缺失”，不直接标记“业务违规”。

### 5. 第一版核验规则

| 规则编号 | 规则 | 计算方式 | 结果 |
|---|---|---|---|
| R01 | 供应商一致 | 标准化后精确比较；别名必须来自维护表 | 通过 / 异常 / 待确认 |
| R02 | 入库量不超过申请量 | `received_qty <= requested_qty` | 通过 / 异常 / 无法计算 |
| R03 | 发票数量不超过入库量 | `invoiced_qty <= received_qty` | 通过 / 异常 / 无法计算 |
| R04 | 发票与 ERP 含税金额一致 | 金额差绝对值不超过 0.01 元 | 通过 / 异常 / 无法计算 |
| R05 | 时间顺序合理 | 申请日期不晚于入库日期；开票日期不早于申请日期 | 通过 / 异常 / 待确认 |
| R06 | 申请已审批 | `approval_status = approved` | 通过 / 异常 / 未知 |

金额和数量比较由程序执行，不让大模型心算。模型可以负责字段候选、版面理解和非结构化说明，但规则引擎负责确定性比较。

## 五、三组课堂案例

### 案例一：正常通过

- 四类材料齐全，采购单号一致；
- 供应商均为“上海恒远电子有限公司”；
- 申请 100 件、入库 100 件、发票 100 件；
- ERP 含税金额与发票价税合计均为 56,500.00 元；
- 申请已审批，日期顺序合理。

教学目的：先让学员看懂完整数据链和通过状态，避免一上来只讨论异常。

### 案例二：确定性差异

- 采购申请 100 件；
- 入库单 100 件；
- 发票 110 件；
- ERP 含税金额 56,500.00 元；
- 发票价税合计 62,150.00 元。

系统应分别命中 R03 和 R04，展示三个数量、两个金额及其原始位置。系统可以描述“发票数量高于入库数量 10 件，发票金额高于 ERP 记录 5,650.00 元”，但不能直接断言“供应商虚开发票”或“存在舞弊”。

教学目的：区分客观差异与最终风险定性。

### 案例三：识别不确定与材料缺失

- 发票扫描件金额区域模糊，模型候选值为 56,500.00 元，置信度低；
- 入库单没有采购单号；
- 依据供应商、物料和日期能找到两笔候选采购；
- 系统缺少足够依据自动关联。

正确结果不是“金额一致、审核通过”，也不是“发现异常”，而是：字段待确认、关联待确认，相关规则暂不执行，由审核人员查看原图并选择对应业务。

教学目的：说明低置信度不是业务风险，不能把无法判断强行变成二选一结论。

## 七、各节需要讲透的结论

### 第一节：先讲业务，不从 OCR 开始

- 穿行测试是在同一笔业务的不同环节之间寻找证据；
- “票据审核”不是单张发票真伪识别；
- AI 的价值是扩大覆盖和整理证据，不是替代最终责任人。

### 第二节：字段字典是系统共同语言

- 同一业务概念在不同材料中可能名称不同；
- 先统一标准字段、数据类型和来源，再谈模型输出；
- 关联关系必须允许一对多、缺失和多候选，不能假设文件天然成套。

### 第三节：识别结果必须可追溯

- OCR 负责文字候选，视觉模型负责版面和区域理解，大模型可辅助语义映射；
- 每个字段都要保留原文与证据位置；
- 低置信度进入复核，不应自动改成空值或业务异常。

### 第四节：模型与规则分工

- 金额、数量、日期等精确比较交给程序；
- 模型不承担最终计算，也不根据常识补齐缺失字段；
- 风险状态由规则结果、置信度和材料完整性共同映射。

### 第五节：人工复核不是系统失败后的补丁

- 人工需要同时看到原图、提取值、规则、差异和修改入口；
- 修正字段后应重新运行受影响规则；
- 最终确认、驳回和例外放行都必须留痕。

### 第六节：至少区分五类状态

| 状态 | 含义 | 默认动作 |
|---|---|---|
| passed | 资料足够且规则通过 | 进入人工抽查或批量确认 |
| flagged | 资料足够且规则命中差异 | 人工审核风险 |
| needs_review | 识别或关联不确定 | 人工修正字段或关系 |
| missing_document | 应有材料未找到 | 补充材料或登记例外 |
| system_error | 解析、模型或服务失败 | 重试、降级或人工处理 |

### 第七节：评测不能只看“最终答对没有”

| 层级 | 代表指标 |
|---|---|
| 文档分类 | 各类单据准确率、未知类型拒识率 |
| 字段提取 | 字段级准确率、金额与日期规范化准确率 |
| 证据定位 | 正确字段是否指向正确原文区域 |
| 业务关联 | 精确匹配准确率、候选召回率、误关联率 |
| 规则执行 | 规则结果正确率、无法计算状态正确率 |
| 风险结果 | 漏报率、误报率、待确认召回率 |
| 人工效率 | 单笔复核时间、字段修正率、一次处理完成率 |

评测集至少覆盖正常、确定性差异、低质量扫描、字段缺失、多候选关联和系统失败。训练或调试样本不能全部兼作最终评测样本。

### 第八节：个人项目迁移

学员可以迁移到报销、保险理赔、合同履约、医疗票据、贷款材料、供应商资质或其他材料审核场景，但必须保留以下结构：

```text
多份业务材料
→ 字段结构化
→ 材料关联
→ 确定性规则
→ 风险证据
→ 人工复核
```

不能只做“上传一份文件，让 AI 总结内容”。

## 八、个人项目作业标准

### 1. 点评课前初版

1. 一页业务背景与审核目标；
2. 现状流程与目标流程；
3. 单据或材料清单；
4. 字段字典；
5. 关联规则和至少 5 条核验规则；
6. 核心页面或可操作 Demo；
7. 至少 6 组脱敏或模拟测试材料；
8. 当前测试结果或明确卡点。

### 2. 点评后最终版

除初版内容外，还需要：

- 跑通一条完整核心链路；
- 覆盖正常、确定性差异、不确定/缺失三类测试；
- 给出字段提取、规则执行和最终风险三层结果；
- 展示一次人工修正与规则重跑；
- 保存一份审核留痕；
- 记录至少一个 Bad Case、原因和修改；
- 提供 3—5 分钟演示录屏。

### 3. 不合格的典型情况

- 只有通用需求文档，没有测试材料；
- 只有单文档问答或摘要；
- 让大模型直接输出金额比较结果；
- 不展示原始证据位置；
- 把识别失败当成业务风险；
- 所有异常都只显示“审核不通过”；
- 没有人工修正和审核留痕；
- 把模拟结果描述成真实上线效果。
