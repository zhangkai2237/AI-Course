# DisputeIQ 产品需求文档（中文改写）

> 来源：同目录英文 `原始PRD.xlsx` 与 `原始PRD.csv`。本文不是逐单元格翻译，而是保留完整产品逻辑的中文重组。

## 1. 产品定义

DisputeIQ 是面向中小型电商商户的 AI 拒付收入保护平台。产品覆盖发货前订单风险识别，以及拒付发生后的原因分类、证据收集、完整度判断、胜诉建议和材料生成。

## 2. 问题背景

商户目前通常从邮件发现拒付通知，手工解释原因代码，再到订单、支付、物流和客服系统中查找证据，最后撰写说明并提交。一次案件约耗时 45 分钟；每月 80 次争议约占用 40 小时。大量案件并非真实欺诈，却因材料缺失或组织不当而败诉。

## 3. 用户与商业场景

- 使用者：运营经理、财务人员、拒付专员；
- 购买者：商户老板、财务负责人、运营负责人；
- 客户：中小型电商、订阅业务和数字商品商户；
- 购买阈值：每月争议数量高、人工处理时间明显、拒付损失可量化。

## 4. 产品目标

- 将单个拒付处理时间从约 45 分钟压缩到数分钟；
- 自动识别原因代码对应的证据要求；
- 提升证据完整度并减少可避免的败诉；
- 保证所有陈述可追溯到输入事实；
- 对不确定或高风险案例保留人工审核。

## 5. 产品范围

### 发货前

- 根据设备、IP、购买频率、AVS/CVV 等信号评分；
- 将订单划分为低、中、高风险；
- 低风险放行，中风险复核，高风险验证或取消。

### 拒付后

- 解析拒付原因代码；
- 查询该代码所要求的证据；
- 从 Shopify、Stripe、物流和客服系统拉取事实；
- 判断证据存在、缺失或部分满足；
- 计算完整度和胜诉建议；
- 生成证据包和争议说明；
- 由商户提交、放弃或转人工。

## 6. 输入与输出

### 输入

原因代码、交易 ID、金额、日期、商户类别、订单详情、物流号、配送状态和日期、客服历史、退款承诺、服务条款接受记录、设备与支付验证信号。

### 输出

- 原因代码解释；
- 该代码要求的证据清单；
- 每项证据的存在、缺失或部分状态；
- 证据完整度评分；
- 争议说明；
- `SUBMIT`、`DONT_CONTEST` 或 `REVIEW_MANUALLY`；
- 置信度和缺失字段；
- 最终处理状态和审计记录。

## 7. 核心功能需求

### F1 争议接入与标准化

通过 Webhook 接收新拒付，统一支付机构字段，验证交易 ID、金额、原因代码和截止日期。

### F2 规则知识匹配

根据 Visa、Mastercard 等原因代码矩阵，确定强制和可选证据。原型知识规模较小，直接以结构化 JSON 注入，不建立向量库。

### F3 多系统证据聚合

并行读取订单、支付、物流和客服记录，按交易 ID 和时间线合并，保留来源。

### F4 AI 判断与生成

模型判断证据是否满足要求，生成完整度、胜率建议和简短说明。禁止使用输入之外的事实。

### F5 决策路由与人工审核

高置信度、证据完整的案例进入提交队列；明显无证据的案例建议放弃；矛盾、缺失或边界案例进入人工复核。

## 8. 技术与模型方案

- n8n：Webhook、API 连接、重试、条件判断和写回；
- Claude Haiku：生产分类、判断和文本生成；
- Claude Sonnet：开发、提示词迭代和模型评审；
- Next.js：前端工作台；
- 规则 JSON：原因代码与证据要求；
- 初期数据：20 个合成争议案例和模拟接口响应。

## 9. 验收标准

- 事实全部来自输入数据；
- 证据完整度判断目标不低于 85%；
- 建议与专家标签匹配目标不低于 80%；
- JSON Schema 合规率 100%；
- 说明专业、克制，约 150—300 词；
- 端到端处理时间低于 30 秒；
- 任何自动建议都可被人工覆盖。

## 10. 评测方案

回归集包括 10 个可胜诉案例、5 个明显不可胜诉案例和 5 个边界案例，覆盖不同原因代码、物流缺失、客服承诺退款和证据矛盾。

评测器包括 JSON Schema 脚本、事实交叉检查、Sonnet 单项评审和人工专家抽查。目标是在 20 个案例中至少 80% 同时通过全部评测器，而不是只通过某个总体分数。

## 11. 风险与边界

- 合成数据无法覆盖真实商户和支付机构长尾；
- 胜率预测需要真实历史结果校准；
- 支付规则更新必须可追踪版本；
- 自动提交前必须保留商户确认；
- 产品建议不能被表述为法律或财务保证。
