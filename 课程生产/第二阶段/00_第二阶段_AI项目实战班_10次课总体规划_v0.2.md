# 第二阶段 AI项目实战班 10次课总体规划 v0.2

> 当前结论：第二阶段采用“1次启动 + 3组公共项目讲解与个人项目点评 + 1次主项目深化 + 1次作品集制作 + 1次路演验收”的10次课结构。取消独立线上工作坊，改为公共项目课后分阶段提交，点评课集中纠偏并安排现场修改。

## 一、第二阶段的定位

第一阶段解决的是“是否理解AI产品的基本知识和方法”，第二阶段解决的是“能否把这些方法连续地用在真实项目里，并形成可以展示和讲述的项目证据”。

第二阶段不再按照Prompt、Workflow、RAG、Agent等技术名词分别设计项目。三个项目都从业务问题出发，并根据业务需要综合使用：

- Prompt与结构化输出；
- Workflow、规则和人工节点；
- RAG与企业知识库；
- Agent与工具调用；
- 原型、测试集、Bad Case和数据反馈；
- 成本、风险、权限和人工接管。

项目不以“使用了多少AI技术”衡量价值，而以是否讲清业务问题、方案选择、产品边界、评测证据和迭代判断为标准。

## 二、公共项目与个人项目的关系

### 1. 三个公共项目

公共项目由教师在课堂上完整拆解，用于让所有学员看到一个有出处、有材料、有取舍的项目是怎样从业务背景走到PRD、原型、评测和迭代的。

三个公共项目是教学母本，不要求学员把教师项目改名后直接作为自己的项目。

### 2. 三个个人项目

每讲完一个公共项目，学员选择一个与自己行业、工作经历、可获得材料或目标岗位相关的场景，按照同一类业务问题完成个人项目。下一次课集中点评并修改。

因此，学员最终应当形成：

- 3个亲自完成的个人AI项目；
- 3个经过课堂完整学习的公共参考项目；
- 其中1个重点项目的深度作品集版本；
- 3个项目的简历描述和项目讲述稿。

对外表达时，三个个人项目必须如实标注为个人项目、课程实战项目或业务改造方案，不能伪装成已经在原公司上线的项目。

## 三、三个公共项目总览

| 项目 | 业务类型 | 公开原型 | 课程扩展来源 | 核心能力 |
|---|---|---|---|---|
| 企业客户研究与销售方案助手 | 增长与销售辅助 | GTM Copilot | 知乎客服与销售类AI产品 | 客户研究、RAG产品匹配、方案与话术生成、人工确认 |
| 采购穿行与票据核验系统 | 财务、审计与风险控制 | AI Invoice Auditor | 亚慧投行核查审查与穿行测试系统 | 文档识别、字段提取、确定性规则、差异汇总、人工复核 |
| RFP发现、需求拆解与智能标书生成平台 | 企业知识与专业内容生产 | Nimra AI | 知乎智能标书项目、亚慧金融智能文档平台 | 长文档解析、需求清单、RAG、树状工作流、分章节生成、校验溯源 |

三个项目不是按技术划分，而是对应三类不同的产品判断：

1. 如何让AI帮助专业人员理解客户并形成销售方案；
2. 如何让AI进入准确性要求很高的企业核验流程；
3. 如何让AI处理超长专业文档，并生成有依据、可校验的结果。

## 五、第1次课 AI项目立项 选题与完成标准

> 详细课程设计：[第一课 AI项目立项 选题与完成标准](./01_第一课_AI项目立项选题与完成标准_课程设计_v1.0.md)
>
> 老师版完整讲义：[第一课 AI项目立项 选题与完成标准 老师版完整讲义](./02_第一课_AI项目立项选题与完成标准_老师版完整讲义_v1.0.md)

### 本次课要解决的问题

- 为什么项目班不能继续按照知识点听课；
- 什么样的材料才算一个完整AI产品项目；
- 课程项目怎样形成可信的简历和作品集证据；
- 三个公共项目分别代表哪类业务问题；
- 公共项目怎样迁移成与学员背景相关的个人项目；
- 怎样判断一个选题是否值得做；
- 什么项目可以写入简历，什么项目不能伪造为工作经历。

### 课堂结构

1. 讲清第二阶段三个个人项目与一个主项目的完成标准；
2. 通过对比案例区分项目想法、功能清单、PRD、Demo和完整项目；
3. 说明课程实战项目如何如实写入简历；
4. 介绍三个公共项目的业务差异和能力组合；
5. 讲解公共项目迁移成个人项目的方法；
6. 使用六项标准判断选题；
7. 诊断课前收集的真实学员项目；
8. 完成第一个个人项目的选题卡。

### 学员需要提交

- 项目一正式选题卡；
- 项目一六项评分；
- 项目一可获得的材料和数据清单；
- 项目一MVP初步边界；
- 项目二和项目三候选方向；
- 真实性声明与尚未验证的假设。

### 建议时长

正常约100分钟，可根据现场项目诊断缩短至90分钟或自然延长至120分钟左右，不为凑时长增加内容。

## 六、第2次课 公共项目一 企业客户研究与销售方案助手

### 项目来源

- 公开原型：Product Faculty的GTM Copilot；
- 课程扩展：知乎“客服系统、销售系统智能化升级”中的保险销售建议书和产品推荐案例。

### 本次课的项目主线

```text
输入企业与客户信息
→ 收集公开资料、财务信息、新闻和CRM上下文
→ 形成带来源的客户研究简报
→ 理解客户需求和业务背景
→ 从企业产品知识库中检索适合的产品或方案
→ 对产品组合和适用条件进行规则校验
→ 生成销售建议、会前材料和沟通话术
→ 销售人员确认后使用
```

### 课堂重点

1. 为什么销售人员需要的不是普通总结，而是可以支持下一次沟通的客户情报；
2. 如何区分公开事实、内部信息、模型推测和证据不足；
3. 如何设计客户信息、产品信息和销售角色三个输入；
4. 如何通过RAG检索产品资料，而不是让模型凭空推荐；
5. 哪些产品组合需要规则或表格校验；
6. 如何生成客户简报、销售建议书和沟通话术；
7. 为什么最终沟通仍由销售人员确认；
8. 如何用事实准确率、来源覆盖率和人工采纳情况评测项目。

### 当前MVP边界

- 输入一个目标企业或客户及必要上下文；
- 收集和整理指定来源的信息；
- 生成带来源的客户研究简报；
- 从有限的企业产品知识库中匹配方案；
- 生成一份销售建议或会前沟通材料；
- 由人工确认、修改和反馈。

### 不进入当前MVP

- 自动化销售线索评分与分配；
- 自动预测成交概率；
- 自动执行多轮销售触达；
- 自动向CRM写回完整销售结果；
- 销售主管经营看板。

### 对应个人项目方向

学员不必做企业软件销售，可以迁移到自己熟悉的专业顾问场景，例如教育课程顾问、保险顾问、招聘顾问、医疗服务顾问、招商顾问或行业解决方案顾问。但个人项目必须保留“研究对象—匹配方案—形成专业建议—人工确认”的核心结构。

## 七、第3次课 个人项目一点评与迭代

### 点评重点

- 客户和使用者是否被混为一谈；
- 是否存在真实的客户研究成本；
- 推荐是否有产品知识和证据支撑；
- 是否把模型推测写成了事实；
- 是否说明为什么需要AI，而不是普通筛选和模板；
- MVP是否过度扩展成CRM或完整销售管理系统；
- 原型是否展示来源、置信和人工确认状态；
- 评测是否覆盖事实准确、检索命中、推荐合理和人工采纳。

### 课堂流程

1. 汇总全班共性问题；
2. 展示3至5份有代表性的作业；
3. 学员先判断问题和修改方向；
4. 教师逐份点评关键取舍；
5. 学员现场修改核心流程、MVP和评测方案；
6. 提交个人修改清单。

### 课后定稿

个人项目1 V1.0至少包含：业务背景、目标用户、现状流程、核心问题、输入输出、AI与规则分工、MVP、核心原型、测试样本、指标、Bad Case和迭代记录。

## 八、第4次课 公共项目二 采购穿行与票据核验系统

### 项目来源

- 公开原型：Product Faculty的AI Invoice Auditor；
- 课程扩展：亚慧“对外投行核查审查与穿行测试系统”中的采购申请单、入库单和发票核验案例。

### 本次课的项目主线

```text
上传ERP交易数据、采购申请单、入库单和发票
→ 识别单据类型
→ 提取供应商、日期、数量、金额等关键字段
→ 关联同一笔采购业务的单据
→ 使用确定性规则核对字段
→ 标记缺失项和不一致项
→ 生成差异汇总表
→ 人工修正字段并确认风险
→ 保留审核记录
```

### 课堂重点

1. 穿行测试在业务上要验证什么；
2. 如何定义单据、字段、主键和关联关系；
3. OCR、视觉模型和大模型分别处理什么；
4. 为什么金额、数量和日期比较必须使用确定性规则；
5. 如何处理字段缺失、识别置信度低和单据无法匹配；
6. 如何把风险结果与原始证据位置关联；
7. 人工复核如何修正字段、确认风险并回流；
8. 如何建立字段提取和风险识别两层评测集。

### 当前MVP边界

- 支持ERP交易数据、采购申请单、入库单和发票；
- 提取有限的关键字段；
- 完成同一采购业务的单据关联；
- 配置一组明确的核验规则；
- 输出差异汇总表和证据；
- 支持人工修改与确认；
- 形成基本审核留痕。

### 不进入当前MVP

- 完整采购管理系统；
- 合同全文审核；
- 供应商准入管理；
- 银行流水和付款审批全链路；
- 自动给出最终审计结论；
- 企业全部核查场景一次性覆盖。

### 对应个人项目方向

学员可以迁移到报销材料、保险理赔、合同履约、医疗票据、贷款材料、供应商资料或资质材料等场景。但必须保留“文档识别—字段提取—规则核验—风险证据—人工复核”的核心结构。

## 九、第5次课 个人项目二点评与迭代

### 点评重点

- 是否真正理解了业务单据之间的关系；
- 是否先定义字段和规则，再讨论模型；
- 是否错误地让大模型承担精确计算；
- 是否区分字段提取错误和业务风险；
- 是否展示原始证据和人工复核；
- 评测指标是否区分文档分类、字段提取、规则命中和风险结果；
- 是否考虑漏报、误报和高风险人工兜底；
- MVP是否膨胀成完整业务管理系统。

### 课后定稿

个人项目2 V1.0除完整项目材料外，还应包含：单据清单、字段字典、关联规则、核验规则表、风险分级、人工处理状态和一组脱敏测试材料。

## 十、第6次课 公共项目三 RFP发现 需求拆解与智能标书生成

### 项目来源

- 公开原型：Product Faculty的Nimra AI；
- 课程扩展一：知乎“智能标书系统、政府应用产品”中的树状长文档生成工作流；
- 课程扩展二：亚慧金融智能文档写作平台中的“读、查、问、写”、知识溯源、规则核查和人工校对。

### 本次课的项目主线

```text
发现或上传RFP
→ 提取资格、截止时间、强制项、技术项和商务项
→ 生成带原文位置的需求清单
→ 判断企业是否具备响应条件
→ 输入企业资质、公司信息、产品资料和人工补充信息
→ 根据招标要求和评分标准生成一级目录
→ 循环生成二级、三级目录
→ 分章节调用知识库生成内容
→ 持续写入外部文档
→ 人工校对并处理证据不足项
→ 输出标书草稿
```

### 课堂重点

1. Nimra为什么先解决机会发现、资格判断和需求拆解；
2. 如何抽取不能漏掉的强制要求并保留原文位置；
3. 招标文件、评分标准、企业资质、产品资料分别有什么作用；
4. 为什么严谨长文档必须采用“大纲—分层拆解—分章节生成”的树状工作流；
5. 如何持续向每个生成节点传递要求和评分标准；
6. 什么时候调用企业知识库或数据库；
7. 如何将超长生成结果持续写入外部文档；
8. 如何处理资料缺失、证据不足和需要人工补充的内容；
9. 如何评测需求召回率、引用准确率、事实准确率和内容覆盖率。

### 当前MVP边界

- 上传或选择一份RFP；
- 提取资格、时间和核心要求；
- 生成带原文证据的需求清单；
- 输入有限的企业资质和产品资料；
- 生成一级和二级标书结构；
- 选择部分章节进行知识库增强生成；
- 标记证据不足和需人工补充项；
- 输出标书草稿文档。

### 不进入当前MVP

- 完整跨部门任务管理；
- 多层级审批中心；
- 复杂权限和组织体系；
- 完整版本管理平台；
- CRM自动分配负责人；
- 直接承诺无需人工审核的完整自动投标。

### 对应个人项目方向

学员可以迁移到政府项目申报、咨询方案、尽调报告、研究报告、法律文书、保险方案、安全问卷或其他专业长文档场景。但必须保留“长文档理解—要求拆解—知识检索—结构生成—分段写作—证据核查”的核心结构。

## 十一、第7次课 个人项目三点评与迭代

### 点评重点

- 是否只是做了一个普通写作助手；
- 是否先识别要求和约束，再开始生成；
- 是否有明确的输入材料和企业知识来源；
- 是否保留来源、引用和证据不足状态；
- 长文档是否被合理拆成树状工作流；
- 是否控制上下文、循环、文档写入和人工确认；
- 是否评测遗漏、虚构、前后冲突和引用错误；
- 项目是否扩张成完整OA或协同办公系统。

### 课后定稿

个人项目3 V1.0除完整项目材料外，还应包含：文档结构、要求清单、知识来源、生成工作流、引用机制、人工补充点、长文测试样本和关键Bad Case。

## 十二、第8次课 主项目深化

### 本次课的定位

三个个人项目都需要达到完整产品方案的标准，但不要求三个项目都做成相同深度。学员从中选择一个最符合个人背景、目标岗位和材料条件的项目作为主项目，进一步补齐Demo、评测、迭代、风险、成本和价值判断。

### 主项目深化内容

1. 补充用户、流程和业务问题的真实证据；
2. 检查AI介入点和替代方案是否合理；
3. 完成一组可实际运行的测试样本；
4. 形成评测结果，而不只是评测计划；
5. 找到典型Bad Case并分析原因；
6. 展示至少一次修改前后的对比；
7. 补充权限、隐私、误报、漏报和人工接管；
8. 说明模型、工具和技术方案的选择依据；
9. 估算Token、模型调用和人工审核成本；
10. 判断项目可能创造的效率、质量或业务价值；
11. 说明Demo与真实生产系统之间仍然缺少什么；
12. 记录尚未验证的假设和项目限制。

### 本次课产出

- 主项目深度版PRD；
- 可运行Demo或关键链路验证；
- 测试集与评测结果；
- Bad Case分析；
- V0.1到V1.0的迭代记录；
- 成本、风险和ROI初步判断；
- 面试追问树初稿。

## 十三、第9次课 作品集 简历描述与项目讲述

### 本次课的定位

这一节解决“项目做过了，但无法对外展示和讲清楚”的问题。作品集不是把PRD全部截图，而是呈现项目判断、关键证据、方案取舍和迭代结果。

### 课堂内容

1. 将主项目压缩成8至12页作品集；
2. 确定作品集的业务背景、问题、方案、原型、评测和复盘结构；
3. 区分项目事实、教学材料、个人判断和未验证假设；
4. 展示个人贡献，不把课程公共项目冒充个人项目；
5. 为三个个人项目分别撰写简历描述；
6. 将主项目整理成3分钟讲述稿；
7. 准备1分钟简版、3分钟标准版和深入追问版；
8. 检查作品集是否存在堆技术名词、缺少证据或结果夸大的问题。

### 本次课产出

- 主项目作品集初稿；
- 三个个人项目的简历描述；
- 主项目3分钟讲述稿；
- 项目真实性和个人贡献说明；
- 需要在最终路演前修改的问题清单。

## 十四、第10次课 项目路演 验收与阶段总结

### 路演要求

每位学员围绕主项目，用3至5分钟回答：

1. 为什么选择这个问题；
2. 原来的业务流程有什么问题；
3. 为什么需要AI；
4. AI、规则、系统和人工如何分工；
5. 为什么这样确定MVP；
6. 使用了什么材料和数据；
7. 如何测试和评测；
8. 发现了什么Bad Case；
9. 根据测试修改了什么；
10. 如果进入真实生产环境还缺什么。

### 最终验收

教师按照真实性、业务、产品、AI、数据、评测、风险、迭代和表达九个维度进行验收。路演不是只评价演讲效果，而是检查项目是否经得起连续追问。

### 三个项目的横向总结

| 维度 | 项目一 | 项目二 | 项目三 |
|---|---|---|---|
| 主要价值 | 辅助专业判断与销售沟通 | 降低审核成本与业务风险 | 提升专业文档处理和生产效率 |

| 规则作用 | 产品适用条件与组合校验 | 金额、数量、日期等精确核验 | 强制项、格式和结构检查 |

## 十八、范围控制规则

后续制作课程、PRD、PPT和原型时遵循以下规则：

1. 当前核心功能必须能够对应到公开原型、知乎项目或亚慧项目中的明确材料；
2. 没有明确来源的功能不能悄悄进入当前MVP；
3. 上一版功能统一标记为“后期延展”，不能与当前必做范围混写；
4. 每次增加功能都要说明解决的问题、所需数据、使用者和评测方式；
5. 公共项目首先保证主链路完整，不追求一次做成大型企业平台；
6. 学员个人项目可以迁移行业，但不能只替换项目名称和页面文案；
7. 三个项目都必须体现业务、产品、AI、评测、风险和价值，而不是只交一份流程图或Demo。

## 附录 前一版三个项目的完整产品蓝图

> 本附录用于保留前一版讨论中形成的完整产品设想，避免后续遗失。它描述的是三个项目完成核心MVP以后可能演进成的完整产品，不代表当前10次课全部都要讲，也不代表学员第一次作业需要全部实现。正式备课时，应以前文定义的课程来源和当前MVP边界为准。

### 一 销售增长智能工作台完整蓝图

#### 1. 产品定位

这是一个面向To B销售团队的AI工作台。它不只是生成销售邮件，而是希望帮助销售完成从发现客户机会、研究客户、判断优先级，到制定策略、生成内容和跟踪结果的完整过程。

完整产品试图回答四个问题：

- 应该优先跟进谁；
- 为什么现在值得跟进；
- 应该从什么问题切入；
- 下一步应该采取什么行动。

#### 2. 业务背景

企业的销售线索可能来自官网留资、市场活动、广告、CRM、合作渠道、公开企业信息和销售人员自行拓展。销售人员同时面对大量客户，但客户信息分散、更新时间不同，客户研究和沟通策略高度依赖个人经验。

传统CRM主要负责记录客户和销售过程，但通常无法直接回答：

- 哪些客户最值得投入时间；
- 客户最近出现了什么变化；
- 客户可能面临什么业务问题；
- 应该联系客户的什么角色；
- 应该推荐什么产品或方案；
- 第一次沟通应该怎样展开；
- 跟进失败后下一步做什么。

#### 3. 目标用户

- 一线销售：减少客户研究和销售材料准备时间；
- 销售主管：了解重点客户、销售过程和策略执行情况；
- 销售运营：配置客户分层、线索评分和策略规则；
- 市场团队：判断不同渠道带来的线索质量和转化情况。

#### 4. 完整业务流程

第一步，汇集客户信息。系统从CRM、Excel、表单、企业官网、新闻、财务资料和历史沟通记录中获得客户信息。

第二步，生成客户画像。系统整理企业规模、行业、近期动态、历史关系、潜在需求和信息缺口，并区分明确事实、模型推测和证据不足。

第三步，判断销售机会。系统结合结构化条件、公开信号和历史行为，判断客户优先级、采购信号和当前销售阶段。

第四步，推荐销售策略。系统给出推荐联系角色、业务切入点、适合的产品方案、需要确认的问题和下一步最佳行动。

第五步，生成销售内容。系统根据客户画像和策略生成客户简报、邮件、微信话术、电话提纲、会议材料和会后跟进内容。

第六步，记录结果并优化。销售人员反馈是否采纳、客户是否回复、是否约到会议以及推荐是否准确，系统据此优化评分规则、提示词和销售策略库。

完整流程如下：

```text
客户或线索进入
→ 补充企业与联系人信息
→ 提取业务动态和采购信号
→ 生成客户画像
→ 进行优先级判断
→ 推荐销售策略和下一步行动
→ 生成个性化沟通内容
→ 销售人员确认并执行
→ 记录回复、会议和转化结果
→ 优化评分与策略
```

#### 5. AI 规则与系统分工

| 任务 | 主要实现方式 |
|---|---|
| 企业规模、行业、地区等硬性条件 | 结构化数据与规则 |
| 搜索客户最新信息 | 搜索、API或外部数据工具 |
| 从新闻和沟通记录提取业务信号 | 大模型 |
| 线索优先级判断 | 规则评分与模型信号结合 |
| 从企业产品中匹配方案 | RAG、产品规则与大模型 |
| 推荐销售策略 | 大模型与销售策略知识库 |
| 生成客户简报和沟通内容 | 大模型 |
| 将结果写回CRM | API或Function Calling |
| 统计销售效果 | 数据分析与指标系统 |

#### 6. 完整产品页面

1. 销售线索池：展示线索等级、推荐理由、采购信号和下一步行动；
2. 客户研究报告：展示企业画像、业务动态、历史沟通、来源和信息缺口；
3. 销售策略工作台：展示推荐切入点、产品方案、关键问题和沟通策略；
4. 内容生成编辑器：生成邮件、微信话术、会议提纲和建议书，并支持人工修改；
5. 客户互动记录：记录触达、回复、会议、异议和下一步计划；
6. 销售效果看板：展示推荐采纳率、客户回复率、会议转化率和线索质量；
7. 策略与规则配置：配置客户条件、评分项、产品适用条件和风险规则。

#### 7. 完整产品评测指标

- 客户信息提取准确率；
- 事实来源覆盖率；
- 采购信号识别准确率；
- 高价值客户命中率；
- 产品与方案匹配合理性；
- 销售策略采纳率；
- 生成内容人工修改率；
- 客户回复率；
- 会议转化率；
- 销售人员节省的时间；
- 模型推测被误认为事实的比例。

#### 8. 完整项目交付物

- 销售业务背景与用户研究；
- 客户研究和销售跟进现状流程；
- 完整产品PRD；
- 客户画像和销售策略数据结构；
- AI工作流与外部数据调用方案；
- 产品知识库和销售策略库设计；
- 线索评分与规则方案；
- Prompt与结构化输出设计；
- 核心页面原型；
- 评测集、指标与Bad Case；
- 数据反馈和持续优化方案；
- 项目作品集与简历描述。

#### 9. 与当前课程版本的关系

当前课程只要求完成客户研究、带来源简报、产品知识检索、方案匹配、销售建议生成和人工确认。线索评分、自动分配、自动触达、CRM回流、销售经营看板和成交预测保留为后期延展。

### 二 采购穿行与票据核验系统完整蓝图

#### 1. 产品定位

这是一个面向财务、采购、审计和合规团队的AI风险核验产品。它不仅处理单张发票，还可以逐步扩展到同一笔采购业务中的申请、合同、订单、入库、验收、发票、付款和入账记录。

完整产品的目标是：

> 让AI读取业务单据、提取关键字段、完成跨单据核对，并把真正可疑的问题和原始证据交给人工复核。

#### 2. 业务背景

一笔采购业务可能存在以下问题：

- 发票金额与合同或订单金额不一致；
- 入库数量与采购数量不一致；
- 开票日期早于业务发生日期；
- 供应商名称在不同单据中不一致；
- 付款账户与合同账户不一致；
- 同一张发票被重复使用；
- 必要业务单据缺失；
- 审批或验收流程不完整；
- 合同条款与实际执行不一致。

传统处理方式需要人工逐张打开文件、查找字段、复制到Excel并进行核对，效率低且容易遗漏。

#### 3. 目标用户

- 企业财务和应付账款人员；
- 采购管理人员；
- 内部审计人员；
- 会计师事务所和投行核查人员；
- 合规与风险控制团队；
- 业务部门的单据提交和整改人员。

#### 4. 完整业务链路

```text
采购申请
→ 业务审批
→ 签订合同或下达订单
→ 货物入库
→ 验收
→ 收到发票
→ 付款申请
→ 银行付款
→ 财务入账
```

系统围绕这条业务链路检查资料是否齐全、字段是否一致、时间是否合理、金额是否匹配，以及是否存在重复或异常。

#### 5. 完整产品流程

第一步，创建核验任务并选择采购穿行、销售穿行、报销核验、合同发票核验或付款核验等类型。

第二步，上传ERP交易数据和业务文档。系统自动判断文件属于申请单、合同、订单、入库单、验收单、发票、付款记录或其他附件。

第三步，使用OCR、视觉模型和大模型提取供应商、统一社会信用代码、单号、日期、数量、含税金额、税率、银行账户等字段。

第四步，对供应商名称、业务单号和金额等信息进行标准化和实体对齐，同时保留原始文本、来源文档和原文位置。

第五步，关联属于同一笔业务的不同单据，形成完整业务链。

第六步，执行确定性核验规则，检查金额、数量、币种、税率、日期顺序、供应商、付款账户、重复票据和必要文档。

第七步，使用大模型辅助发现合同语义、附件描述和交易背景中的复杂冲突，但不让模型独立完成精确金额判断。

第八步，生成风险等级、差异字段、触发规则、原始证据和建议核查事项。

第九步，由审核人员确认、驳回、修改字段、补充说明、要求整改或标记解决，并保留完整处理记录。

#### 6. AI 规则与人工分工

| 任务 | 主要实现方式 |
|---|---|
| 文档图像和文字识别 | OCR或视觉模型 |
| 文档分类 | 分类模型或大模型 |
| 非结构化字段提取 | 视觉模型与大模型 |
| 金额、数量、日期比较 | 确定性规则 |
| 发票号码重复检查 | 数据库规则 |
| 供应商名称对齐 | 字符匹配、企业标识与语义判断 |
| 合同条款与附件语义冲突 | 大模型辅助 |
| 风险等级 | 规则为主，模型辅助 |
| 风险解释和报告初稿 | 大模型 |
| 最终审计或核查结论 | 人工负责 |

#### 7. 完整产品页面

1. 核验任务列表：展示任务状态、单据数量、风险数量、负责人和处理时效；
2. 资料上传与分类：展示文件分类、缺失单据和识别状态；
3. 文档识别页面：左侧显示原始文档，右侧显示提取字段和置信度；
4. 业务链路页面：展示申请、合同、订单、入库、发票和付款之间的关联；
5. 跨单据比对矩阵：横向比较关键字段并高亮差异；
6. 风险详情页面：展示异常原因、规则、涉及文档和原始证据；
7. 人工复核页面：支持确认、修正、驳回、补充说明和发起整改；
8. 核验报告页面：生成风险汇总、整改状态和正式报告；
9. 风险管理看板：展示风险类型、业务部门、供应商和时间趋势；
10. 规则配置页面：管理字段、阈值、比较方式和风险等级。

#### 8. 完整产品评测指标

- 文档分类准确率；
- 关键字段提取准确率；
- 金额和票据号码完全一致率；
- 单据关联准确率；
- 风险召回率；
- 风险准确率；
- 误报率和漏报率；
- 原始证据定位准确率；
- 人工修正率；
- 人工复核通过率；
- 单个核验任务节省时间；
- 高风险问题遗漏数量。

金额、票据号码等字段不能只采用语义相似度评测，必须使用精确匹配或确定性计算。

#### 9. 完整项目交付物

- 业务背景和穿行测试说明；
- 用户、角色和现状流程；
- 完整产品PRD；
- 单据清单、字段字典和实体关系；
- 文档识别与字段提取流程；
- 单据关联和核验规则表；
- 风险分级和人工复核方案；
- 核心页面原型；
- 测试单据、评测集和Bad Case；
- 审核留痕和反馈闭环；
- 项目作品集和简历描述。

#### 10. 与当前课程版本的关系

当前课程只要求ERP交易数据、采购申请单、入库单和发票的识别、关联、字段核验、差异汇总和人工复核。合同、订单、验收、付款、供应商风险、其他核查场景、风险看板和持续控制监测保留为后期延展。

### 三 智能标书与RFP响应平台完整蓝图

#### 1. 产品定位

这是一个帮助企业发现招投标机会、理解RFP要求、组织响应材料并生成投标文件的企业知识生产平台。

完整产品希望把一份复杂的招标文件转化成可追踪的要求和任务，再利用企业知识库生成有依据、可核验的投标内容。

#### 2. 业务背景

大型标书可能包含数百页内容，要求企业在较短时间内完成：

- 寻找值得参与的项目；
- 阅读招标文件；
- 判断是否具备投标资格；
- 提取强制要求和评分项；
- 拆分响应任务；
- 查找产品、案例和资质；
- 编写技术与商务方案；
- 组织多部门协作；
- 检查遗漏、矛盾和过期材料；
- 生成符合格式要求的最终文件。

常见问题包括要求遗漏、历史资料分散、重复写作、版本混乱、技术参数不一致、资质材料过期以及大模型虚构企业能力。

#### 3. 目标用户

- 销售和投标负责人；
- 售前解决方案经理；
- 产品和技术负责人；
- 商务、财务、法务和合规人员；
- 标书制作人员；
- 项目负责人和管理者。

#### 4. 完整产品流程

第一步，发现投标机会。系统根据企业能力和目标行业搜索匹配的RFP，或接收用户上传的招标文件。

第二步，完成资格初判。系统提取项目名称、截止时间、投标资格、否决项和关键要求，辅助判断是否值得参与。

第三步，生成要求与响应矩阵。系统将资格、技术、商务、交付、服务、评分和证明材料要求整理成可追踪清单，并保留原文位置。

第四步，接入企业资料。系统读取公司信息、产品文档、技术参数、客户案例、历史标书、资质证书、服务承诺和标准条款。

第五步，拆分标书结构和协作任务。系统根据招标要求和评分标准形成商务标、技术标及其他材料的目录，并将章节分配给相关角色。

第六步，分章节生成内容。系统采用树状工作流生成一级、二级和三级目录，再分别调用知识库生成章节内容，每个节点持续携带招标要求和评分规则。

第七步，进行事实与合规检查。系统检查是否遗漏强制项、参数是否一致、资质是否过期、引用是否正确、承诺是否超出企业能力、章节和附件是否完整。

第八步，进行人工协作、审核和版本管理。不同人员编辑、提交、审核和确认负责的章节，并处理资料缺失和高风险承诺。

第九步，生成和导出最终文件，同时保存响应矩阵、风险清单、引用材料、审核记录和项目复盘。

完整流程如下：

```text
输入企业能力
→ 发现或上传RFP
→ 资格判断与要求抽取
→ 生成带证据的响应矩阵
→ 检索企业产品 案例 资质和历史标书
→ 生成标书目录
→ 分配章节任务
→ 分章节生成内容
→ 一致性 事实和合规检查
→ 多人校对与审批
→ 排版导出
→ 投标结果与知识回流
```

#### 5. 完整产品中的AI能力

| 能力 | 产品应用 |
|---|---|
| 长文档解析 | 理解招标文件、评分标准和附件 |
| 信息抽取 | 提取资格、参数、时间、评分项和否决项 |
| RAG | 检索企业产品、案例、资质和历史材料 |
| 内容生成 | 生成技术方案、商务响应和章节草稿 |
| Agent任务规划 | 拆分目录、章节和处理步骤 |
| Workflow | 控制解析、生成、审核和导出流程 |
| 规则检查 | 检查强制项、数字、格式和材料完整性 |
| 语义检查 | 发现前后矛盾、过度承诺和能力夸大 |
| Function Calling | 调用资质库、项目库、CRM和文档系统 |
| 人机协同 | 处理资料缺失、关键承诺和最终定稿 |

#### 6. 完整产品页面

1. RFP机会列表：展示项目匹配度、截止时间、资格和参与建议；
2. 投标项目首页：展示整体进度、风险、负责人和关键时间；
3. 招标文件解析：原文与提取结果对照，并支持定位证据；
4. 要求与响应矩阵：管理每项要求的状态、响应方式、负责人和证据；
5. 企业知识库：管理产品、案例、资质、历史标书和标准条款；
6. 章节任务看板：展示章节负责人、状态、截止时间和审核人；
7. AI标书编辑器：编辑章节内容，同时查看引用材料、生成依据和风险；
8. 标书检查中心：展示遗漏、矛盾、过期资质、无依据内容和高风险承诺；
9. 审核与审批页面：完成跨部门审核和最终确认；
10. 版本与导出页面：比较版本并生成Word或PDF；
11. 项目复盘页面：记录投标结果、材料复用和需要更新的知识。

#### 7. 完整产品评测指标

- RFP机会匹配准确率；
- 投标资格判断准确率；
- 强制要求召回率；
- 要求分类和去重准确率；
- 响应项覆盖率；
- 知识检索命中率；
- 引用来源准确率；
- 生成内容事实准确率；
- 无依据内容比例和幻觉率；
- 遗漏项识别准确率；
- 参数与章节一致性；
- 人工修改率；
- 标书制作时间缩短比例；
- 历史材料复用率。

评测重点不是文案是否流畅，而是有没有漏项、有没有依据、有没有虚构、能不能实际交付。

#### 9. 与当前课程版本的关系

当前课程要求完成RFP发现或上传、资格和要求抽取、带证据的需求清单、企业资料检索、目录生成、部分章节生成、证据不足标记、人工校对和草稿输出。完整多人任务管理、审批、复杂权限、版本平台、CRM集成、中标分析和投标协同保留为后期延展。

### 四 完整蓝图的使用规则

1. 前一版完整蓝图用于展示产品可能的长期演进，不用于反向扩大当前MVP；
2. 当前课程先把最短、最重要且有明确来源的主链路讲透；
3. 只有当核心链路已通过测试，才讨论完整蓝图中的扩展功能；
4. 扩展功能进入正式课程前，必须重新补充来源、用户证据、数据条件和评测方法；
5. PPT和学员任务书必须明确区分“当前实现”和“未来规划”；
6. 学员可以在主项目深化时选择一至两个扩展方向，但不能把扩展清单全部堆进第一版PRD。
