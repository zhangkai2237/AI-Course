## 一、课程定位

第02课已经解决“如何把业务要求写进结构化 Prompt，并把 Prompt 封装进产品”。但单次模型调用仍只能完成一次处理。本课向前推进一步：

> 当任务需要多步处理、条件分流、不同风险走不同路径时，产品经理如何先画清业务流程，再把流程翻译成 Workflow 节点并完成最小测试闭环。

本课不重新讲“AI产品经理是什么”，也不重复第0课的场景价值判断；重点是让学员第一次获得**从流程图到可运行 Demo**的体验。

## 四、本课程教学重组（T）

以下内容不是某一参考课的逐字结论，而是基于来源重新组织的教学方法：

1. **Workflow五块积木**：节点、连线、变量、分支、输出。
2. **四步设计法**：先定输出 → 明确输入 → 画业务路径 → 准备测试集。
3. **三版递进产出**：纸面V0.1 → 单路V0.2 → 四路V0.3。
4. **四步排查法**：先看输入变量 → 再看节点输出 → 再看分支条件 → 最后改Prompt或模型。

## 五、虚构案例（CASE）

### 商家咨询分流助手

背景：虚构的“邻里增长平台”每天收到大量商家咨询。第一版不追求自动解决所有问题，只需要判断问题属于哪一类，并进入安全路径。

- `RULE`：平台规则/活动规则咨询 → 基于课堂规则卡回答；
- `DATA`：GMV、订单、结算、门店状态等实时数据 → 明确提示需查询业务系统，不生成数值；
- `COMPLAINT`：投诉、扣费争议、退款赔付、高风险表达 → 记录原问题并转人工，不承诺结果；
- `OTHER`：信息不足或不属于以上三类 → 追问一个澄清问题。

所有公司名、规则、数据和话术均为教学虚构。

## 六、本课明确不讲

- RAG原理、知识库切片、召回和引用；
- 真实API、数据库或插件接入；
- Agent自主规划、工具选择与多Agent；
- 循环、复杂异常重试、子工作流和长期记忆；
- 特定平台全部按钮和版本细节；
- 可直接上线的客服系统。

## 七、结论

本课定位合理，且与第02课形成清晰增量：第二课教会模型“一次怎么做”，第三课教产品“不同情况分别怎么走”。核心知识均能在现有参考课程中找到明确位置；案例和四步法属于透明标注的课程教学重组，不伪装成参考课原话。
