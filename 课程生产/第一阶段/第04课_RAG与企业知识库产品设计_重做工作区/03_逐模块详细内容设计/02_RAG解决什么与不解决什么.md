# 02 RAG解决什么与不解决什么（8-23分钟）

## 教学目标

让学员建立RAG的正确边界，避免形成“企业数据都放进知识库”的错误理解。

## 产品化定义

> RAG（Retrieval-Augmented Generation，检索增强生成）是：收到用户问题后，先从指定的外部知识源中找出相关内容，再把问题和找到的内容一起交给大模型生成答案。

用一句更口语的话：

> 不是让模型凭记忆闭卷回答，而是先找到允许使用的资料，再带着资料回答。

“开卷考试”只是帮助理解的类比，正式产品仍要拆成检索、生成、引用和失败处理。

## RAG主要解决的四类问题

### 1. 模型不知道企业内部知识

例如：

- 商家活动规则；
- 企业制度和流程；
- 产品使用说明；
- 售后政策；
- 项目历史经验；
- 内部FAQ。

这些内容没有进入通用模型训练，单靠角色Prompt无法补齐。

### 2. 知识需要持续更新

直接重新训练或微调模型成本高、周期长。知识库允许在不改变模型参数的情况下增删文档、更新版本。

需要提醒：能更新不等于自动正确。旧文档是否下线、更新是否审核，仍然是产品和运营问题。

### 3. 用户表达方式不统一

文档里写“活动有效期”，用户可能问：

- “这个优惠到哪天？”
- “月底还能报名吗？”
- “什么时候截止？”

语义检索的价值是根据意思寻找相关片段，而不只匹配完全相同的关键词。

### 4. 回答需要提供依据

企业问答不能只给一个流畅答案，还要能够回到：

- 哪份文档；
- 哪个章节或片段；
- 什么版本；
- 什么生效时间。

这使用户、客服和运营人员可以核验，也便于出错后定位。

## RAG不能解决的四类问题

### 1. 实时业务事实

“我门店今天用了多少补贴”“订单为什么没到账”需要查询业务系统，而不是搜索静态文档。

RAG可以查“补贴规则是什么”，不能查“我的补贴实际发生了多少”。

### 2. 知识库里根本不存在的答案

检索不到可靠内容时，正确策略是：

- 明确没有找到；
- 追问补充信息；
- 引导到其他系统；
- 转人工。

不能让模型用通用常识补齐企业事实。

### 3. 高风险业务裁决

投诉、赔付、法律承诺和账户操作，不应因为检索到一段文字就自动执行。RAG可以提供参考依据，但不能自动获得决策权限。

### 4. 模型本身的所有能力问题

RAG不会自动提升：

- 复杂推理的稳定性；
- 特定语气的高度一致性；
- 工具操作能力；
- 所有领域的专业判断。

## 四类能力对比

| 用户问题 | 应使用的主能力 | 原因 |
|---|---|---|
| “把这段话改得更礼貌” | Prompt | 已提供全部材料，只需一次生成 |
| “新客立减活动到哪天” | RAG | 答案来自可更新的内部规则 |
| “我门店今天消耗了多少补贴” | 业务系统/API | 查询实时、精准的个体数据 |
| “平台必须赔我5000元” | 人工/受控流程 | 涉及争议和高风险承诺 |

## 课堂微判断

让学员依次判断：

1. 查询公司报销制度；
2. 查询本月工资是否到账；
3. 根据产品手册回答使用问题；
4. 生成一个无约束的创意口号；
5. 查询某笔退款的最新状态。

参考：

- 1、3适合RAG；
- 2、5查询业务系统；
- 4通常直接使用Prompt。

## 常见误区纠偏

- 错误：“RAG就是把所有数据扔进去。”
  - 纠偏：先定义用户问题，再选择允许使用的数据源。
- 错误：“RAG能解决幻觉。”
  - 纠偏：只能增加可靠上下文，检索或生成仍可能出错。
- 错误：“文件越多越好。”
  - 纠偏：错误、过期和冲突的知识会放大产品风险。
