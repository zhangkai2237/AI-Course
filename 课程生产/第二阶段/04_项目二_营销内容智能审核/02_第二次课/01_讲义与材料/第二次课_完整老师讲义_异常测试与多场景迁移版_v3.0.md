# 项目二｜营销内容智能审核｜第二次课老师讲义

## 真实异常、测试判断与多场景迁移

> 适用对象：已完成项目第一次课，理解业务流程、审核点、规则与模型基本分工的学员。  
> 建议时长：180分钟。  
> 本课定位：继续推进项目，不重复讲基础理论。核心是让学员看到一个方案怎样从“能跑”走向“敢试点”，以及怎样迁移到新的业务场景。

---

## 一、课程目标

完成本课后，学员应能：

1. 把异常从一句报错提示，设计成可恢复、可交接、可追溯的产品流程；
2. 面对资料缺失、局部失败、版本错位、结论冲突和无人承接时，做出继续、重试、降级、转人工或终止的取舍；
3. 建立测试样本与指标体系，并根据测试结果判断方案应进入试点、补齐能力、收缩范围还是暂停；
4. 用同一套方法重新分析合同、客服、招聘、报销和金融营销等判断型 AI 产品；
5. 说清不同场景中对象、材料、责任角色和企业系统为什么不同。

| 时间 | 内容 | 核心产出 |

# 开场：一个产品能运行，不等于能交给真实业务（00—10分钟）

## 教师讲述

第一次课里，我们已经把营销内容审核的业务对象、审核点、能力分工和核心流程搭出来了。如果只演示正常流程，系统很容易显得完整：提交一段文案，机器返回几个问题，运营修改，再次提交。

但真实业务不会一直配合我们的流程。活动材料可能没同步，某一路模型会超时，用户会在检查途中修改文案，规则和模型会给出不同判断，人工也可能不知道该由谁处理。

所以今天不再继续堆功能，而是回答三个更难的问题：

1. 正常流程被打断时，产品怎样安全地继续；
2. 测试结果不完美时，产品经理怎样决定下一步；
3. 离开营销审核以后，这套方法是否还能迁移到其他业务。

板书：

```text
能跑通：证明流程存在
能处理异常：证明流程可以被真实使用
能根据测试取舍：证明方案可以被管理
能迁移到新场景：证明掌握的是方法，而不是模板
```

# 第四节：真实异常中的产品取舍（10—60分钟）

## 1. 异常设计不是写一句“系统失败”（10—17分钟）

### 教师讲述

异常不是技术团队内部的一条报错，而是一次业务任务没有按预期完成。产品要告诉用户：哪里没有完成、已经完成了什么、现在还能做什么、下一步由谁负责。

一个完整的异常设计至少包含八项：

| 项目 | 要回答的问题 |
| --- | --- |
| 触发条件 | 什么情况被判定为异常 |
| 影响范围 | 影响一个检查点、一个分支还是整次任务 |
| 当前状态 | 已经完成什么，还缺什么 |
| 页面表达 | 用户能否看懂发生了什么 |
| 可执行动作 | 重试、补材料、转人工、继续还是终止 |
| 处理角色 | 谁拥有下一步权限 |
| 恢复方式 | 条件补齐以后怎样继续 |
| 过程留存 | 原输入、输出、时间与人工动作能否回看 |

板书：

```text
异常设计
≠ 告诉用户“失败了”
= 告诉用户“哪里没完成、还能做什么、由谁继续”
```

## 2. 异常一：业务材料缺失（17—25分钟）

### 案例

文案写着“下单即送滤芯”，但系统没有找到本次活动的赠品资格、数量和有效期。

这时不能直接判断“违规”，也不能判断“没有问题”。系统只能说明：完成赠品检查所需的材料缺失。

| 项目 | 产品设计 |
| --- | --- |
| 当前结论 | 赠品检查未完成，不输出确定结论 |
| 其他检查 | 与赠品无关的分支继续运行 |
| 页面提示 | 明确缺少哪类材料、影响哪个检查点 |
| 用户动作 | 补材料、选择正确活动或交负责人确认 |
| 恢复方式 | 补齐后只重跑受影响分支，形成新记录 |

### 教师强调

“材料缺失”和“内容错误”是两个不同状态。前者是信息不足，后者是现有材料已经足以说明内容不符合要求。把二者混在一起，运营就不知道应该改文案还是补材料。

## 3. 异常二：模型超时或局部失败（25—33分钟）

一次检查包含三个分支：功能对象检查已完成，价格条件检查已完成，赠品语义检查超时。

正确的产品状态应当是：

```text
整次运行：部分完成
├─ 功能对象：完成
├─ 价格条件：完成
└─ 赠品语义：超时，等待重试或人工补核
```

常见错误包括：

- 整页只显示“系统异常”；
- 把超时分支显示为“未发现问题”；
- 让用户反复点击，生成多个重复任务；
- 重试后覆盖第一次运行，无法回看发生过什么。

如果赠品检查是当前活动的必检项，系统不能自动给出完整通过。可以要求重试成功后再决定，也可以允许有权限的审核员完成人工补核并记录原因。决定依据不是技术成功率，而是缺失分支是否影响当前业务决定。

## 4. 异常三：旧版本结果迟到（33—40分钟）

### 演示顺序

1. 用 V1 文案发起检查；
2. 检查运行中保存 V2；
3. V1 的结果在稍后返回；
4. 结果仍绑定 V1，不覆盖 V2；
5. V2 页面提示“内容已变化，需要重新检查”。

### 四条原则

- 迟到结果要保留在原运行中；
- 迟到结果不能自动覆盖当前版本；
- 页面必须展示内容版本、材料版本和规则版本；
- 正式提交时，当前版本必须拥有有效的完整运行。

教师可追问：“结果本身是正确的，为什么不能继续用？”

收口：因为结果正确不代表对象一致。AI 输出必须和当时的输入快照绑定。

## 5. 异常四：规则与模型结论冲突（40—48分钟）

### 场景一

文案写着“最后看一下会员券，价格会更划算”。关键词规则命中“最后”，模型结合上下文认为它是顺序词，并非绝对化承诺。

### 场景二

程序确认“1799元”的数字计算成立，但模型发现文案遗漏了新会员资格和两类券的使用条件。

### 教师讲述

规则与模型不是两位投票者。它们可能在回答不同问题：

- 规则检查确定表达、字段和值；
- 模型判断上下文、对象关系与语义条件；
- 程序确认计算与格式；
- 业务材料说明事实范围；
- 人工处理无法自动确定的争议。

| 情况 | 建议动作 |
| --- | --- |
| 关键词命中但上下文是否定或引用 | 保留命中位置，进入语义复核 |
| 数值成立但适用条件缺失 | 保留计算结果，同时提出条件缺失 |
| 两份业务材料互相矛盾 | 暂停确定判断，交材料负责人确认有效版本 |
| 模型定位的原句不存在 | 判定输出校验失败，不进入业务结果 |
| 多个分支报告同一问题 | 按位置与类型合并，保留各分支记录 |

## 6. 异常五：有问题但无人承接（48—54分钟）

### 三类角色场景

- 作者不同意机器结论：可以发起异议，但不能直接把正式任务改成通过；
- 审核员发现材料可能过期：可以标记未完成并转给材料负责人，不能静默修改受控材料；
- 巡检发现线上问题：系统要有认领、处理时限和升级对象，不能只把问题丢进列表。

| 角色 | 可以做什么 | 不应直接做什么 |
| --- | --- | --- |
| 作者 | 修改正文、补充上下文、提交异议 | 修改正式审核结论 |
| 审核员 | 确认、退回、人工补核、记录原因 | 把旧版本通过状态复制给新版本 |
| 材料负责人 | 更新受控材料、确认有效期 | 静默改写历史运行所用材料 |
| 内容负责人 | 分配问题、核验实际修改、发起升级 | 未经复核关闭高风险问题 |
| 系统维护人员 | 查看调用与校验失败、恢复服务 | 代替业务人员作内容决定 |

## 7. 五种取舍动作（54—58分钟）

```text
继续：未完成项不影响当前业务决定
重试：输入有效，只是执行暂时失败
降级：切换到边界明确的替代能力
转人工：需要业务判断、权限或补充信息
终止：输入不合法或无法安全继续
```

教师强调：降级不是把失败改成成功，而是明确换用另一种已知能力，并向用户说明当前边界。

## 8. 本节收束（58—60分钟）

```text
正常流程决定产品能不能演示
异常流程决定产品能不能交给真实业务
```

# 第五节：用测试结果判断方案是否成立（70—115分钟）

## 1. 测试不是给模型打一个总分（70—76分钟）

### 教师讲述

产品经理测试的不是“模型聪不聪明”，而是整套方案能否完成业务任务。需要一起观察规则、模型、业务材料、结果合并、页面动作和人工承接。

测试要回答四个问题：

1. 能不能识别应该识别的问题；
2. 输出能不能被业务人员直接处理；
3. 系统失败或不确定时能不能安全停下；
4. 相比人工基线，是否真的减少了总投入。

## 2. 建立可复现的测试样本（76—83分钟）

首版样本可以来自脱敏历史内容、审核员整理的典型案例、重点规则的边界样本和已上线内容的抽检结果。

每条样本至少包含：

| 字段 | 说明 |
| --- | --- |
| 内容与场景 | 被审核文案及发布场景 |
| 必要上下文 | 商品、活动、渠道与业务材料 |
| 问题位置 | 应被标记的原文范围 |
| 问题类型与等级 | 期望分类和风险等级 |
| 期望动作 | 通过、修改、退回或转人工 |
| 标注人与版本 | 谁确认、按哪个规则版本确认 |

测试集还要保留正常样本、问题样本、边界样本和异常样本，不能只放“明显违规”的简单题。

## 3. 四组指标一起看（83—91分钟）

| 指标组 | 关注内容 | 它回答的问题 |
| --- | --- | --- |
| 识别效果 | 分类型准确率、召回率、F1、定位正确率 | 找得准不准、漏得多不多 |
| 工程稳定性 | 结构化输出成功率、超时率、依赖失败率 | 能不能稳定完成流程 |
| 业务处理 | 人工复核比例、平均处理时长、一次修改通过率 | 是否减少了真实工作量 |
| 高风险表现 | 严重漏检数、人工调整高风险结论比例 | 是否达到可接受的安全边界 |

课堂可以用“准确率不低于90%、召回率不低于85%、单篇两分钟内”作为讨论用假设，但必须强调：真实门槛要根据问题成本、样本分布和人工基线共同确定，不能把课堂数值直接带进项目。

## 4. 测试结果要与人工基线比较（91—97分钟）

假设人工审核平均每篇 8 分钟，机器运行 40 秒，但有 60% 的内容仍需人工复核。如果复核还要花 6 分钟，整套方案未必比原流程更省。

产品经理要比较的是：

```text
机器耗时
+ 人工复核耗时
+ 失败与返工耗时
+ 规则和材料维护成本
= 新流程总投入
```

不能因为模型速度快，就认定业务效率提升。

## 5. 用四种结论判断下一步（97—104分钟）

| 测试表现 | 产品判断 | 下一步 |
| --- | --- | --- |
| 高风险表现可接受，流程稳定，人工投入下降 | 方案成立 | 进入限定范围试点 |
| 主要问题集中在少数可修复环节 | 方向成立、能力未齐 | 补材料、调规则或优化合并后回归 |
| 某类场景持续表现差，拖累整体结果 | 范围过大 | 收缩场景或拆分流程 |
| 高风险漏检不可接受，失败无法安全承接 | 当前方案不成立 | 暂停试点，重新设计 |

教师强调：测试不是为了证明之前的方案正确，而是为了决定下一步怎么做。

## 6. 三个坏案例怎样定位根因（104—111分钟）

### 坏案例一：否定句误报

输入：“我们不承诺100%有效，实际体验因人而异。”

问题：关键词命中后直接判高风险，忽略否定关系。

改进：关键词负责召回，增加上下文语义确认；把否定句、引用句和对比句加入回归样本。

### 坏案例二：上下文不足却强行下结论

输入：“连续三年销量第一。”

问题：系统不知道是否存在有效报告，却直接给出通过或不通过。

改进：检查报告范围、时间和来源；缺失时返回“需补充材料”或转人工。

### 坏案例三：一个问题重复展示

输入：“全网第一，排名第一。”

问题：规则和模型产生多条高度重叠结果，运营不知道先处理哪一条。

改进：按位置、类型和语义相似度合并；保留最高等级和完整判断说明。

### 根因分类

```text
误报 / 漏报 / 分级错误 / 定位错误 / 材料缺失
输出校验失败 / 结果合并失败 / 页面动作不可用 / 人工承接失败
```

## 7. 形成版本迭代闭环（111—114分钟）

```text
线上任务
  ↓
机器结果与人工结果对比
  ↓
归类问题并定位责任环节
  ↓
修改规则、提示、业务材料、合并逻辑或页面交互
  ↓
回归测试
  ↓
发布新版本并继续观察
```

每次迭代都要记录：改了什么、为什么改、影响哪些样本、旧问题是否消失、是否引入新问题。

## 8. 本节收束（114—115分钟）

```text
一个漂亮的平均分，不能替代产品判断。
产品经理要用测试结果决定：进入试点、补齐能力、收缩范围，还是暂停。
```

# 第七节：从合同审核到多个判断型 AI 产品（125—175分钟）

## 1. 为什么从合同审核开始（125—128分钟）

合同审核和营销审核都不是单纯生成文本，而是在材料、规则和业务上下文之间做判断。它适合作为迁移的母案例，因为边界、责任和人工确认都很清楚。

本节吸收知乎第5课法律合同审核案例的讲法，但目标不是复制课程内容，而是把“先理解人工工作，再设计 AI 流程”的方法迁移到本项目和其他业务。

## 2. 母案例：常规业务合同初步审核（128—140分钟）

### 首版边界

第一版不做诉讼判断、完整法律咨询和自动作出最终决定。只做常规业务合同的初步检查、问题条款定位、修改建议和待确认项整理。

### 人工原来检查什么

| 对象 | 要回答的问题 |
| --- | --- |
| 合同主体 | 签约对象是否准确，主体是否存在异常 |
| 合同条款 | 付款、交付、验收、违约等条款是否合理 |
| 规范引用 | 引用是否准确、是否仍适用 |
| 履约方式 | 约定在真实业务中能否执行 |
| 周边风险 | 对方历史履约与合作关系是否存在异常 |

### 从输出反推输入

输出包括问题条款、问题类型、原因、业务影响、修改建议和待确认项。要得到这些结果，输入不能只有合同正文，还需要审核重点、企业合同规则、对方企业信息和交易背景。

### 工作流

```text
文件解析
  ↓
条款检查 / 规范引用检查 / 企业与履约风险检查
  ↓
结果合并、分级、冲突处理
  ↓
法务确认、修改、审批与归档
```

### 企业连接

“30天交付”在文本上可能正常，但结合库存、产能、物料和历史履约后，可能成为真实风险。企业 AI 产品的价值，往往来自对这家公司当前业务状态的理解。

## 3. 十一项迁移框架（140—145分钟）

| 阶段 | 项目 |
| --- | --- |
| 定义 | 业务问题、首版小场景、人工工序、最终输出 |
| 构建 | 输入来源、快速验证、并行拆分、边界分支 |
| 落地 | 结果合并、企业连接、运行验证 |

板书：

```text
先定义要支持的业务决定
→ 还原人工工序
→ 反推输出与输入
→ 验证基础能力
→ 拆分流程与边界
→ 接入企业系统
→ 用运行结果判断是否继续
```

## 4. 案例一：售后退款会话质检（145—152分钟）

### 业务情境

客服承诺“今天到账”，但前序口径是三个工作日，随后又出现推诿。系统需要结合多轮会话、订单状态和服务政策判断。

| 项目 | 设计 |
| --- | --- |
| 首版范围 | 售后退款会话中的口径一致性、流程遵循和服务问题 |
| 人工工序 | 还原角色与时间线，核对订单，定位问题，确认申诉与整改 |
| 输入 | 会话、角色、订单退款状态、服务政策、质检规则 |
| 并行流程 | 流程规则检查、多轮语义判断、订单与政策核对 |
| 输出 | 问题位置、类型、等级、整改建议、待确认项 |
| 异常 | 转写失败、角色混淆、接口无返回、客服申诉 |
| 人工承接 | 质检主管复核，客服确认或申诉 |
| 企业连接 | CRM、订单、工单、知识库和培训系统 |

关键结论：质检产品的终点不是给会话打分，而是确认、申诉、整改与复训。

## 5. 案例二：岗位发布前的招聘信息审核（152—158分钟）

### 业务情境

岗位文案同时出现高薪承诺、性别年龄限制、本地户口、零经验和付费培训。系统需要区分文本表达问题与企业事实问题。

| 项目 | 设计 |
| --- | --- |
| 首版范围 | 岗位发布前的必填项、限制性表达和承诺一致性检查 |
| 人工工序 | 查企业、岗位、薪资、必填项和限制条件 |
| 输入 | 招聘文案、企业、岗位编制、薪酬范围、渠道要求 |
| 并行流程 | 文案必填项、企业账号、岗位资料一致性 |
| 输出 | 缺项、问题位置、类型、修改要求与转人工状态 |
| 异常 | 岗位无法确认、资料冲突、异常引流 |
| 人工承接 | 招聘运营和 HR 负责人确认 |
| 企业连接 | 招聘系统、岗位编制、薪酬和投诉记录 |

关键结论：模型能看表达，企业系统才能确认岗位和承诺是否真实。

## 6. 案例三：员工费用报销初步审核（158—164分钟）

### 业务情境

周末高额休闲服务发票备注“客户招待”；金额在权限内，但没有 OA 申请，部门预算也接近用完。多个单点正常，不代表整体成立。

| 项目 | 设计 |
| --- | --- |
| 首版范围 | 报销提交后的票据、制度、预算与审批初步检查 |
| 人工工序 | 验票、核科目、核金额、查人员、预算、合同与审批 |
| 输入 | 发票、报销单、员工部门、预算、合同、OA和制度 |
| 并行流程 | 票据验真、政策检查、预算检查、合同与审批核对 |
| 输出 | 可继续、待补材料、退回、等待预算、转人工 |
| 异常 | 接口失败、重复报销、业务矛盾、多路冲突 |
| 人工承接 | 财务复核并完成最终处理 |
| 企业连接 | 财务、OA、预算、合同和付款系统 |

关键结论：发票真实不等于报销成立，首版也不应自动付款。

## 7. 案例四：理财产品营销材料审核（164—170分钟）

### 业务情境

文案宣称“年化收益6%”“本金安全”“适合所有投资者”。系统需要结合正式产品材料、风险提示、目标人群和渠道版本进行判断。

| 项目 | 设计 |
| --- | --- |
| 首版范围 | 营销材料发布前的表达、产品事实、风险披露与人群适配检查 |
| 人工工序 | 查表达、产品事实、风险提示、适用人群和版本 |
| 输入 | 宣传材料、产品文件、风险提示、人群、渠道与版本 |
| 并行流程 | 明确表达、产品事实、风险披露、渠道适配 |
| 输出 | 问题位置、缺失信息、等级、修改建议与人工结论 |
| 异常 | 材料冲突、人群不清、版本失效、结论冲突 |
| 人工承接 | 产品与合规人员完成最终确认 |
| 企业连接 | 产品中心、合规、客户分层、渠道与版本管理 |

关键结论：高风险场景可以由 AI 辅助定位与比对，但最终责任必须明确到人。

## 8. 五个案例的横向比较（170—173分钟）

| 场景 | 被判断对象 | 关键材料 | 最终人工角色 | 企业连接的价值 |
| --- | --- | --- | --- | --- |
| 合同 | 条款 | 模板、交易背景 | 法务 | 判断实际履约风险 |
| 客服 | 多轮会话 | 政策、订单状态 | 质检主管 | 形成申诉与整改闭环 |
| 招聘 | 岗位文案 | 编制、薪酬 | HR负责人 | 确认岗位与承诺真实 |
| 报销 | 票据、报销单 | 预算、OA、合同 | 财务 | 完成组合判断 |
| 金融营销 | 宣传材料 | 产品、风险、人群 | 产品与合规 | 管理版本与发布范围 |

## 9. 本节收束（173—175分钟）

迁移不是把“营销文案”四个字换成“合同”或“招聘”。真正可迁移的是：先定义业务决定，再还原人工工序，然后重新确定输入、输出、流程、异常、责任角色和企业连接。

---

# 全课收束（175—180分钟）

## 三道判断门

```text
第一道：异常门
正常路径被打断后，产品能否安全停下、恢复和交接？

第二道：测试门
测试结果是否支持进入试点，还是应该补齐、收缩或暂停？

第三道：迁移门
换一个业务以后，能否重新理解对象、材料、角色与边界？
```

## 教师结束语

AI 可以快速生成页面、流程和一段看起来合理的判断。但产品经理的专业性，不是让方案显得完整，而是能在异常里做取舍、能用测试结果否定或收缩自己的方案，也能进入一个新业务后重新完成分析。

今天这三个部分共同回答的是同一个问题：一个 AI 产品方案，怎样从“看起来能用”走向“可以被真实业务采用”。

## 本课建议课后作业

从客服、招聘、报销或金融营销中任选一个场景，提交一页方案：

1. 一句话业务问题；
2. 第一版范围与不做范围；
3. 一条人工工作流；
4. 输入、输出和至少两条异常分支；
5. 三项测试指标；
6. 测试结果分别在什么情况下进入试点、收缩范围或暂停。

---

## 教师备课提示

- 第四节重点不是罗列异常，而是讲清“为什么做这个取舍”；
- 第五节不要只讲准确率、召回率，要把工程稳定性、人工总投入和高风险表现放在一起；
- 第七节的四个新场景均为正式案例，按完整产品逻辑讲解，不改成分组练习；
- 合同案例只作为迁移母案例，不把课程讲成法律课；
- 金融营销案例只讨论产品设计，不给出具体专业结论；
- 如果时间不足，压缩案例细节，但保留五场景横向比较与三道判断门。
