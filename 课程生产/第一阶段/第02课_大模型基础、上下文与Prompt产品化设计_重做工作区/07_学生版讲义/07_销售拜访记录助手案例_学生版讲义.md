# 模块07：案例实战——销售拜访记录助手

> 课堂时间：84—108分钟；充分讲评时约27—29分钟  
> 本模块任务：用完整材料测试已有的V0.2和V0.3，并根据Bad Case做最小修改  
> 课堂产出：《销售拜访记录助手Prompt产品化设计单》课堂版  
> 案例声明：公司、人物、产品、数据和对话均为教学虚构

## 一、这个案例为什么再次出现

第0课和第2课使用同一个案例，但训练目标不同：

| 第0课 | 第2课 |
|---|---|
| 判断场景是否值得做 | 假设已经决定做，怎样让模型完成任务 |
| 分析AI可以承担哪些环节 | 定义模型需要的上下文和规则 |
| 讨论人与AI怎样分工 | 区分信息供给方式与结果风险处理 |
| 形成初步产品方案 | 测试Prompt并完成产品化设计 |

本模块不重新讨论销售拜访助手有没有价值，也不从头写一遍六要素。

## 二、本模块要完成的完整链路

已有产出：

- V0.1：目标输出、验收标准和上下文；
- V0.2：结构化Prompt关键骨架；
- V0.3：信息供给方式、风险处理和交互。

本模块增加：

模糊任务  
→ 观察第一轮结果  
→ 对照证据定位Bad Case  
→ 找到Prompt缺口  
→ 最多修改3处  
→ 再次验收  
→ 修正产品流程

重点不是一次写出完美Prompt，而是学习怎样根据结果进行针对性迭代。

## 四、第一轮：模糊结果找错

第一轮基线指令：

> 帮我整理一下这次销售拜访。

课堂材料中的第一轮结果是教学构造的错误样例，用于建立统一找错基线，不代表特定模型的真实表现。这句话即使配合完整背景和转写，仍然没有明确：

- 目标字段；
- 事实和推测规则；
- 缺失信息处理；
- 证据要求；
- 行动项结构；
- 结果怎样进入CRM。

### 找错不能只靠感觉

每条问题使用以下结构：

1. 结果写了什么；
2. 具体问题是什么；
3. 原文证据是什么；
4. 违反了哪条验收标准。

不合格的表达：

- 太笼统；
- 不准确；
- 不够专业；
- 感觉有问题。

合格的表达示例：

> 结果把一项尚未确认的信息写成确定计划；原文使用的是“可能”，违反了“区分已确认和待确认”的验收标准。

## 五、为什么语言通顺仍然不能用

业务结果需要同时满足：

- 事实正确；
- 确定性程度正确；
- 字段完整；
- 能回到原文；
- 能支持下一步动作；
- 高风险内容可确认。

一段文字可能语言顺畅、逻辑完整，却发生：

- 把可能写成承诺；
- 把条件估计写成正式工期；
- 把提问写成客户事实；
- 遗漏负责人和日期；
- 忽略缺失信息；
- 无法进入CRM。

所以：

> AI产品验收不能只看“读起来像不像一份好答案”。

## 六、第二轮：根据Bad Case做最小修改

### 1. 先定位Prompt的哪一部分有问题

| Bad Case表现 | 优先检查 |
|---|---|
| 不知道要完成什么 | 任务目标 |
| 缺少完成任务的事实 | 输入和上下文 |
| 把推测写成事实 | 规则与约束 |
| 结果无法进入CRM | 输出字段和验收标准 |
| 结论无法核对 | 证据要求 |

### 2. 每组最多修改3处

限制修改数量是为了训练：

- 识别最重要问题；
- 建立问题与修改的对应；
- 避免每次推翻重写；
- 观察一项修改带来的影响。

### 3. 不把案例答案写死

不建议：

> 必须输出5家试点。

这只能解决当前材料。

更通用：

> 区分已确认、讨论中和待确认；可能方案不能改写为确定事实。

下一个客户即使讨论的不是5家和8家，这条规则仍然可以使用。

## 七、第二轮怎样验收

第二轮必须使用课堂现场生成或老师发放的完整输出，并记录模型名称、生成日期和完整Prompt；没有第二轮输出时，只能完成“预期验收项”，不能勾选已经通过。

请检查：

- 是否区分已确认、讨论中和待确认；
- 是否把试点写成采购承诺；
- 条件估计是否变成正式工期；
- 希望尽快是否变成确定日期；
- 行动项是否有人、事、时间和状态；
- 关键结论是否有证据；
- 缺失信息是否单独列出。

一次改善只表示：

> 本次测试在这些检查项上变得更好。

不能因此证明：

- 所有新拜访都会准确；
- 转写一定正确；
- 模型不会出现新错误；
- 可以取消人工确认；
- 已经完成正式评测。

## 八、第三轮：检查V0.3产品化设计

再次打开V0.3，回答：

### 1. 系统已经准备什么

可能包括：

- 客户资料；
- 商机阶段；
- 拜访时间；
- 参会人；
- 拜访转写；
- CRM字段和业务规则。

### 2. 用户仍需做什么

可能包括：

- 选择本次重点输出；
- 填写特殊备注；
- 修正自动带入的数据；
- 确认关键事实；
- 决定是否写入CRM。

### 3. AI生成后怎样检查

结果不应只是一段纯文本，可以包括：

- 按CRM字段分块；
- 已确认、讨论中和待确认状态；
- 关键结论对应证据；
- 日期、金额、责任人和承诺高亮；
- 编辑、删除和返回原文；
- 用户确认后才能写入。

## 九、产品流程三句话

请在课堂设计单中完成：

1. 用户进入页面后，系统已经准备：________；
2. 用户仍需填写、选择或确认：________；
3. AI生成后，必须确认才能写入CRM的是：________。

## 十、案例讲评的五项标准

1. 目标输出是否可以验收；
2. 上下文是否足够且没有无差别堆料；
3. Prompt规则是否对应真实业务风险；
4. 产品固定、用户提供、系统获取是否合理，风险处理是否单独设计；
5. 用户是否仍被迫理解和填写大量Prompt。

## 十一、常见误区

### 重新讨论场景值不值得做

本模块假设项目已经决定验证，只分析怎样完成任务。

### 看到错误就重写完整Prompt

先定位问题，做最小修改，再观察结果。

### 为了修正案例把答案写死

应总结通用规则，不把具体数字写成固定答案。

### 结构化结果正确，就取消人工确认

一次正确不代表永久正确，高风险字段仍需确认。

### 开始设计完整CRM

本课只设计AI生成前的必要输入，以及生成后的检查和确认。

## 十二、先记住

1. 语言通顺不等于业务可用；
2. Bad Case必须有原文证据和验收标准；
3. Prompt优先做针对性最小修改；
4. 案例答案不能写死进通用Prompt；
5. 好Prompt仍需要产品交互和人工确认；
6. 一次结果改善不等于系统已经稳定。
