# 从完整审核链路到判断型 AI 产品迁移

课程时长：180分钟（含两次休息，每次10分钟）  
贯穿案例：净小伴P1营销内容智能审核  
课程定位：在第一次课已经完成业务分析、审核体系与整体方案的基础上，继续把方案走成一条真实可运行的链路，并通过异常场景检验产品设计，最后迁移到合同审核及其他判断型业务。

本课只保留三条主线：

1. 关键流程与页面怎样真正连起来；
2. 真实异常中的产品取舍；
3. 从合同审核到其他判断型 AI 产品。

本课不重复讲规则、模型、知识库等基础概念，也不重新讨论第一次课已经确定的总体方案。重点是让学员回答三个更接近落地的问题：系统怎样真正运行，遇到异常怎样继续工作，离开营销审核后这套方法还能不能使用。

## 一、整堂课的目标

完成本课后，学员应当能够：

1. 沿着一条内容走完自检、正式审核、修改复核和历史巡检；
2. 区分内容版本、检查运行、正式审核任务和巡检任务；
3. 解释页面上的每个关键动作在后台改变了什么状态；
4. 为资料缺失、调用失败、旧结果迟到、结论冲突和人员争议设计明确处理方式；
5. 判断异常发生后是继续、重试、降级、转人工还是终止；
6. 从合同审核案例中提取判断型 AI 产品的共同设计方法；
7. 把方法迁移到客服质检、招聘审核、报销审核或金融营销材料审核。

# 开场：今天不再讨论“要不要做”，而是检验“能不能跑”（00—10分钟）

## 教师开场

第一次课结束时，我们已经有了一个看起来完整的营销内容审核方案：作者可以自检，审核员可以正式审核，业务条件变化以后还可以发起历史巡检。

但一张流程图完整，不等于产品已经可以运行。真正进入实施以后，问题会变成：

- 自检通过以后，作者又改了文案，旧结果还能不能用？
- 一次检查有三个分支，两个完成、一个超时，页面显示什么？
- 规则说有问题，模型认为没有问题，谁来决定？
- 机器提出问题，作者不认同，审核员凭什么处理？
- 活动条件变了，系统找到旧内容以后，谁负责真正修改线上内容？

今天我们就沿着这些问题继续推进。

## 开场提问

> 一个 AI 审核系统输出了“通过”，这两个字至少要依赖哪些条件？

让学员自由回答1—2分钟。教师不急着纠正，先把回答写在白板上。

可能出现的答案：

- 当前文案没有变化；
- 使用的业务资料仍然有效；
- 审核要求没有更新；
- 所有必要检查已经完成；
- 正式审核人员拥有决定权限；
- 结果不是一次超时后的默认值。

## 教师收束

“通过”不是模型生成的一个词，而是一个有条件、有版本、有责任人的业务状态。

板书：

```text
一个可用结论
= 对应明确对象
+ 使用有效资料
+ 完成必要检查
+ 处在正确版本
+ 由正确角色处理
```

# 第一节：关键流程与页面怎样真正连起来（10—55分钟）

## 本节任务

本节回答：原型中的一次点击，怎样对应后台的任务、状态、版本和下一步责任？

学员最终应能画出：

```text
内容版本
→ 检查运行
→ 正式审核任务
→ 修改与复核
→ 条件变化后的历史巡检
```

## 1. 从“几张页面”切换到“一条业务链”（10—15分钟）

### 教师讲述

很多产品方案的问题，不是页面画得少，而是页面之间没有真实关系。

例如，我们可以分别画出：

- 内容编辑页；
- 自检结果页；
- 正式审核详情页；
- 历史巡检页。

但如果说不清作者在编辑页修改以后，审核详情页原来的结果是否继续有效；说不清审核员退回以后，作者提交的是原任务还是新任务；说不清巡检发现问题以后谁去改线上内容，那么这些页面只是静态界面，不是一套产品。

### 核心判断

产品链路不是“页面A跳到页面B”，而是：

```text
谁对哪个业务对象
执行了什么动作
写入了什么结果
改变了什么状态
下一步由谁继续处理
```

### 课堂小问

> 作者点击“重新检查”，最少需要重新确认哪些内容？

教师参考：当前正文、商品和活动上下文、资料版本、审核点配置、运行时间、输出状态。不是只调用一次模型。

## 2. 先认识链路中的四类对象（15—22分钟）

### 教师讲述

要把页面真正连起来，先不要急着讨论按钮。先区分系统中四类不同对象。

| 对象 | 解决的问题 | 示例 |
| --- | --- | --- |
| 内容版本 | 这次检查的到底是哪一版正文 | P1推广文案V1、V2 |
| 检查运行 | 系统何时、按什么配置检查了哪一版 | Run-101绑定V1、资料M3、配置C5 |
| 正式审核任务 | 谁对哪个提交版本作业务决定 | Review-021等待审核员处理 |
| 巡检任务 | 业务条件变化后，哪些在用内容需要重新核对 | Inspect-008由活动负责人发起 |

教师强调：这四个对象不能合成一个“审核状态”。

一篇文案可以同时出现：

- 当前编辑版本是V3；
- 最近一次完整检查针对V2；
- 正式审核通过的是V1；
- 巡检任务发现V1对应的线上内容需要修改。

这些状态同时存在并不矛盾。真正危险的是产品只显示一个绿色“已通过”，让用户误以为所有版本、所有场景都已经安全。

### 板书

```text
内容状态 ≠ 检查状态 ≠ 正式审核状态 ≠ 巡检处理状态
```

## 3. 课堂演示一：从问题稿到自检修改（22—30分钟）

### 演示目标

让学员看到一次自检不是得到一个总分，而是生成一组绑定当前版本、资料和配置的检查结果。

### 演示步骤

1. 进入“内容与自检”；
2. 载入问题稿；
3. 确认关联商品、活动和适用日期；
4. 发起检查；
5. 展开三项问题，查看原句、问题类型、使用资料和建议动作；
6. 载入“只补会员资格”稿，再次检查；
7. 观察价格检查仍然提示两类券及使用条件没有完整说明；
8. 载入“条件完整稿”，完成自检。

### 演示时教师重点说什么

第一，自检服务的是作者修改，不是替代正式审核。作者看到的结果要能回答：哪句话、哪里有问题、参考什么资料、下一步怎样改。

第二，每次检查都要绑定快照。如果作者修改了正文，即使只改一个数字，也不能把旧结果直接盖到新版本上。

第三，“未发现问题”只代表已经运行的检查项没有发现问题，不代表整篇内容在所有要求下自动通过。

### 页面与后台对应

| 页面动作 | 后台应发生的事情 |
| --- | --- |
| 保存正文 | 形成或更新内容版本 |
| 选择商品与活动 | 写入本次业务上下文 |
| 发起检查 | 固定正文、资料、配置等本次运行快照 |
| 展开问题 | 读取问题定位、问题类型和参考资料 |
| 修改后重检 | 生成新的内容版本和新的检查运行 |

## 4. 课堂演示二：正式提交、人工复核与再修改（30—38分钟）

### 演示步骤

1. 使用条件完整稿完成一次自检；
2. 点击正式提交；
3. 切换到审核员角色；
4. 在正式审核页查看提交正文、检查结果和所用资料；
5. 对问题执行“确认”“不成立”“人工补核”等动作；
6. 记录正式审核决定与处理理由；
7. 返回作者角色，修改正文；
8. 观察旧的正式结果不能自动对应新版本。

### 教师讲述

正式审核和自检最大的区别，不是模型换了，而是业务责任发生了变化。

自检结果帮助作者发现问题；正式审核任务需要有权限的人对提交快照作出业务决定。即使二者复用同一套检查能力，也不能把自检完成直接写成正式通过。

### 正式审核最少要保留什么

- 提交的内容版本；
- 提交时使用的商品和活动上下文；
- 相关资料与配置版本；
- 各检查分支是否完成；
- 机器输出与程序校验结果；
- 审核员的处理动作与理由；
- 退回、修改和复核之间的关联。

### 课堂提问

> 审核员在V1上点了通过，作者随后把“新会员专享”删掉。正式状态应该怎样显示？

教师参考：V1的通过记录继续保留；V2不能继承V1的正式通过；页面应明确当前编辑版本与已通过版本不同，并要求对V2重新检查和提交。

## 5. 课堂演示三：从历史巡检走到实际更新（38—45分钟）

### 场景

活动负责人确认：原来承诺的前200名赠品名额已经用完。历史上已经发布的内容里，仍有一部分在使用旧表达。

### 演示步骤

1. 进入课堂控制，载入“名额用完后的巡检”；
2. 切换内容负责人角色；
3. 根据活动、使用状态和内容关联选择巡检范围；
4. 发起巡检；
5. 比较C01、C03、C05、C06四条内容；
6. 认领需要处理的C01；
7. 创建修订稿，交作者修改、自检和提交；
8. 审核员完成正式复核；
9. 返回巡检页，登记实际使用位置与上线版本；
10. 确认问题在真实渠道完成更新后再关闭。

### 教师强调

巡检发现问题，不等于问题已经解决。

系统内部创建了修订稿，也不等于外部渠道已经更新。巡检闭环至少要区分：

```text
发现问题
→ 认领
→ 创建修订稿
→ 修改与复核
→ 更新实际使用位置
→ 核验生效
→ 关闭
```

如果缺少“实际更新”和“核验生效”，产品只完成了内部任务管理，没有完成业务闭环。

## 6. 把页面动作整理成一张状态表（45—49分钟）

| 业务动作 | 主要对象 | 状态变化 | 下一责任人 |
| --- | --- | --- | --- |
| 作者保存新稿 | 内容版本 | 草稿V1→V2 | 作者 |
| 作者发起自检 | 检查运行 | 待运行→运行中→完成/未完成 | 作者或系统维护人员 |
| 作者正式提交 | 正式审核任务 | 未提交→待审核 | 审核员 |
| 审核员退回 | 正式审核任务 | 待审核→待修改 | 作者 |
| 作者修改重提 | 新内容版本与审核任务 | V1任务保留，V2建立新关联 | 审核员 |
| 负责人发起巡检 | 巡检批次 | 待选择→运行中→待处理 | 内容负责人 |
| 内容负责人认领 | 巡检问题 | 待认领→处理中 | 认领人 |
| 渠道完成更新 | 使用记录 | 待更新→待核验→已完成 | 内容负责人 |

## 7. 小组练习：旧结果迟到，系统怎么处理（49—54分钟）

### 题目

作者对V1发起检查。运行过程中，作者保存了V2并删掉一句话。此时V1的检查结果才返回，并提示被删掉的那句话存在问题。

每组用3分钟回答：

1. 结果是否保存；
2. 页面是否展示；
3. 能否用于V2正式提交；
4. 用户需要看到什么提示；
5. 是否自动触发V2重检。

### 教师参考

- V1结果应保存，便于追溯本次运行；
- 可以展示，但要明确标记“对应旧版本”；
- 不能把V1结果用作V2的正式结论；
- 当前编辑页应提示正文已变化，需要重新检查；
- 是否自动重检取决于产品策略，但不能悄悄把旧结果覆盖到新版本；
- 如果自动重检，要防止连续编辑导致大量无效调用，可采用防抖、取消旧任务或显式再次发起。

## 8. 本节收束（54—55分钟）

### 教师总结

这一节真正建立的不是四张页面，而是四类对象之间的关系。

板书：

```text
页面是入口
任务是过程
版本是边界
状态是协作语言
责任人让流程真正闭环
```

# 第二节：真实异常中的产品取舍（65—110分钟）

## 本节任务

本节回答：资料不全、执行失败、版本变化、结论冲突和人员争议发生以后，产品怎样继续工作？

本节不要求学员背异常清单，而是掌握一套处理模板。

## 1. 异常不是一个报错弹窗（65—70分钟）

### 教师讲述

理想流程只需要回答“正常情况下怎样运行”。真实产品还要回答：

- 系统现在完成了多少；
- 哪些结论还能使用；
- 哪些结论不能继续使用；
- 当前用户可以做什么；
- 谁负责补齐或确认；
- 恢复以后从哪里继续；
- 原来的过程是否保留。

因此，一个完整的异常设计至少包含八项：

| 项目 | 要回答的问题 |
| --- | --- |
| 触发条件 | 什么情况被判定为异常 |
| 影响范围 | 影响一个检查点、一个分支还是整次任务 |
| 当前状态 | 系统已经完成什么、还缺什么 |
| 页面表达 | 用户能否看懂发生了什么 |
| 可执行动作 | 重试、补资料、转人工、继续还是终止 |
| 处理角色 | 谁拥有下一步权限 |
| 恢复方式 | 条件补齐以后怎样继续 |
| 过程留存 | 原输入、输出、时间和人工动作是否可追溯 |

板书：

```text
异常设计
≠ 告诉用户“失败了”
= 告诉用户“哪里没完成、还能做什么、由谁继续”
```

## 2. 异常一：业务资料缺失（70—77分钟）

### 场景

文案写了“下单就送滤芯”，但系统没有找到本次活动的赠品资格、数量和有效期资料。

### 先让学员判断

> 系统应该判定文案违规，还是判定文案没有问题？

正确方向：两者都不合适。系统当前只能说明缺少完成判断所需的资料。

### 产品处理

| 项目 | 设计 |
| --- | --- |
| 当前结论 | 该检查点未完成，不输出确定通过或违规 |
| 其他检查 | 与赠品资料无关的分支可以继续 |
| 页面提示 | 明确缺少哪类资料、影响哪个检查点 |
| 用户动作 | 补充资料、选择正确活动或交业务负责人确认 |
| 正式审核 | 审核员可查看未完成原因，不把未完成伪装为通过 |
| 恢复方式 | 补齐资料后重新运行受影响分支，形成新记录 |

### 教师强调

“资料缺失”和“内容错误”必须分开。前者说明系统暂时无法完成判断；后者说明已有足够依据指出内容与要求不一致。

## 3. 异常二：模型调用超时或局部失败（77—84分钟）

### 场景

一次检查包含三个分支：功能对象检查已完成，价格条件检查已完成，赠品语义检查超时。

### 常见错误设计

- 整个页面只显示“系统异常”；
- 超时分支自动显示“未发现问题”；
- 用户连续点击，产生多次重复任务；
- 重试以后覆盖第一次运行，无法确认发生过什么。

### 产品处理

```text
整次运行：部分完成
├─ 功能对象：完成
├─ 价格条件：完成
└─ 赠品语义：超时，等待重试或人工补核
```

教师说明：局部失败时是否允许业务继续，要看缺失分支是不是本场景的必要检查。不能用统一的“成功率超过80%就放行”代替业务判断。

### 课堂追问

> 如果赠品检查是当前活动的必检项，正式审核能不能点通过？

教师参考：系统不应自动给出完整通过；可允许有权限的审核员在完成明确的人工补核并记录理由后继续，或者要求重试成功后再作决定。具体选择由业务责任和风险等级决定。

## 4. 异常三：旧版本结果迟到（84—90分钟）

### 教师演示

在课堂控制中选择“旧版本结果迟到”：

1. 用V1发起检查；
2. 检查运行中保存V2；
3. 等待V1结果返回；
4. 观察结果仍然绑定V1；
5. 检查V2页面是否明确提示需要重新运行。

### 关键原则

- 迟到结果不是垃圾数据，应保留到原运行；
- 迟到结果不能自动覆盖当前版本；
- 当前页面必须展示版本关系；
- 正式提交时要检查提交版本是否拥有有效的完整运行；
- 如果资料或配置也发生变化，同样按新快照重新运行。

## 5. 异常四：规则与模型结论冲突（90—97分钟）

### 场景

文案写着：“最后看一下会员券，价格会更划算。”

关键词规则因为命中“最后”把它识别为“绝对化表达”；模型结合上下文认为这里是顺序词，不是“最优、最高、最后机会”等营销承诺。

另一个场景中，程序确认1799这个数字计算成立，但模型发现文案遗漏了新会员资格和两类券的使用条件。

### 教师讲述

规则与模型不是两位投票者。它们可能在回答不同问题：

- 规则擅长确定表达、字段和值的核对；
- 模型擅长上下文、对象关系和语义条件；
- 程序可以确认数字计算；
- 业务资料决定可接受范围；
- 人工处理无法自动确定的争议。

所以冲突不能简单采用“少数服从多数”，也不能只比较两个分数。

### 冲突处理表

| 冲突类型 | 建议动作 |
| --- | --- |
| 关键词命中但上下文否定 | 显示规则命中与上下文解释，进入语义复核 |
| 数值成立但适用条件缺失 | 保留数值核算结果，同时提出条件缺失问题 |
| 业务资料之间互相矛盾 | 停止确定判断，交资料负责人确认有效版本 |
| 模型定位的原句不存在 | 判定本次输出校验失败，不进入业务结果 |
| 多个分支报告同一问题 | 按原句位置与问题类型合并，保留各分支记录 |

## 6. 异常五：角色争议、权限不足与无人承接（97—103分钟）

### 场景A：作者不同意机器结论

作者可以提交异议，但不能直接把正式审核任务改成通过。异议至少要包含：不同意哪个问题、理由是什么、是否补充了新资料。

### 场景B：审核员发现资料可能过期

审核员可以标记该检查未完成，并转给资料负责人；不能自行修改受控资料后让原任务静默通过。

### 场景C：巡检发现问题但无人处理

系统必须显示待认领、处理时限和升级对象。如果产品只批量找到问题，却没有责任人、提醒和升级机制，问题只会从线上转移到任务列表。

### 角色表

| 角色 | 可以做什么 | 不应直接做什么 |
| --- | --- | --- |
| 作者 | 修改正文、补充上下文、提出异议 | 修改正式审核结论 |
| 审核员 | 确认、退回、人工补核、记录理由 | 把旧版本通过状态复制给新版本 |
| 资料负责人 | 更新受控资料、确认有效期 | 静默改写历史运行所用资料 |
| 内容负责人 | 发起巡检、分配问题、核验实际更新 | 在没有复核时关闭高风险问题 |
| 系统维护人员 | 查看调用与校验失败、恢复服务 | 代替业务人员作内容决定 |

## 7. 异常处理不是越自动越好（103—105分钟）

教师给出五种常见动作：

```text
继续：未完成项不影响当前业务决定
重试：输入有效，只是执行暂时失败
降级：切换到能力较弱但边界明确的处理方式
转人工：需要业务判断、权限或补充信息
终止：输入不合法或无法安全继续
```

让学员注意：降级不是把失败结果改成成功，而是明确换用另一种已知能力，并让用户知道当前能力边界。

## 8. 角色练习：同一个争议，三类用户分别需要什么（105—109分钟）

### 题目

系统提示“1799元优惠条件不完整”。作者认为大家都知道需要领券；审核员认为文案可能误导；资料负责人发现活动说明刚刚更新过，但系统仍使用旧版资料。

三组分别扮演作者、审核员、资料负责人，用2分钟填写：

1. 我需要看到什么信息；
2. 我能执行什么动作；
3. 我把任务交给谁；
4. 什么条件满足后才能继续。

### 教师点评

作者需要定位原句和缺失条件；审核员需要当前提交快照、资料版本和处理权限；资料负责人需要确认旧版与新版资料的生效时间。三类角色看的是同一问题，但他们需要的信息和动作不同。

## 9. 本节收束（109—110分钟）

板书：

```text
正常流程决定产品能不能演示
异常流程决定产品能不能交给真实业务
```

# 第三节：从合同审核到其他判断型 AI 产品（120—170分钟）

## 本节任务

本节先用法律合同审核还原一套完整的企业内部 AI 项目方法，再现场迁移到客服会话质检，最后让学员把方法迁移到招聘信息、发票报销或金融营销场景。

本节讲产品设计与工作流拆解，不提供法律、财务或金融专业结论。案例、角色和业务数据均用于课堂推演。

## 1. 为什么在营销审核之后讲合同审核（120—124分钟）

### 教师讲述

刚才我们已经证明，一项审核产品不能只靠一句Prompt。它需要明确业务对象、输入资料、任务拆分、版本关系、异常分支和人工责任。

现在要回答一个更重要的问题：如果离开营销审核，这套方法还能不能使用？

如果只是把“营销文案”换成“招聘文案”，把页面标题改一下，这不叫迁移。真正的迁移，是进入另一个业务以后，仍然能够重新完成业务分析、任务拆解、能力分工、异常设计和运行判断。

我们先看知乎第5课中的合同审核案例，因为它比较完整地展示了一项企业内部 AI 产品怎样从一个小问题开始，逐步变成可以运行的工作流。

### 课堂提问

> 如果让你做一个“AI法务”，你会从哪里开始？

学员可能会回答：建立法律知识库、做合同审核、做法律咨询、查询案例或生成合同。

### 教师收束

这些方向都可能成立，但范围太大。产品真正开始时，要先选择一个足够具体、能够验证的任务。

板书：

```text
不是先问 AI 能做什么
而是先问企业中哪一段工作值得被重新设计
```

## 2. 合同审核母案例（124—139分钟）

### 2.1 先收窄项目边界

很多企业都需要处理合同，但不同企业的法务能力差异很大。小公司不一定愿意承担完整法务团队和长期外部顾问的成本；已经有法务的公司，也可能面对合同数量多、基础审核重复、外部信息查询容易遗漏等问题。

第一版边界可以写成：

> 面向企业内部业务人员和法务人员，为常规业务合同提供初步检查、问题定位和修改建议；复杂争议、重大风险与最终决定仍由专业人员负责。

这里已经完成第一个关键判断：不做诉讼，不做完整法律咨询，也不把系统包装成自动作出最终法律决定的工具。

### 2.2 先理解人工怎样审核合同

| 人工审核对象 | 要回答的问题 |
| --- | --- |
| 合同主体 | 和谁签约，主体信息是否完整，对方公司是否存在异常 |
| 合同条款 | 权利义务是否清楚，付款、交付、验收和违约条款是否合理 |
| 法律引用 | 合同引用的规范是否仍然适用，引用是否准确 |
| 履约方式 | 交付时间、付款条件、验收标准和责任是否能够实际执行 |
| 周边风险 | 对方历史履约、企业异常、内部关联和其他业务风险 |

教师强调：这一阶段还没有讨论模型、知识库或者工作流节点。先把人的工作说清楚。

### 课堂提问

> 如果只把合同全文交给模型，并要求“全面审核”，最容易出现什么问题？

教师参考：输出标准不稳定；不同类型问题混在一起；遗漏外部公司信息；不知道使用哪个版本的内部要求；结果看起来专业，但很难确认是否覆盖了需要检查的内容。

### 2.3 从最终输出反推输入

合同审核最终不能只输出“有风险”或者一个总分。业务人员和法务需要看到：

- 问题所在条款；
- 问题类型；
- 为什么需要关注；
- 可能产生的业务影响；
- 建议怎样修改；
- 哪些内容仍需人工确认。

为了得到这些输出，输入也不能只有合同文件。

| 输入 | 作用 |
| --- | --- |
| 合同正文 | 确定本次审核对象 |
| 本次审核重点 | 告诉系统本次特别关注付款、交付、知识产权或其他部分 |
| 企业合同规则 | 提供公司内部可接受的条款范围与模板要求 |
| 对方企业信息 | 辅助判断签约主体和外部风险 |
| 业务上下文 | 说明交易关系、合作历史、时间要求和谈判空间 |

### 2.4 先验证基础能力，再搭完整系统

选择一份已经脱敏的合同，用能力较强的模型完成一轮快速测试，再请法务人员评价输出。

重点不是看文字是否流畅，而是看：

- 能否定位到真实条款；
- 能否发现付款、交付、验收等明显矛盾；
- 修改建议是否可以理解；
- 有没有把正常商业安排一律判成风险；
- 有没有编造不存在的内容；
- 对不确定问题是否知道交给人工。

合同案例中，一个有价值的评价是：模型像一个认真、基础能力不错，但缺少实际商业经验的法务实习生。

这帮助我们确定产品位置：模型可以先完成覆盖面较广的初步检查，但不能直接替代熟悉公司业务和谈判背景的法务负责人。

### 2.5 把人工分工拆成并行流程

```text
上传合同与本次审核要求
          ↓
读取文件并确认是可处理的合同
          ↓
 ┌────────┼────────┐
 │        │        │
常规条款  法律引用  签约主体与企业风险
审核      检查      查询
 │        │        │
 └────────┼────────┘
          ↓
问题合并、去重与分级
          ↓
形成审核意见和修改建议
          ↓
法务人员确认
```

并行拆分不是为了让工作流看起来复杂，而是为了让每条路线目标明确、输入明确、结果可以单独检查。

### 2.6 补齐边界条件

| 边界情况 | 产品动作 |
| --- | --- |
| 上传的不是合同 | 终止审核，提示重新上传正确文件 |
| 合同无法读取 | 标记解析失败，保留原文件并给出下一步 |
| 缺少签约主体 | 形成明确缺项，不继续猜测主体身份 |
| 企业名称查询不到 | 显示“暂未查询到”，不直接判断对方为虚假企业 |
| 外部接口失败 | 保留其他已完成结果，该分支进入重试或人工查询 |
| 多路结果重复 | 按条款位置和问题类型合并，保留各分支原始记录 |
| 结果发生冲突 | 标记冲突并交给法务确认 |

### 2.7 从通用能力升级为企业能力

如果产品只检查通用法律和条款，它很难超过市场上的专业工具。企业内部项目的特殊价值来自与本公司业务连接。

例如把合同交付条款连接到：

- ERP订单；
- 库存和生产排期；
- 资金计划；
- 历史履约记录；
- 供应商名录；
- 内部黑名单和关联关系。

一份合同要求30天交付，单看条款可能没有明显问题。但如果生产线已经接近满负荷，原材料也无法按时到货，这项条款就可能带来实际履约风险。

教师收束：

> 企业内部 AI 产品不一定要比专业垂直模型更懂法律，而要比通用工具更懂这家公司的业务。

## 3. 提取十一项迁移框架（139—144分钟）

| 步骤 | 要回答的问题 |
| --- | --- |
| 1 业务问题 | 企业为什么现在需要解决它 |
| 2 小场景 | 从大业务中先选择哪一段 |
| 3 人工工序 | 人原来按什么顺序完成 |
| 4 最终输出 | 用户最终需要看见什么并执行什么动作 |
| 5 输入来源 | 完成判断需要哪些文件、数据和上下文 |
| 6 快速验证 | 当前模型是否具备基础能力 |
| 7 并行拆分 | 哪些工作适合分开执行 |
| 8 边界分支 | 缺项、失败、冲突和版本变化怎样处理 |
| 9 结果合并 | 多路结果怎样去重、分级并交给人 |
| 10 企业连接 | 接入哪些内部系统才能形成特殊价值 |
| 11 运行验证 | 用什么结果决定继续、修改或缩小范围 |

板书：

```text
业务问题
→ 人工工序
→ 输出与输入
→ 能力验证
→ 并行流程
→ 异常分支
→ 企业系统
→ 运行验证
```

## 4. 现场迁移到客服会话质检（144—154分钟）

### 4.1 业务问题与首版范围

某电商平台每天产生大量售后对话，主管只能抽查少量会话。部分客服存在错误承诺、没有核对订单状态、前后口径不一致或服务态度不当等问题。

第一版不做完整客服管理系统，只选择：

> 售后退款会话的智能质检。

### 4.2 课堂材料

> 客户：退款什么时候能到账？  
> 客服：肯定今天到账，您放心。  
> 客户：昨天另一个客服说需要三个工作日。  
> 客服：反正系统已经处理了，具体您自己等着吧。

课堂提问：如果你是质检主管，会检查哪些内容？

教师参考：是否完成身份或订单核验；是否错误承诺到账时间；是否查询当前订单状态；是否解释口径差异；是否存在推诿；客户情绪是否升级。

### 4.3 按合同案例完成映射

| 合同审核 | 客服质检 |
| --- | --- |
| 合同文件 | 对话文本或通话录音 |
| 法务人员 | 质检主管 |
| 合同条款 | 客服话术与处理动作 |
| 法律引用 | 服务制度和标准口径 |
| 企业信息 | 订单、退款和客户状态 |
| 审核意见 | 质检问题、等级和改进建议 |
| 法务确认 | 主管复核与客服申诉 |

需要的输入包括：

- 会话内容和说话人角色；
- 订单与退款状态；
- 当前服务政策；
- 本次质检规则；
- 客服所属团队和必要的历史记录。

并行流程：

```text
导入会话或录音
       ↓
转写、分句与角色区分
       ↓
┌────────┼────────┐
│        │        │
流程规则  多轮语义  订单与政策
检查      判断      核对
│        │        │
└────────┼────────┘
       ↓
问题合并与风险分级
       ↓
主管复核、客服确认或申诉
       ↓
进入培训与规则改进
```

### 4.4 客服场景的边界条件

| 边界情况 | 产品动作 |
| --- | --- |
| 录音无法转写 | 标记转写失败，不能继续假装完成质检 |
| 客户与客服角色混淆 | 暂停对应判断，允许人工修正角色 |
| 订单接口没有返回 | 保留话术检查结果，业务事实检查待完成 |
| 否定句被关键词误报 | 引入上下文确认并进入测试样本 |
| 主管与机器结论不同 | 保留双方结论及调整理由 |
| 客服提出申诉 | 进入复核流程，不直接覆盖原始记录 |

### 4.5 企业连接

通用模型能够判断语气和语义，但真正的企业能力来自CRM、订单系统、工单系统、客服知识库、投诉记录、培训和质检系统。

合同场景连接ERP、财务和供应商数据；客服场景连接订单、工单和服务政策。变化的是业务对象，不变的是产品方法。

## 5. 小组迁移练习（154—166分钟）

### 练习要求

全班分成三组，每组选择一个场景。6分钟设计，6分钟快速分享。每组只回答八个问题：

```text
1 业务问题是什么
2 第一版选择哪个小场景
3 人工原来怎样完成
4 最终输出是什么
5 需要哪些输入和业务资料
6 可以拆成哪几条并行路线
7 哪些情况必须转人工
8 接入什么企业系统后才有特殊价值
```

### A组：招聘信息审核

课堂材料：

> 高薪招聘运营经理，月入2万元起。限男性，30岁以下，本地户口。无经验也可以，面试通过即可入职。需先参加公司指定培训，培训费用可以办理分期。

教师参考：

| 项目 | 参考方向 |
| --- | --- |
| 业务问题 | 招聘信息数量多，完整性、真实性和发布质量难管理 |
| 小场景 | 企业发布岗位前的信息审核 |
| 人工工序 | 查企业、查岗位、查薪资、查必填项、查限制条件 |
| 输出 | 缺项、问题位置、风险类型、修改要求和是否转人工 |
| 输入 | 招聘文案、企业信息、岗位编制、薪酬范围、有效期 |
| 并行路线 | 文案与必填项、企业资质、岗位资料一致性 |
| 人工条件 | 企业或岗位无法确认、信息冲突、疑似异常引流 |
| 企业连接 | 招聘系统、企业名录、岗位编制、薪酬系统、投诉记录 |

### B组：发票与报销审核

课堂材料：

> 技术部门员工提交一张周末产生的高额休闲服务发票，备注为客户招待；报销金额在个人权限内，但OA中没有对应招待申请，部门预算也接近用完。

教师参考：

| 项目 | 参考方向 |
| --- | --- |
| 业务问题 | 财务需要反复核票、查预算、查合同和查审批流程 |
| 小场景 | 员工费用报销初步审核 |
| 人工工序 | 验票、核科目、核金额、查人员、查预算、查审批 |
| 输出 | 通过、驳回、待补材料、等待预算或人工复核 |
| 输入 | 发票、报销单、员工、部门、预算、合同和OA记录 |
| 并行路线 | 票据验真、报销政策、预算、合同与审批核对 |
| 人工条件 | 科目与业务矛盾、异常人员、预算冲突或多路结论不一致 |
| 企业连接 | 财务系统、OA、预算、合同系统和付款系统 |

### C组：金融营销材料审核

课堂材料：

> 稳健理财，年化收益6%。本金安全，无需承担市场风险。历史表现优秀，适合所有投资者。

教师参考：

| 项目 | 参考方向 |
| --- | --- |
| 业务问题 | 宣传内容需要与正式产品材料、风险提示和适用人群保持一致 |
| 小场景 | 一类理财产品宣传材料发布前审核 |
| 人工工序 | 查宣传表达、查产品文件、查风险提示、查适用人群和版本 |
| 输出 | 问题位置、缺失信息、风险等级、修改要求和人工结论 |
| 输入 | 宣传材料、正式产品文件、风险提示、目标人群和渠道要求 |
| 并行路线 | 明确表达检查、产品事实核对、风险披露完整性 |
| 人工条件 | 高风险承诺、材料冲突、适用人群不清或系统结论冲突 |
| 企业连接 | 产品中心、合规系统、客户分层、渠道发布和版本管理 |

### 教师点评原则

不要只评价学员是否想到了很多功能。重点检查：

1. 场景是否足够小；
2. 人工工序是否具体；
3. 输出是否能够推动下一步动作；
4. 输入是否包含业务事实，而不只有待审核文本；
5. 并行路线是否来自真实分工；
6. 人工接管条件是否明确；
7. 企业内部连接是否真的改变判断质量。

## 6. 本节收束（166—170分钟）

### 教师讲述

今天不是让大家记住四个行业案例，而是掌握一套迁移方法。

合同审核告诉我们：先理解法务怎样工作，再把条款、法律引用和企业风险拆开处理；客服质检告诉我们：同样的方法可以迁移到多轮对话、订单和服务政策；招聘、报销和金融材料进一步说明，不同行业的输入、责任人和自动化边界都不同。

真正可迁移的不是页面，而是下面这条主线：

```text
理解业务问题
→ 拆解人工工序
→ 定义输出与输入
→ 验证基础能力
→ 设计并行工作流
→ 补齐异常和人工承接
→ 连接企业内部系统
→ 用实际运行决定下一步
```

最后强调两句话：

1. 通用模型提供基础判断能力，企业数据和业务流程决定产品是否真正可用。
2. 迁移不是更换行业名称，而是在新业务中重新完成一次完整的产品判断。

# 全课收束与课堂输出（170—180分钟）

## 1. 回看三节课之间的关系

```text
第一节：让正常链路跑起来
        ↓
第二节：让链路在异常中继续工作
        ↓
第三节：把这套设计能力带到其他业务
```

教师讲述：

第一节解决“系统如何围绕版本、任务和角色运行”；第二节解决“理想条件不成立时怎样继续”；第三节解决“能否离开当前页面和当前行业，重新完成一遍产品判断”。

这三件事合起来，才是一名 AI 产品经理在项目里真正需要承担的工作。

## 2. 一页课堂输出

每位学员选择一个自己熟悉的业务，完成一页判断型 AI 产品设计图，至少包含：

- 一个具体业务问题；
- 一个第一版小场景；
- 一条人工工作流程；
- 主要输入与最终输出；
- 两至三条并行任务；
- 三个异常分支；
- 一个人工承接点；
- 一个需要连接的企业系统；
- 一个决定继续、修改或缩小范围的观察结果。

## 3. 结束语

一个判断型 AI 产品是否专业，不取决于页面里放了多少模型能力，而取决于它能否在真实业务中回答：

```text
判断谁
参考什么
怎样运行
失败怎么办
谁来负责
如何继续改进
```

# 教师备课补充

## 授课边界

- 合同、报销、招聘和金融案例用于产品设计教学，不作为相应专业意见；
- 不让学员讨论某个具体条款最终是否合法，重点讨论系统需要什么输入、怎样分工和何时交人；
- 合同案例中的模型定位是初步审核助手，不能替代法务负责人；
- 高风险业务中，系统可以辅助定位和核对，但最终责任仍需明确到人；
- 课堂Demo默认使用本地模拟能力，不把演示结果表述为真实生产系统表现；
- “未发现问题”“检查完成”“正式通过”“巡检关闭”是四种不同状态，授课时不要混用。

## 节奏控制

- 第一节演示不要逐项介绍所有按钮，要围绕内容版本、运行快照、正式任务和巡检闭环讲；
- 第二节每个异常先让学员作决定，再给处理框架；
- 合同案例控制在15分钟，重点是项目方法，不展开法律专业知识；
- 客服质检必须现场完成一次映射，让学员看到迁移过程；
- 小组练习不追求完整PRD，每组只回答八个问题；
- 如果学员讨论技术实现过多，立即拉回“人工原来怎样做、最终谁使用结果”；
- 如果课堂时间不足，金融营销组可以作为教师口头补充，保留招聘和报销两个小组。

## 课堂板书总图

```text
业务对象与版本
      ↓
检查运行与任务状态
      ↓
人工处理与实际闭环
      ↓
缺项 / 失败 / 冲突 / 争议
      ↓
继续 / 重试 / 降级 / 转人工 / 终止
      ↓
抽象方法并迁移到新业务
```
