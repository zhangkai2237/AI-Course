## 一、本模块的唯一教学目标

本模块不是再次证明“销售拜访记录助手值得做”，也不是展示AI可以生成一份漂亮纪要。

本模块只完成一次完整转换：

> 模糊需求 → 明确输出与上下文 → 结构化Prompt → 固定项/变量项/自动获取项 → 用户可操作的产品流程。

模块04—06已经分别产出了V0.1、V0.2和V0.3，因此本模块不让学员从头再写一遍。本模块的新增价值是：把已有设计放进一段完整转写中测试，用真实Bad Case校验并完成最小修改。

### 学员在24分钟内必须完成的结果

一份《销售拜访记录助手Prompt产品化设计单》课堂版，至少包含：

- 目标输出与验收标准；
- 必要上下文；
- 结构化Prompt关键部分；
- 产品固定、用户提供和系统获取三类信息供给；
- 普通展示、建议检查和必须确认三档风险处理；
- 用户看到的输入与确认动作；
- 至少三条第一轮结果中的问题。

### 不再讨论的内容

这些内容第0课已经讲过，本模块直接采用既有结论：

- 销售拜访后整理记录耗时且容易遗漏；
- AI可以辅助转写、提取和生成CRM草稿；
- 重要事实、日期、金额和承诺需要人工确认；
- AI结果不能在未经确认时直接作为最终商务事实。

## 二、案例设计原则

### 1. 有足够事实，也有故意保留的不确定性

转写中同时包含：

- 明确诉求；
- 明确异议；
- 清楚的下一步行动；
- 销售人员的推测；
- 客户主动纠正；
- 没有确认的预算、决策人和采购时间；
- 相对确定的5店试点与尚待确认的扩店范围。

这样才能检查模型是否把“可能、希望、内部确认”错误改写成确定事实。

### 2. 业务复杂度够用，但不依赖行业知识

案例使用虚构的连锁餐饮门店运营SaaS，不要求学员理解餐饮专业知识。核心问题集中在：

- 多系统数据接口；
- 数据和隐私要求；
- 小范围试点；
- 商务条件尚未确认；
- 多方行动项。

### 3. 不用模型知识考学员

学员不需要判断模型架构、RAG方案或接口实现，只使用本课已经学过的：

- 输出与验收；
- 上下文；
- 六要素；
- 产品化三类信息。

FlowSight用于汇总门店经营数据、巡检记录和任务进展，帮助连锁企业减少人工报表整理，并跟踪门店行动项。

以下信息在会议前尚未确认：

- 客户预算金额；
- 最终采购决策人；
- 正式采购时间；
- 全量上线范围；
- 私有化部署方案及价格。

首要用户是一线销售林然。她需要在拜访后检查AI草稿并录入CRM，为后续技术评审和试点推进做准备。

本次只整理：

- 客户核心诉求；
- 客户异议与风险关注；
- 试点意向；
- 下一步行动；
- 待确认信息。

不要求模型完成：

- 判断客户一定会不会签约；

- 自动写入CRM；

## 五、虚构拜访转写

> 使用说明：下列文本为教学虚构。正式课堂中保留说话人标签，不要清洗成一段无角色文本，否则会把“说话人识别”问题混入Prompt练习。

```text
林然（客户经理）：今天主要想确认三件事：你们希望先解决的运营问题、试点范围，以及我们两边接下来要准备什么。如果有我理解不准确的地方，请你们直接纠正。

陈洁（客户运营负责人）：我们现在48家直营店，每天巡检照片、整改任务和销售数据散在三个群和几张Excel里。区域经理每周要花差不多半天汇总，最后还经常追不到门店有没有改。我们最想先解决的不是做一个更漂亮的报表，而是自动汇总异常、找到责任人，并且能看到整改有没有按时完成。

林然：我理解核心是经营数据汇总和任务闭环。如果试点效果可以，你们是不是就准备直接采购并铺到全部门店？

陈洁：这个先别这样写。试点通过不等于已经承诺采购，我们还要看数据接入、店长使用情况和内部预算。第一批可以先选5家店；如果内部协调顺利，也可能加到8家，但今天只能确认先按5家准备。

周凯（客户IT负责人）：数据接入是我最担心的。交易数据在现有POS里，会员数据是另一个系统，巡检照片又在企业协作工具里。你们要先给接口清单，我们才能判断哪些能开放。另外，员工照片和门店经营数据不能未经确认就传到外部环境，部署方式和权限日志要单独评审。

赵楠（解决方案顾问）：如果POS提供的是标准接口，交易数据接入通常两周左右能完成；但现在还没看过你们的接口文档，这不是正式工期承诺。照片和会员数据是否进入第一期，也建议技术评审后再定。我们可以提供公有云和专有部署的说明，具体方案要结合安全要求确认。

陈洁：预算不是唯一考虑，但今年确实比较紧，目前没有确认金额。我们希望先把5家店跑起来，看两周内能不能减少区域经理整理时间、提高整改任务按时完成率。有人刚才问能不能6月底上线，我只能说希望尽快，具体启动时间要等安全评审和内部排期，今天不能承诺。

林然：明白。那我们这边本周五，也就是6月19日18点前，发接口清单和5店试点方案。我负责试点方案，赵楠负责接口清单。你们这边能否下周二前给一份脱敏的样例数据和现有巡检字段？

周凯：可以，我负责，6月23日下班前给。如果脱敏审批卡住，我会提前说。

赵楠：技术评审暂定6月24日下午3点，参会人包括双方IT和方案团队。我会发会议邀请。评审之前我们不把两周接入时间写进正式计划。

陈洁：对。另外请在CRM里写清楚：目前确认的是5店试点准备，不是采购承诺，也没有确认全量上线时间。
```

### 5.1 转写中的关键教学点

| 类型 | 文本中的设计 |
|---|---|
| 明确诉求 | 自动汇总异常、找到责任人、跟踪整改是否按时完成 |
| 可量化现状 | 48家直营店；区域经理每周约半天汇总 |
| 客户纠正 | “试点通过不等于已经承诺采购” |
| 确定范围 | 当前确认按5家店准备 |
| 尚未确认 | 可能扩到8家；预算；采购；启动时间；部署方式 |
| 技术异议 | 多系统接口、外部环境、权限日志、安全评审 |
| 非正式估计 | 标准接口情况下约两周，但不是承诺 |
| 下一步安排 | 6月19日方案和接口清单、6月23日样例与字段已明确；6月24日技术评审时间为暂定 |
| 负责人 | 林然、赵楠、周凯分别承担具体动作 |

## 六、简化CRM字段说明

| 字段 | 填写要求 |
|---|---|
| 客户核心诉求 | 只写客户明确表达的问题和目标，尽量附证据原话 |
| 当前方案/试点范围 | 区分“已确认”“讨论中”“待确认” |
| 主要异议与风险 | 写明客户担心的具体对象，不写泛泛的“有技术风险” |
| 合作意向 | 不把试点意向写成采购承诺 |
| 预算 | 有明确金额才填写；否则标记“未确认” |
| 决策人 | 有明确角色或姓名才填写；否则标记“待确认” |
| 预计启动/采购时间 | 客户明确承诺后填写；“希望尽快”不等于确定时间 |
| 下一步行动 | 每条尽量包含事项、负责人、截止时间和状态 |
| 证据 | 关键结论对应的客户原话或转写片段 |

## 八、第一轮：模糊输入暴露问题（84—89分钟）

### 8.1 模糊Prompt

```text
帮我整理一下这次销售拜访。
```

实际课堂应把背景卡和完整转写与这句Prompt一同交给模型，否则结果差异可能只是“没有输入材料”，不能有效展示任务定义问题。

### 8.2 教学预置示意结果

> 注意：以下不是指定模型的实测输出，正式PPT必须替换成课堂所用模型的真实结果。

```text
禾味餐饮拥有48家门店，目前数据分散、人工整理效率较低，希望通过FlowSight实现经营数据自动汇总和整改闭环。

客户认可产品方案，计划先在8家门店试点，试点成功后采购并推广到全部门店。客户预算虽然紧张，但不是主要问题，预计6月底上线。技术上需要对接POS、会员和巡检系统，预计两周完成。

下一步：北辰云科提供试点和技术方案，禾味餐饮提供数据，双方安排技术会议。
```

### 8.3 学员找错任务

要求学员至少找到3处，不能只说“太笼统”。

### 8.4 参考问题清单

| 示意结果 | 问题 | 原文依据 |
|---|---|---|
| 计划先在8家门店试点 | 把可能方案写成确定事实 | 客户只确认按5家准备，8家需内部协调 |
| 试点成功后采购并全量推广 | 把销售推测写成客户承诺 | 客户明确纠正“试点通过不等于承诺采购” |
| 预计6月底上线 | 把希望和提问改成计划 | 客户明确表示今天不能承诺启动时间 |
| 技术对接预计两周完成 | 把条件估计写成正式工期 | 方案顾问明确说未看接口，不是承诺 |
| 客户预算不是主要问题 | 淡化预算未确认事实 | 客户说今年预算紧，目前没有确认金额 |
| 下一步行动无负责人和日期 | 无法进入CRM和创建任务 | 原文给出了具体负责人和截止时间 |
| 未体现数据和隐私风险 | 漏掉关键异议 | 客户要求部署方式、权限日志和安全评审 |
| 未标记决策人等缺失信息 | 看起来完整但实际关键信息缺失 | 原文未确认预算、决策人和采购时间 |

### 8.5 第一轮收口

> 这份结果语言通顺，也抓到了一部分主题，但它把可能性写成了承诺、漏掉行动项细节，因此不能直接进入CRM。问题不只是模型“聪不聪明”，还包括任务、规则和输出标准没有说清楚。

## 九、第二轮：结构化Prompt改善结果（89—98分钟）

### 9.1 小组只做最小修改，不重新写Prompt

小组取出模块05完成的Prompt V0.2，根据第一轮发现的问题，最多新增或修改3条内容。优先从以下四项选择：

1. 任务目标是否过宽；
2. 事实与缺失信息规则是否缺失；
3. CRM输出字段是否不可验收；
4. 关键证据要求是否不足。

限制修改数量的目的是训练“根据Bad Case做针对性修正”，避免再次完整练习六要素。

### 9.2 结构化Prompt参考答案

```text
【角色与能力】
你是销售拜访记录整理助手，负责依据给定材料生成便于销售检查和录入CRM的草稿。

【任务目标】
请根据客户背景、CRM字段说明和本次拜访转写，整理：
1. 客户核心诉求；
2. 试点范围与当前状态；
3. 主要异议与风险；
4. 合作意向；
5. 下一步行动；
6. 待确认信息。

【输入材料】
客户背景：{{customer_context}}
CRM字段说明：{{crm_schema}}
拜访转写：{{visit_transcript}}

【规则与约束】
1. 只依据输入材料，不把销售提问、推测或方案方估计写成客户承诺；
2. 区分“已确认”“讨论中”“待确认”；
3. 客户主动纠正的内容优先作为最终事实；
4. 关键结论附一段证据原话；
5. 未确认的预算、决策人、采购和启动时间必须标记“待确认”；
6. 行动项尽量包含事项、负责人、截止时间和状态；
7. 不生成成交概率和采购建议。

【输出格式与验收标准】
请按CRM字段表输出。每个结论包含“内容、状态、证据”。
行动项单独用表格输出。最后列出待确认问题。

【输出前检查】
检查是否把5店写成8店、把试点写成采购承诺、把两周估计写成正式工期、把希望6月底上线写成确定时间。如有，必须修正。
```

#### 客户核心诉求

|---|---|---|

| 减少区域经理人工汇总时间 | 已明确 | “区域经理每周要花差不多半天汇总。” |

### 10.1 信息供给与风险处理参考

### 10.2 用户打开页面时应该看到什么

#### 顶部：系统自动带入

- 客户：禾味餐饮；
- 商机阶段：方案验证；
- 拜访时间：6月16日；
- 参会人：可编辑；
- 转写状态：已完成/需检查。

#### 中部：用户最小必要输入

- 本次输出：诉求、试点、异议、行动项、待确认信息，默认选中；
- 特殊备注：可选；
- 是否生成跟进邮件：默认关闭，作为独立后续任务；
- 生成CRM草稿按钮。

#### 结果区：不是一段纯文本

- 按CRM字段分块；
- 每条关键结论展示证据原话；
- “已确认/讨论中/待确认”状态标签；
- 日期、金额、责任人、采购承诺等高风险字段高亮；
- 支持编辑、删除和回到原文；
- 用户确认后才允许写入CRM。

## 十二、案例常见争议与老师处理

### 争议1：为什么不直接让模型判断合作意向？

合作意向可以作为草稿字段，但必须区分客户原话与销售判断。本案例刻意不让模型输出成交概率，因为缺少决策人、预算和采购时间等关键信息。

### 争议2：为什么5家试点算确认，技术评审却写“暂定”？

客户明确说“今天只能确认先按5家准备”；技术评审使用了“暂定”，因此状态不同。课堂重点是尊重原文中的确定性程度。

### 争议3：为什么客户基本信息可以自动带入？

因为场景假设产品与CRM连接。但自动带入的数据可能过期，所以仍允许销售查看和修正。本课不展开接口实现。

### 争议4：为什么要附证据原话，会不会太长？

重要商务事实需要可追溯。产品可以默认折叠证据，不必把全部原文铺开；高风险字段至少应能回到原文核对。

### 争议5：结构化Prompt已经很好，为什么还要人工确认？

Prompt可以减少一类错误，不能保证模型、转写和业务数据永远正确。采购承诺、时间、金额和责任人会影响后续商务动作，需要保留确认。

### 争议6：这个案例为什么没有讲ASR准确率？

本课专注大模型上下文和Prompt。案例直接提供带说话人的转写，避免把语音识别问题混入练习。ASR错误可在后续真实项目中作为另一类Bad Case分析。

## 十三、课堂执行风险与预案

### 1. 时间超出

优先压缩：

- 学员分享人数，从2组减到1组；
- 第二轮逐字段讲解，只检查试点、采购、行动项；
- 线框图讨论，只保留输入、结果和确认三块。

不能压缩：

- 第一轮至少找到3处事实性问题；
- 第二轮必须明确事实/推测/待确认；
- 第三轮必须完成三类信息拆分和人工确认。

### 2. 现场模型结果过于完美

直接使用预生成的真实Bad Case截图，不为证明课程价值而反复修改Prompt诱导模型犯错。课堂讨论可以转向：即使这一次正确，产品怎样保证面对其他拜访仍可检查。

### 3. 现场模型结果过于糟糕

先确认是否完整提供了背景、转写和字段说明。若是技术或网络异常，切换预生成结果，不在课堂上临时调试模型。

### 4. 学员再次讨论场景价值

提醒：第0课已经完成场景判断。本轮只回答“已决定做以后，模型如何得到正确上下文，用户如何使用结果”。

### 5. 学员开始设计完整CRM

限制输出：只画AI生成前的必要输入和生成后的检查确认，不扩展客户管理、商机漏斗和权限后台。
