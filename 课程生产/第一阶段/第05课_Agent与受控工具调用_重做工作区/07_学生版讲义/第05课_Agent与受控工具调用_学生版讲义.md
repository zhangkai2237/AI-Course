# 第05课：Agent与受控工具调用

## 一、本课要解决的问题

大模型可以回答问题，但真实产品经常还需要：

- 查询实时数据；
- 读取业务规则；
- 调用外部系统；
- 创建草稿；
- 根据中间结果决定下一步；
- 在风险过高时停止或转交人工。

本课关注的不是“Agent这个词有多热门”，而是：

> 当任务路径不能完全提前写死时，产品经理怎样设计一个能够使用工具、又不会失控的Agent？

---

# 第一部分：Chatbot、Workflow与Agent

## 1. Chatbot

Chatbot描述的是一种对话交互形态。用户输入问题，系统用对话方式回应。

它可能只是问答，也可能在内部调用Workflow或Agent。因此，“有聊天框”不能证明它就是Agent。

## 2. Workflow

Workflow适合主要步骤可以提前确定的任务。

```text
触发任务 → 执行步骤A → 执行步骤B → 执行步骤C → 输出结果
```

Workflow也可以包含条件分支，但关键路径主要由设计者提前规定。

适合：

- 标准审批；
- 固定信息抽取；
- 稳定的内容生成流程；
- 强调确定性和可预测性的任务。

## 3. Agent

本课采用的产品化定义是：

> Agent围绕一个目标，根据当前信息和工具返回结果判断下一步，调用外部能力改变任务状态，直到完成、停止或转交人工。

Agent更适合：

- 目标明确，但中间路径会变化；
- 需要在多个工具中动态选择；
- 工具结果会改变下一步；
- 需要补充信息、处理失败或调整计划。

## 4. 三者不是高低关系

| 对比项 | Chatbot | Workflow | Agent |
|---|---|---|---|
| 主要描述 | 交互方式 | 预设执行路径 | 目标驱动的动态执行 |
| 路径 | 不一定涉及执行 | 主要提前规定 | 根据状态动态判断 |
| 工具 | 可有可无 | 节点中固定调用 | 根据情况选择调用 |
| 可预测性 | 取决于内部实现 | 通常较高 | 通常较低 |
| 适用重点 | 对话体验 | 稳定流程 | 开放路径任务 |

真实产品可以组合使用：

> Workflow控制稳定主干，Agent负责局部动态判断。

# 第二部分：Agent的最小运行循环

为了判断一个产品是否真的具备Agent能力，可以观察下面的循环：

```text
目标
→ 当前状态
→ 判断下一步
→ 行动或调用工具
→ 观察结果
→ 继续、确认、停止或转人工
```

## 门店经营助手示例

用户目标：

> 分析指定门店的新客下降问题，并给出改善建议。

可能的运行过程：

1. 检查是否提供门店和日期；
2. 信息不足则向用户追问；
3. 信息完整后查询经营数据；
4. 根据工具返回的诊断标签判断下一步；
5. 如确实是新客下降，再查询适用活动规则；
6. 根据数据和规则生成建议；
7. 用户只要建议时直接结束；
8. 用户希望创建草稿时，展示完整参数并等待确认。

## 判断Agent运行质量时看什么

不要只看最后一句回答，还要观察：

- 当前目标是什么；
- 系统掌握了哪些信息；
- 为什么选择这个工具；
- 实际传入了哪些参数；
- 工具返回了什么；
- 返回结果怎样改变下一步；
- 何时停止；
- 何时要求确认。

# 第三部分：Function Calling与工具设计

## 1. Function Calling是什么

Function Calling让模型可以用结构化方式表达：

- 想调用哪个工具；
- 需要传入哪些参数。

典型过程：

```text
模型提出工具和参数
→ 应用校验参数、权限和风险
→ 应用真正执行工具
→ 工具结果返回模型
→ 模型继续判断或停止
```

需要特别注意：

> 模型提出调用，不等于工具已经执行。真正访问数据库或修改业务系统的是应用和工具。

## 2. 为什么工具描述很重要

模糊工具：

```text
query_data：查询数据
```

模型无法确定：

- 查询什么；
- 什么时候使用；
- 要提供哪些参数；
- 与其他工具有什么区别；
- 失败后怎么办。

更清晰的工具：

```text
query_store_metrics：
查询指定门店在指定日期范围内的经营指标；
不查询活动规则，不创建活动，不访问未授权门店。
```

## 3. 产品经理需要定义的十项内容

| 字段 | 要回答的问题 |
|---|---|
| 名称 | 系统怎样唯一识别 |
| 用途 | 解决什么问题 |
| 使用条件 | 什么时候应该调用 |
| 输入参数 | 执行前需要什么 |
| 参数类型 | 日期、数字、枚举还是文本 |
| 必填/选填 | 缺少什么必须追问 |
| 成功返回 | 成功后得到什么 |
| 异常返回 | 失败、无数据、冲突怎样表示 |
| 权限 | 谁可以使用 |
| 确认 | 调用前是否需要确认 |

## 4. 错误返回也应结构化

只有“查询失败”四个字时，Agent不知道下一步。

更可用的返回：

```text
status: failed
error_code: STORE_NOT_FOUND
message: 门店ID不存在
retryable: false
next_action: ask_user_to_check_store_id
```

这样系统才能判断重试、追问或停止。

# 第四部分：同一目标为什么会走不同路径

课堂案例只使用三个工具：

```text
query_store_metrics
search_activity_rules
create_campaign_draft
```

## 1. 新客下降

```text
查经营数据
→ 返回新客下降标签
→ 查新客活动规则
→ 生成建议
→ 用户确认
→ 创建活动草稿
```

## 2. 补贴异常

```text
查经营数据
→ 新客正常、补贴异常
→ 不走拉新活动路径
→ 查询补贴与成本限制
→ 输出优化建议
→ 不创建新活动
```

## 3. 数据不足

```text
查经营数据
→ 只有少量数据
→ 询问是否扩大时间范围
→ 用户同意后重新查询
→ 用户拒绝则停止
```

关键结论：

> Agent不是按固定顺序把所有工具调用一遍，而是根据工具返回状态选择下一步或停止。

经营异常标签应由数据规则返回，不能让模型自行发明“下降多少才算异常”。

# 第五部分：设计一个可控Agent

在进入平台前，先回答下面的问题。

## 1. 目标

- 服务对象是谁？
- 用户要完成什么任务？
- 什么结果代表任务完成？

## 2. 信息

- 开始任务最少需要什么信息？
- 缺少信息时应该追问什么？
- 哪些内容不能自行猜测？

## 3. 工具

- 每个工具解决什么问题？
- 什么情况下调用？
- 哪些事情明确不负责？

## 4. 边界

- 哪些动作可以自动执行？
- 哪些动作需要用户确认？
- 哪些动作必须审批或禁止？

## 5. 异常与结束

- 工具失败怎么办？
- 无权限怎么办？
- 结果冲突怎么办？
- 什么情况下停止？
- 什么情况下转人工？

# 第六部分：风险、异常与人工接管

## 1. 能建议不等于能执行

| 动作 | 示例 | 默认控制 |
|---|---|---|
| 读取公开知识 | 查询公开规则 | 可自动并记录 |
| 读取业务数据 | 查询门店指标 | 校验身份与权限 |
| 生成建议 | 输出运营方案 | 展示依据，允许修正 |
| 创建草稿 | 创建活动草稿 | 执行前明确确认 |
| 对外发布 | 发布活动、发送消息 | 强确认或人工审批 |
| 不可逆动作 | 扣款、删除、发放高额补贴 | 默认禁止自动执行或严格审批 |

判断风险时至少看：

- 出错后的影响；
- 是否容易撤销；
- 是否涉及真实用户、资金、隐私或外部系统；
- 是否需要用户确认或人工审批。

## 2. 四类异常

### 信息不足

指出缺什么并追问，不自行猜测。

### 工具失败

区分无结果、参数错误和调用失败，不编造结果。

### 权限超界

说明当前可执行范围，不使用其他方式绕过限制。

### 任务失控

限制重试次数；连续失败后停止，并保留上下文转交人工。

## 3. 为什么需要确认卡

一句“是否确认”信息不足。确认卡至少应展示：

- 操作对象；
- 目标人群；
- 关键方案；
- 时间；
- 预算；
- 当前动作会造成什么结果；
- 是否可以撤销。

## 4. 人工接管时应保留

- 用户原始目标；
- 已确认参数；
- 已调用工具；
- 工具返回；
- 失败位置；
- 建议人工下一步。

# 第七部分：用五条测试验证Agent

一次成功对话不能证明产品可靠。课堂测试至少覆盖：

| 编号 | 测试类型 | 主要检查 |
|---|---|---|
| T1 | 正常完成 | 工具与参数是否正确 |
| T2 | 信息缺失 | 是否先追问而不猜测 |
| T3 | 动态改路 | 工具结果是否改变下一步 |
| T4 | 工具失败 | 是否如实说明并安全停止 |
| T5 | 越权请求 | 是否拒绝越权并要求确认 |

# 第八部分：MCP与Multi-Agent

## 1. 三个概念分别解决什么

| 概念 | 主要问题 |
|---|---|
| Function Calling | 模型如何结构化表达工具和参数 |
| MCP | AI应用如何用相对统一的协议连接工具、资源和上下文 |
| Agent | 如何围绕目标判断下一步并完成任务 |

MCP不是Agent，也不替Agent做任务决策。

## 2. 什么情况下考虑MCP

- 需要连接多个外部系统；
- 工具和资源经常变化；
- 多个AI客户端需要复用同一组能力；
- 希望减少重复适配。

只有三个固定工具的课堂案例不必为了使用MCP而使用MCP。

## 3. 什么是Multi-Agent

Multi-Agent让多个承担不同角色或子任务的Agent协作。

可能适用：

- 子任务高度专业化；
- 不同角色需要不同知识、工具或权限；
- 任务能明确拆分和校验；
- 协作收益高于成本。

不适用：

- 一个Agent加少量工具已经能完成；
- 角色边界不清；
- 无法评价每个角色的输出；
- 对成本和时延要求严格。

默认原则：

> 先用单Agent加少量工具跑通闭环，出现明确瓶颈后再考虑拆分。

# 第九部分：课程总结与作业

## 四句话总结

1. Agent不是更会聊天，而是围绕目标判断下一步并使用工具；
2. 工具不是越多越好，职责、参数、权限和异常必须明确；
3. 能执行就必须能受控，高风险动作需要确认或审批；
4. 先跑通单Agent最小闭环，再判断是否需要MCP或Multi-Agent。

## 课后作业

选择一个来自工作或生活的真实但已脱敏的场景，完成《受控Agent产品设计V1.0》：

1. 写清用户、问题和任务目标；
2. 说明为什么需要Agent；
3. 设计2—4个工具；
4. 标出动态判断、确认、停止和人工接管；
5. 设计五条测试；
6. 判断是否需要MCP；
7. 判断是否需要Multi-Agent。

评价重点不是复杂，而是：

> 场景真实、目标明确、工具清晰、执行受控、结果可测试。
