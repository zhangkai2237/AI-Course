# AI Invoice Auditor 产品需求文档（中文改写）

> 来源：英文 `原始PRD.xlsx` 与 `原始PRD.csv`。本文按中文 PRD 结构重组原方案。

## 1. 产品定义

AI Invoice Auditor 是一套企业内部的应付账款批量审计工具。用户在月末上传 ERP 交易 CSV 和发票 PDF 文件夹，系统自动匹配、检查、分流并生成审计记录。

## 2. 用户问题

财务 Controller 每月要处理约 1,500 张发票。人工只能抽样，无法在有限人力下覆盖全部票据；核对 ERP 和 PDF、判断费用类别、发现可疑编辑以及整理外审材料都耗费大量时间。

## 3. 用户与场景

- 使用者：Controller、高级 AP 经理；
- 购买者：CFO、VP Finance；
- 场景：月末结账、AP 复核、SOX 准备和外部审计；
- 产品形态：针对单企业政策和流程的内部工具。

## 4. 产品目标

- 对月度发票进行全量预检查；
- 缩小人工需要深入复核的范围；
- 对每个结论给出证据和可解释原因；
- 保证单张票据失败不影响整批任务；
- 形成可导出、可追溯的审计记录。

## 5. 输入与输出

### 输入

- ERP CSV：交易 ID、日期、供应商、金额、币种、费用类别、提交人和描述；
- 发票 PDF 文件夹：文件名与交易 ID 对应；
- 企业费用分类政策；
- 模型密钥和可编辑系统提示词。

### 输出

- 金额、币种、供应商、类别和真实性的单项结论；
- 0—1 置信度；
- 发票中的证据引用；
- 简短解释；
- 最终应用状态；
- 人工评论、修改和重跑记录；
- 审计 CSV 和完整时间线。

## 6. 核心功能

### F1 批次接入与预检查

验证 CSV 必填字段、PDF 命名和交易匹配关系。缺失、重复或无法匹配的项目单独标记，不阻断其他记录。

### F2 五类发票检查

1. 金额是否与 ERP 一致；
2. 币种是否一致；
3. 供应商是否一致；
4. 费用类别是否符合政策；
5. 票据是否存在编辑或伪造迹象。

每项检查返回通过、失败或不明确，并附置信度、证据和解释。

### F3 应用层状态判断

应用程序根据不同检查的风险设置不同阈值，将记录分为匹配、金额/供应商不匹配、类别异常、可疑、人工复核或 AI 错误。模型不直接控制最终状态。

### F4 人工复核

Controller 可以查看 PDF 与证据、修改任何字段、添加评论、重跑模型并做最终签字。

### F5 历史与导出

保存每次模型输出、阈值判断、人工修改和重跑记录，生成可供审计使用的 CSV 和汇总仪表盘。

## 7. 模型与系统方案

- 模型：GPT-4o-mini；
- 原因：支持视觉 PDF、速度较快、JSON 稳定且成本较低；
- 当前政策：7 个费用类别直接放入系统提示词；
- 扩展方案：政策变长后按类别切分，用 RAG 只检索最相关的 2—3 类；
- 执行单位：每张发票一次模型调用；
- 数据存储：Supabase 保存批次、结果、历史和人工操作。

## 8. 异常处理

- PDF 不可读：标记 `AI_ERROR`，继续处理后续记录；
- JSON 无法解析：自动重试，失败后转人工；
- CSV 必填字段缺失：在预检查阶段隔离；
- 交易和 PDF 无法匹配：列入异常清单；
- API 超时：按项目重试，不重跑整批；
- 低置信度：进入人工复核，不自动定性。

## 9. 评测方案

项目建立 30 张已标注发票的 Gold Set，并保留 10 张不参与调参的 Hold-out Set。

v6 结果为：JSON 和 Schema 30/30；150 项检查中 138 项与人工一致；最终状态 24/30 正确。主要错误集中在真实性判断。

v7 增加版式一致性、金额算术检查和编辑票据 Few-shot，在同一 30 例上达到 150/150 单项一致、30/30 状态正确。由于这是调参集结果，必须使用 Hold-out Set 验证是否过拟合。

## 10. 验收与风险

- 结构化输出必须稳定；
- 任何最终状态都能回溯单项检查与证据；
- 批次中单项失败不得引发全局失败；
- 人工必须拥有覆盖和签字权；
- 真实部署需完成零留存、安全、法务和数据治理审查；
- 上线前需验证真实 1,500 张规模下的时延、成本和长尾准确性。
