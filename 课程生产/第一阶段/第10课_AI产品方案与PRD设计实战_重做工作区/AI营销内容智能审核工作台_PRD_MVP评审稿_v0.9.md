# 一、项目摘要

## 1.1 项目名称

AI营销内容智能审核工作台。

## 1.2 业务问题

营销内容在发布前需要经过审核。随着内容生产效率和提交量提升，纯人工审核逐渐出现以下问题：

- 审核任务积压，内容发布等待时间变长；
- 同类表达可能因审核人员经验不同得到不同结论；
- 审核规则持续变化，人工难以及时掌握全部最新要求；
- 审核意见缺少结构化记录，历史问题难以复用；
- 大量重复、低价值检查占用专业审核人员时间；
- 高风险、争议和责任性判断仍然不能直接交给机器。

## 1.3 目标用户

- 提交、查看并修改内容的营销运营人员；
- 处理高风险、争议和机器不确定结果的人工审核人员；
- 维护审核标准、规则解释和版本的规则运营人员；
- 关注审核效率、风险和投入产出的业务负责人。

## 1.4 产品目标

在营销内容进入正式发布流程前增加机器预审：

- 识别明确规则风险和需要语义理解的表达风险；
- 标记风险原文，说明风险类型、等级、原因和依据；
- 为运营人员提供可操作的修改方向；
- 将高风险、不确定、依据冲突和机器失败的任务安全转交人工；
- 保留内容、机器、人工和系统版本记录，支持复现、评测和持续改进。

## 1.5 产品方案

采用固定Workflow编排的混合审核方案：

| 能力 | 核心职责 |
|---|---|
| 输入校验 | 确认内容、业务上下文和必要事实是否完整 |
| 确定性规则 | 检查禁用词、必要声明、格式、长度和明确阈值 |
| RAG知识检索 | 提供当前有效规则、解释、正反案例和历史结论 |
| 大模型语义审核 | 识别需要结合上下文判断的隐含、变体和组合语义风险 |
| 结果合并与分流 | 去重风险、保留证据、生成整体结果并路由处理 |
| 人工复核 | 接管高风险、不确定、依据冲突、申诉和机器失败任务 |

## 1.6 MVP范围

第一版支持：

- 试点业务范围内的纯文本营销内容；
- 必要业务上下文和产品事实输入；
- 确定性规则检查；
- 当前审核依据检索；
- 重点语义风险识别；
- 结构化风险结果展示；
- 机器预审通过、建议修改、退回修改、转人工复核四类处理路径；
- 运营修改后重新审核；
- 人工复核、改判和升级；
- 基础内容版本、审核结果和系统版本记录。

第一版不支持：

- 图片、视频和音频审核；
- 自动改写并覆盖原文；
- 自动发布、删除或处罚；
- Agent自主规划或跳过关键审核步骤；
- 根据单次人工结果自动训练或修改规则；
- 完整可视化规则编辑平台；
- 复杂多级线上审批。

## 1.7 核心验证假设

| 编号 | 假设 | 验证方式 |
|---|---|---|
| H-01 | 混合审核能发现纯规则难以识别的有效风险 | 离线评测中比较“纯规则”与“混合方案”的增量识别能力 |
| H-02 | 机器预审能够减少人工重复检查 | 影子运行及辅助审核中比较人工平均处理时间和单位时间处理量 |
| H-03 | 高风险和不确定结果能够被人工安全接管 | 验证转人工召回、任务完整性、处理闭环和异常兜底 |
| H-04 | 结构化解释能够帮助运营完成有效修改 | 观察建议采纳、修改完成和重新审核通过情况 |

## 1.8 上线原则

产品是否上线不由单一“模型准确率”决定。至少需要同时满足：

- 高风险样本达到业务确认的安全底线；
- 主要风险类型达到约定识别要求；
- 结构化输出可被系统稳定解析；
- 人工复核量在业务承载范围内；
- 机器失败、信息不足和依据冲突不会默认放行；
- 内容修改后必须重新审核；
- 规则、知识、模型和Prompt版本可追溯。

具体数值门槛在获得真实基线和首轮PoC结果后，由业务、规则、产品和算法共同确认。

# 二、业务背景与现状

## 2.1 当前业务流程

```text
运营创作文案
→ 提交人工审核
→ 审核人员查找规则并判断
→ 返回通过或修改意见
→ 运营修改后再次提交
→ 审核通过后进入发布流程
```

## 2.2 现状问题

| 编号 | 问题 | 业务影响 |
|---|---|---|
| P-01 | 内容提交量增长，人工审核能力难以同步扩容 | 审核积压、发布延迟、临时增加人力 |
| P-02 | 审核标准依赖个人经验 | 同类内容结论不一致，沟通和返工增加 |
| P-03 | 规则不断更新，人工同步成本高 | 旧规则继续被使用，判断依据不统一 |
| P-04 | 审核意见主要以自然语言保存 | 无法稳定统计、搜索、复现和回归 |
| P-05 | 专业审核人员重复检查低风险内容 | 高价值判断时间被压缩 |
| P-06 | 高风险内容需要明确责任主体 | 机器不能独立承担最终业务或法律责任 |

## 2.3 当前业务基线

下列数据必须从真实业务系统、任务记录和人员访谈中补充。未经核实的示例数字不作为立项依据。

| 指标 | 当前基线 | 数据来源 | 负责人 | 状态 |
|---|---:|---|---|---|

| 峰值日提交量 | 待补充 | 内容提交记录 | 业务负责人 | 待确认 |
| 平均排队等待时间 | 待补充 | 审核任务时间戳 | 研发/业务 | 待确认 |
| 平均单条人工审核时间 | 待补充 | 任务日志与审核人员抽样记录 | 审核负责人 | 待确认 |
| 首次退回修改率 | 待补充 | 审核结果记录 | 业务负责人 | 待确认 |

## 2.4 已确认约束

- 高风险内容不能因为模型失败或系统异常默认放行；
- 机器预审通过不等于自动发布；
- 内容发生实质修改后，旧审核结果不能直接沿用；
- 机器不承担最终业务、法务或合规责任；
- 试点初期保留现有人工审核链路，机器结果先经过离线和影子验证。

# 三、用户、场景与现有流程

## 3.1 用户角色

| 角色 | 核心任务 | 主要诉求 | MVP权限 |
|---|---|---|---|
| 内容运营人员 | 提交内容、查看风险、修改并重新审核 | 知道哪里有问题、为什么、如何修改 | 提交、查看本人任务、修改、重审、申请人工确认 |
| 人工审核人员 | 处理机器转入任务并作出最终判断 | 快速理解机器发现、依据和转人工原因 | 查看完整上下文、复核、驳回、改判、升级 |
| 规则运营人员 | 维护规则、解释、案例和版本 | 确认系统当前使用的审核标准 | MVP采用受控配置或导入，不建设完整编辑平台 |
| 业务负责人 | 查看效率、风险、人工负载和试点效果 | 判断是否值得扩大投入 | 查看汇总数据和试点报告 |

## 3.2 核心使用场景

### 场景S-01：运营提交机器预审

运营在内容进入发布流程前提交完整文案、渠道、产品类型、内容用途和必要产品事实。系统校验输入并启动固定审核Workflow。

### 场景S-02：运营查看并修改风险

系统在原文中标记风险片段，展示风险类型、等级、原因、依据和修改方向。运营修改后生成新版本并重新审核。

### 场景S-03：人工处理高风险或不确定任务

人工审核人员查看原始文案、机器结果、规则命中、RAG依据、模型说明、转人工原因和历史处理记录，完成复核或升级。

### 场景S-04：规则负责人处理新问题

当人工发现规则缺失、规则冲突或新型风险时，任务升级给规则负责人。新结论形成受控规则或案例版本，不直接根据单条人工意见自动生效。

### 场景S-05：业务负责人评估试点

业务负责人查看风险分布、机器处理结果、人工复核量、平均处理时间、机器与人工差异以及重要Bad Case，决定是否扩大试点。

## 3.3 核心用户故事

| 编号 | 用户故事 | 验收要点 |
|---|---|---|
| US-01 | 作为运营人员，我希望系统指出风险原文和原因，以便快速修改 | 风险可定位；原因和建议可读；支持从结果回到原文 |
| US-02 | 作为运营人员，我希望修改后重新审核，以确认问题是否消除 | 新内容生成新版本；重新执行完整审核；旧结果保留 |
| US-03 | 作为审核人员，我希望看到机器依据和转人工原因，以便快速复核 | 可查看规则、知识、模型原始结果与版本 |
| US-04 | 作为审核人员，我希望修改机器结论并记录原因 | 改判必须填写原因；保留机器原始结果和人工结果 |
| US-05 | 作为规则负责人，我希望知道任务使用了哪版规则 | 每次审核记录规则和知识版本 |
| US-06 | 作为业务负责人，我希望比较机器上线前后的效率和风险 | 指标口径一致；支持试点前后或对照组比较 |

# 四、问题、目标与非目标

## 4.1 问题定义

本项目不是简单建设“一个AI审核工具”，而是解决以下产品问题：

> 在不扩大高风险放行概率的前提下，如何把可标准化的重复检查交给系统，把需要上下文理解的判断交给大模型辅助，并让高风险和不确定任务由人工安全接管。

## 4.2 目标

### 业务目标

- 缩短营销内容的平均审核周期；
- 提高单位时间内可处理的内容数量；
- 降低人工重复检查工作量；
- 降低重点高风险问题漏放概率。

### 用户目标

- 运营人员能够快速理解问题并完成有效修改；
- 人工审核人员能够在机器结果基础上完成复核，而不是从零开始检查；
- 规则负责人能够追溯判断依据和规则版本；
- 业务负责人能够基于数据评估系统价值。

### 产品目标

- 建立“提交—机器预审—结果展示—修改/人工—重新审核—记录”的完整闭环；
- 将风险、依据和处理动作结构化；
- 确保不确定、冲突和失败结果有明确接管路径；
- 沉淀可用于评测、回归和产品改进的真实数据。

### AI能力目标

- 识别规则难以穷举、必须结合上下文判断的风险表达；
- 定位风险片段并进行类型和等级分类；
- 基于已提供的业务事实和审核依据说明原因；
- 提供修改方向；
- 无法可靠判断时明确返回信息不足、不确定或需要人工。

## 4.3 成功指标框架

| 维度 | 指标 | 基线 | MVP目标 | 最终确认人 |
|---|---|---:|---:|---|
| 效果 | 重点风险类型识别指标 | 待测 | PoC后确定 | 规则负责人 |
| 安全 | 高风险漏判底线 | 待测 | PoC后确定 | 业务＋规则负责人 |
| 增量 | 混合方案相对纯规则的有效增量 | 待测 | PoC后确定 | 产品＋算法 |
| 稳定 | 结构化输出成功率 | 待测 | 技术评审后确定 | 研发＋算法 |
| 效率 | 平均人工审核时间 | 待补充 | 影子运行后确定 | 业务负责人 |
| 效率 | 单位时间人工处理量 | 待补充 | 影子运行后确定 | 业务负责人 |
| 负载 | 转人工复核率 | 待测 | 不超过人工承载上限 | 审核负责人 |
| 使用 | 运营建议理解/采纳情况 | 无 | 试点后确定 | 产品＋运营 |

任何指标在缺少真实样本、口径和基线时不得填写为承诺值。

## 4.4 非目标

MVP阶段不追求：

- 完全替代人工审核；
- 覆盖所有业务线、行业、渠道和内容类型；
- 对所有法律或合规问题作出最终结论；
- 自动生成、覆盖并发布最终营销内容；
- 用Agent自主决定是否跳过关键审核步骤；
- 自动把单次人工改判转化为生产规则或模型训练数据；
- 建设企业级全量内容治理平台。

# 五、AI介入判断与备选方案

## 5.1 AI介入条件

本项目适合引入AI的前提：

- 业务量足以形成持续审核压力；
- 确定性规则无法完整覆盖同义改写、隐含承诺和上下文组合风险；
- 存在可提供给系统的规则、解释、案例或产品事实；
- 机器错误能够在发布前被阻断、修改或人工接管；
- 高风险内容不允许机器独立作出最终放行决定；
- 审核步骤相对固定，适合被编排、测试和追踪。

## 5.2 备选方案比较

| 方案 | 优势 | 主要问题 | 决策 |
|---|---|---|---|
| 继续纯人工 | 语义判断灵活，责任明确 | 扩展成本高，重复劳动多，规则同步困难 | 保留为高风险与异常接管方式 |
| 只使用确定性规则 | 稳定、快速、低成本、可解释 | 无法穷举复杂语义和表达变体 | 用于明确、可枚举任务 |
| 只使用大模型 | 语义理解强，覆盖表达变体 | 输出波动、依据可能过期、成本和责任边界不足 | 不采用 |
| 规则＋RAG＋大模型＋人工 | 能力互补，可兼顾效率与风险 | 需要结果合并、版本管理和人工闭环 | 采用 |

## 5.3 关键产品决策

| 决策编号 | 决策 | 原因 |
|---|---|---|
| D-01 | 第一版采用固定Workflow，不采用Agent主导审核 | 关键步骤不得被跳过；节点需单测、回归和追踪 |
| D-02 | 确定性规则与大模型分工，不将所有任务交给模型 | 提高稳定性、可解释性并控制成本 |
| D-03 | RAG提供依据，但不独立作出最终结论 | 检索结果可能缺失、过期或冲突 |
| D-04 | 大模型输出判断材料，产品流程决定业务动作 | 避免模型自由决定高影响动作 |
| D-05 | 高风险、不确定和失败结果必须有人工接管 | 满足安全与组织责任要求 |
| D-06 | 修改建议不直接覆盖原文 | 避免改变事实、意图或引入新风险 |

# 六、规则、大模型、RAG与人工的能力分工

## 6.1 能力边界

| 模块 | 主要输入 | 主要输出 | 明确不负责 |
|---|---|---|---|
| 输入校验 | 文案、渠道、产品信息、必要事实 | 缺失字段、格式问题、可否启动审核 | 不判断语义风险 |
| 确定性规则 | 文案、结构化规则、适用范围 | 命中规则、风险片段、规则版本 | 不独立处理复杂上下文 |
| RAG知识检索 | 业务类型、渠道、风险类别、时间 | 当前有效规则、解释、正反案例 | 不作最终审核结论 |
| 大模型语义审核 | 完整文案、上下文、产品事实、规则与依据 | 风险类型、等级、原文、原因、依据、建议、不确定性 | 不承担最终责任或执行外部动作 |
| 结果合并与分流 | 规则结果、模型结果、调用状态 | 去重风险、整体结果、后续动作 | 不修改审核标准 |
| 人工复核 | 原文、机器结果、依据、版本与历史记录 | 最终结论、改判原因、升级信息 | 不重复检查全部低风险内容 |

## 6.2 产品主流程

```text
运营提交内容与业务上下文
→ 输入校验
→ 确定性规则检查
→ 检索当前适用审核依据
→ 大模型语义审核
→ 合并、去重并校验结果
→ 生成整体审核状态
→ 进入通过、建议修改、退回修改或人工复核
→ 运营修改后重新审核
→ 保留机器、人工、内容和系统版本记录
```

## 6.3 功能需求

| 编号 | 优先级 | 功能需求 | 验收说明 |
|---|---:|---|---|
| FR-001 | P0 | 系统接收完整文案及必要业务上下文 | 缺少必填信息时不得启动正式审核 |
| FR-002 | P0 | 系统执行当前有效确定性规则 | 返回命中片段、规则ID、风险类型和规则版本 |
| FR-003 | P0 | 系统检索当前适用规则和案例 | 记录检索依据ID、版本和有效期 |
| FR-004 | P0 | 系统调用大模型完成语义风险识别 | 输出满足第九章能力契约 |
| FR-005 | P0 | 系统合并规则和模型的重复风险 | 相同风险只展示一次，不同来源证据均保留 |
| FR-006 | P0 | 系统根据产品规则生成整体审核结果 | 模型风险等级不能绕过产品路由规则 |
| FR-007 | P0 | 系统支持人工复核任务 | 人工可查看完整信息并完成复核、驳回、改判或升级 |
| FR-008 | P0 | 运营修改内容后生成新版本并重新审核 | 新版本不得沿用旧版本通过结果 |
| FR-009 | P0 | 系统记录完整审核链路和版本 | 能够复现当时使用的内容、规则、知识、模型和Prompt |
| FR-010 | P1 | 系统支持按风险类型和状态筛选任务 | 支持试点运营和人工处理 |
| FR-011 | P1 | 系统提供基础试点数据统计 | 至少支持结果分布、人工复核率和处理时长 |

## 6.4 规则适用范围

确定性规则优先处理：

- 禁用词与固定高风险短语；
- 必要声明是否缺失；
- 格式、字段、长度；
- 明确数值阈值；
- 可以清楚写成“如果……那么……”的业务条件。

关键词召回不等于最终结论。存在否定、引用或上下文歧义时，可将规则结果作为召回证据交给语义审核或人工。

## 6.5 RAG知识范围

知识库优先保存：

- 当前有效的渠道审核规范；
- 公司营销内容管理制度；
- 行业宣传要求；
- 规则解释与正反案例；
- 历史争议确认结论；
- 规则生效和失效时间；
- 不同产品类型的补充要求。

检索不到适用依据或发现依据冲突时，不允许模型根据常识编造规则并作出确定结论。

# 七、审核结果与业务处理流程

## 7.1 单条风险对象

每条正式风险结果至少包含：

| 字段 | 必填 | 说明 |
|---|---:|---|
| risk_id | 是 | 单次审核内唯一风险ID |
| risk_text | 是 | 风险原文或可定位的段落 |
| risk_type | 是 | 受控风险分类 |
| risk_level | 是 | low、medium、high |
| reason | 是 | 基于上下文和依据的判断原因 |
| references | 否 | 规则、知识或案例依据ID及版本 |
| detected_by | 是 | rule、llm或二者组合 |
| suggestion | 否 | 修改方向，不直接覆盖原文 |
| uncertainty | 否 | 信息不足、冲突或其他不确定原因 |
| need_human_review | 是 | 是否要求人工复核 |

## 7.2 结果合并规则

- 相同原文片段、相同风险类型的结果优先合并；
- 规则和模型证据同时保留，不覆盖原始结果；
- 不同原文、不同风险类型不得为了减少数量强行合并；
- 合并后的风险等级取产品路由规则定义的更严格结果；
- 依据冲突时不得自动选择其一，应标记冲突并转人工；
- 原始规则结果、模型结果和合并结果均需保留。

## 7.3 整体审核状态

| 状态 | 触发条件 | 系统动作 | 是否允许自动进入发布 |
|---|---|---|---:|
| 机器预审通过 | 未发现需阻断风险；链路完整；无依据冲突 | 保留机器预审标识，进入原有后续流程 | 否 |
| 建议修改 | 仅存在低风险或提示性问题 | 展示建议，允许运营修改或申请人工确认 | 否 |
| 退回修改 | 存在明确且可由运营修正的问题 | 阻止继续流转，要求修改后重新审核 | 否 |
| 转人工复核 | 高风险、不确定、信息不足、依据冲突、申诉或机器失败 | 创建人工任务，不自动放行 | 否 |

## 7.4 状态流转

```text
草稿
→ 待审核
→ 机器审核中
→ 机器预审通过 / 建议修改 / 退回修改 / 待人工复核
→ 修改后生成新版本并回到待审核
→ 人工复核通过 / 人工驳回 / 已升级
→ 审核完成
```

## 7.5 运营结果页要求

结果页至少展示：

- 当前内容版本和整体审核状态；
- 风险数量及等级分布；
- 原文中的风险位置；
- 每条风险的类型、原因、依据和修改方向；
- 是否必须修改或人工处理；
- 重新审核入口；
- 人工复核状态和最终结果；
- 结果生成时间及适用审核标准版本。

## 7.6 内容版本规则

- 首次提交生成内容版本V1；
- 任何实质文本修改生成新版本，不覆盖旧版本；
- 新版本重新执行完整Workflow；
- 旧版本机器和人工结果只用于追溯，不作为新版本结论；
- 仅元数据修正是否触发重审，由规则负责人定义；默认触发重审；
- 审核完成记录必须能关联到唯一内容版本。

## 7.7 示例

待审文案：

> 这款产品是目前最值得购买的理财产品，预计年化收益可达20%，收益稳定，完全不用担心亏损。

合并后的典型风险：

| 风险片段 | 风险类型 | 识别来源 | 预期动作 |
|---|---|---|---|
| 最值得购买 | 绝对化表达 | 规则＋大模型 | 退回修改 |
| 年化收益可达20% | 数据依据不足 | 大模型＋RAG | 补充依据或转人工 |
| 收益稳定 | 收益误导 | 大模型 | 退回修改或人工确认 |
| 完全不用担心亏损 | 收益保证与风险隐瞒 | 规则＋大模型＋RAG | 转人工复核 |

整体结果：高风险，禁止机器自动放行，转人工复核。

# 八、MVP与试点范围

## 8.1 MVP试点范围

| 维度 | MVP范围 | 待确认项 |
|---|---|---|
| 用户 | 一组内容运营、人工审核和规则负责人 | 具体团队、人数与权限 |
| 内容 | 一种主要纯文本营销内容 | 具体内容类型 |
| 渠道 | 一个规则相对稳定的渠道 | 渠道名称与规则版本 |
| 业务线 | 一个具备明确产品事实和审核依据的业务线 | 是否采用金融营销示例业务 |
| 风险类型 | 高频、重要、已有明确判断依据的风险 | 首批风险分类清单 |
| 试点周期 | 离线评测、影子运行、辅助审核三阶段 | 各阶段时长和样本量 |

## 8.2 MVP能力优先级

| 能力 | 优先级 | MVP |
|---|---:|---:|
| 内容与上下文提交 | P0 | 是 |
| 输入完整性校验 | P0 | 是 |
| 确定性规则检查 | P0 | 是 |
| RAG规则检索 | P0 | 是 |
| 大模型语义审核 | P0 | 是 |
| 结构化结果合并 | P0 | 是 |
| 四类结果分流 | P0 | 是 |
| 人工复核 | P0 | 是 |
| 修改后重新审核 | P0 | 是 |
| 内容、结果和系统版本记录 | P0 | 是 |
| 基础任务筛选与试点统计 | P1 | 是 |
| 图片、视频与音频审核 | P2 | 否 |
| 自动改写并覆盖原文 | P2 | 否 |
| 自动发布 | P2 | 否 |
| Agent自主审核 | P2 | 否 |
| 自动训练或规则自更新 | P2 | 否 |
| 完整规则编辑平台 | P2 | 否 |
| 复杂多级审批 | P2 | 否 |

## 8.3 试点阶段

### 阶段A：离线评测

目的：确认规则、大模型和组合方案具备基本识别能力。

准入条件：

- MVP风险分类和标准答案责任人已确认；
- 首版开发样本和验收样本已建立；
- 输入输出结构已稳定；
- 不影响真实业务。

退出条件：

- 完成主要风险类型分析；
- 关键高风险Bad Case有明确处理；
- 结构化输出和异常链路可用；
- 业务、规则、产品和算法同意进入影子运行。

### 阶段B：影子运行

目的：在不改变原有人工流程的情况下观察真实内容表现。

```text
真实内容 → 原人工流程
        ↘ 同时进入机器审核，仅用于对比
```

退出条件：

- 机器与人工差异完成分类；
- 真实内容上的高风险安全底线达标；
- 人工复核预估量可承受；
- 系统响应与失败率满足试点要求。

### 阶段C：辅助审核

目的：验证机器结果是否真正帮助人工提高效率。

```text
真实内容 → 机器预审 → 人工查看并确认/修改 → 最终结果
```

退出条件：

- 人工处理效率产生可确认改善；
- 人工能够理解并使用机器结果；
- 转人工和失败接管流程稳定；
- 业务同意扩大试点或进入下一阶段。

## 8.4 MVP完成定义

MVP完成不等于页面开发完成。需要同时满足：

- P0功能通过测试；
- 固定Workflow全链路可运行；
- 四类结果均有可验证处理路径；
- 人工复核和修改重审闭环可用；
- 版本记录能够支持复现；
- 验收集与上线门槛经过责任人确认；
- 关键风险和待确认项已达到阶段准入要求。

# 九、AI能力输入、处理、输出与边界

## 9.1 AI能力卡

**能力名称**：营销文案语义风险识别  
**能力目标**：识别必须结合上下文才能判断的营销表达风险，为运营修改和人工复核提供结构化依据。  
**处理对象**：MVP试点范围内的纯文本营销内容。  
**调用方式**：固定Workflow中的语义审核节点。  
**责任边界**：模型提供判断材料，不承担最终业务责任，不直接执行发布、删除、处罚或覆盖原文。

## 9.2 必要输入

| 输入组 | 字段示例 | 必要性 |
|---|---|---|
| 待审核内容 | 标题、正文、按钮文案、相邻上下文 | 必填 |
| 业务上下文 | 产品类型、渠道、目标用户、活动类型、内容用途 | 按风险类型定义必填项 |
| 产品事实 | 功能、适用范围、效果数据、价格、有效期、官方表述 | 涉及事实判断时必填 |
| 适用依据 | 规则ID、规则文本、解释、案例、版本与有效期 | 应尽可能提供 |
| 规则命中 | 风险片段、规则ID、初步风险类型 | 有命中时提供 |
| 输出约束 | 风险类型枚举、JSON Schema、禁止编造、失败定义 | 必填 |

不能只截取可疑句子让模型判断。涉及上下文风险时必须提供完整文案和必要相邻内容。

## 9.3 输入示例

```json
{
  "content": {
    "content_id": "C-20260820-001",
    "version": "V1",
    "title": "七天见证明显改变",
    "body": "已有用户反馈使用后效果明显，现在购买，你也一定能获得相同结果。"
  },
  "business_context": {
    "product_type": "健康管理服务",
    "channel": "信息流广告",
    "target_user": "普通消费者",
    "content_purpose": "拉新"
  },
  "product_facts": {
    "confirmed_effect": "实际效果因个人情况而异",
    "allowed_claim": "可作为日常健康管理辅助工具"
  },
  "applicable_rules": [
    {
      "rule_id": "R-023",
      "rule_version": "V3",
      "rule_text": "不得对无法保证的使用效果作出确定性承诺"
    }
  ],
  "output_schema_version": "1.0"
}
```

## 9.4 主要任务

- 识别隐含效果或收益承诺；
- 识别个别案例向所有用户泛化；
- 识别上下文组合后产生的误导；
- 识别绕开固定关键词的同义改写；
- 区分宣传性表达、否定说明和风险提示；
- 在信息不足、依据缺失或依据冲突时说明不确定性；
- 输出能够被产品流程稳定解析的结构化结果。

## 9.5 输出契约

```json
{
  "schema_version": "1.0",
  "overall_result": "risk_found",
  "risk_items": [
    {
      "risk_type": "效果承诺",
      "risk_level": "high",
      "risk_text": "你也一定能获得相同结果",
      "start_offset": 18,
      "end_offset": 30,
      "reason": "将个别用户反馈直接推导为所有用户均可获得的确定结果",
      "rule_references": ["R-023@V3"],
      "suggestion": "删除确定性承诺，并说明实际效果可能因个人情况而异",
      "uncertainty": null,
      "need_human_review": true
    }
  ],
  "missing_information": [],
  "conflicting_references": [],
  "model_status": "success"
}
```

### 枚举约束

| 字段 | 允许值 |
|---|---|
| overall_result | no_risk、risk_found、insufficient_information、uncertain、failed |
| risk_level | low、medium、high |
| model_status | success、partial、failed |
| risk_type | 使用规则负责人确认的受控风险类型枚举 |

## 9.6 输出校验

系统在使用模型结果前必须检查：

- JSON能否解析；
- 必填字段是否存在；
- 枚举值是否合法；
- 风险原文能否在输入内容中定位；
- 引用依据是否来自本次提供的依据集合；
- high风险是否明确要求人工；
- 模型状态与整体结果是否一致。

校验失败视为机器失败，不得等同于“未发现风险”。

## 9.7 风险等级与业务动作

| 模型结果 | 产品流程继续检查 | 默认动作 |
|---|---|---|
| 未发现语义风险 | 规则是否命中、链路是否完整 | 进入结果合并 |
| 低风险 | 业务是否允许运营自行处理 | 建议修改 |
| 中风险 | 规则要求与业务场景 | 退回修改或转人工 |
| 高风险 | 高风险路由规则 | 转人工 |
| 信息不足 | 缺少哪些必要信息 | 要求补充或转人工 |
| 依据冲突 | 冲突依据和版本 | 转人工 |
| 输出异常/调用失败 | 是否达到安全重试条件 | 有限重试，失败后转人工 |

## 9.8 修改建议要求

模型可以提供：

- 应删除或弱化的表达；
- 需要补充的限制条件或风险提示；
- 推荐的修改方向；
- 一条明确标注为“参考”的示例表达。

模型不得：

- 直接覆盖运营原文；
- 补充未经提供的产品事实；
- 修改后绕过重新审核；
- 将建议表达描述为已经合规通过。

## 9.9 异常处理

| 异常 | 系统处理 |
|---|---|
| 必要信息缺失 | 返回缺失字段，不启动确定结论 |
| 规则或依据冲突 | 展示冲突依据并转人工 |
| 无法稳定定位风险原文 | 允许段落级定位，降低自动处理程度 |
| 输出结构错误 | 按策略有限重试，仍失败则转人工 |
| 模型超时或服务异常 | 记录失败和版本，有限重试后转人工 |
| 不支持的内容类型 | 阻止进入MVP流程或转原人工流程 |

## 9.10 AI能力边界

模型不负责：

- 替代法务、规则负责人或业务责任人作出最终结论；
- 判断未提供证据的产品事实是否真实；
- 自动放行高风险、不确定或链路不完整的内容；
- 自动覆盖原文；
- 自动发布、删除或处罚；
- 根据单次人工改判自动更新规则；
- 在缺少依据时编造规则。

# 十、数据、规则与知识依赖

## 10.1 依赖清单

| 依赖 | 用途 | 最低要求 | 负责人 |
|---|---|---|---|
| 审核规则 | 确定检查标准和路由 | 规则ID、版本、适用范围、风险等级、有效期 | 规则负责人 |
| 规则解释与案例 | 支持语义判断和结果解释 | 已确认的正反案例与说明 | 规则负责人 |
| 产品事实 | 判断夸大、失实和效果承诺 | 来源可靠、更新及时、可追溯 | 业务负责人 |
| 历史审核记录 | 建立基线、评测集和回归集 | 内容、结果、原因、时间和版本尽可能完整 | 业务/数据负责人 |
| 人工复核结果 | 形成真实反馈和回归样本 | 记录改判原因、人员、时间 | 审核负责人 |
| 模型服务 | 语义审核 | 可用性、响应时间、版本标识和失败码 | 算法/研发 |
| Prompt与输出Schema | 约束任务和结构化输出 | 版本管理、变更记录、可回滚 | 算法/研发 |

## 10.2 规则版本要求

每条规则至少包含：

- rule_id；
- rule_version；
- 规则名称和说明；
- 适用业务、渠道、产品与内容类型；
- 风险类型和默认等级；
- 生效、失效时间；
- 责任人；
- 正反案例；
- 变更原因。

## 10.3 知识检索要求

- 只检索当前任务适用且在有效期内的依据；
- 返回依据ID、版本、来源和有效期；
- 优先使用已确认规则和案例；
- 无结果时明确返回“依据不足”；
- 多条依据冲突时同时返回，不由模型静默选择；
- 知识更新需要记录变更并触发必要回归。

## 10.4 最小审计记录

每次审核至少保存：

- task_id、content_id、content_version；
- 原始内容和业务上下文；
- 规则原始结果及规则版本；
- RAG检索结果及知识版本；
- 模型原始输出、模型版本、Prompt版本和Schema版本；
- 合并后的风险结果和整体状态；
- 人工最终结果、改判原因、人员和时间；
- 各节点开始、结束、失败和重试记录。

## 10.5 数据安全与权限

正式实施前需由安全和法务确认：

- 内容是否包含个人信息、商业秘密或受监管信息；
- 是否允许将内容发送给所选模型服务；
- 内容、日志和评测数据的保存期限；
- 不同角色可查看和导出的字段；
- 测试环境是否需要脱敏；
- 模型供应商是否保留或使用输入数据。

上述事项未确认前，不得将真实敏感内容直接用于外部模型测试。

# 十一、评测集来源与验收条件

## 11.1 评测对象

验收必须分别观察：

1. 确定性规则能力；
2. 大模型语义审核能力；
3. 规则、RAG和大模型组合后的整体审核结果；
4. 包含人工接管和修改重审的完整产品闭环。

不得用一个总准确率替代以上四个对象的评估。

## 11.2 首版评测集来源

- 当前MVP风险范围内的历史通过与驳回案例；
- 规则负责人确认的高风险典型案例；
- 历史争议、申诉和升级处理案例；
- 近期真实营销内容；
- 围绕关键规则构造的边界样本；
- 上线或影子运行中发现的重要Bad Case。

## 11.3 样本治理要求

- 历史标签需要抽样复核；
- 高风险、争议和人工改判样本需要逐条确认；
- 人工构造和模型生成样本必须经过人工确认；
- 标准答案需要记录确认人、确认时间和适用规则版本；
- 去除完全重复和无效样本；
- 补齐判断所需业务上下文；
- 开发样本和验收样本分开，避免围绕验收题调参。

## 11.4 评测数据字段

| 字段组 | 最低字段 |
|---|---|
| 样本信息 | case_id、文案、产品类型、渠道、用途、来源、内容版本 |
| 标准答案 | 是否有风险、类型、等级、原文、依据、预期动作、是否需人工 |
| 标签治理 | 确认人、确认时间、规则版本、争议记录 |
| 运行结果 | 规则结果、模型结果、整体结果、实际动作、错误类型 |
| 系统版本 | 规则、知识、模型、Prompt和Schema版本 |
| 运行信息 | 运行时间、响应时间、重试和失败状态 |

## 11.5 数据集划分

| 数据集 | 用途 | 使用约束 |
|---|---|---|
| 开发集 | 规则、Prompt和流程调试 | 产品、算法和研发可以反复查看 |
| 验收集 | 判断是否达到阶段上线条件 | 开发过程中不得逐题针对性调答案 |
| 回归集 | 防止重要错误再次出现 | 由高风险Bad Case和线上问题持续补充 |

## 11.6 验收指标与门槛

具体数值由业务基线、PoC结果和风险承受能力共同确定。数值确认前，以下门槛结构为强制要求。

| 编号 | 验收维度 | 门槛 | 责任人 |
|---|---|---|---|
| AC-01 | 高风险安全底线 | 待PoC后确认；必须单独设门槛 | 业务＋规则负责人 |
| AC-02 | 主要风险类型识别 | 按风险类型分别确认，不只看总体 | 规则＋算法负责人 |
| AC-03 | 混合方案增量 | 相对纯规则方案产生可确认有效增量 | 产品＋算法 |
| AC-04 | 结构化输出 | 解析、必填字段和枚举满足系统要求 | 研发＋算法 |
| AC-05 | 人工承载 | 转人工数量不超过试点团队承载上限 | 审核负责人 |
| AC-06 | 异常兜底 | 调用失败、信息不足、依据冲突均不默认放行 | 产品＋测试 |
| AC-07 | 修改重审 | 新版本必须重新执行完整审核 | 产品＋测试 |
| AC-08 | 可追溯性 | 任意结果可追溯到内容和系统版本 | 研发＋测试 |
| AC-09 | 试点效率 | 人工时间或单位处理量产生可确认改善 | 业务负责人 |

## 11.7 上线阻断条件

出现以下任一情况，当前版本不得进入下一阶段：

- 高风险样本未达到确认的安全底线；
- 机器失败可能被解释为审核通过；
- 人工接管任务缺失必要上下文或证据；
- 内容修改后可以复用旧审核通过结果；
- 结构化输出无法稳定解析；
- 规则、知识、模型或Prompt版本无法追溯；
- 转人工量超过业务承载能力且无降级方案；
- 数据安全或模型供应商合规问题未关闭。

## 11.8 回归触发条件

以下任一内容发生实质变化，至少重新运行回归集，并由产品和规则负责人判断是否需要完整验收：

- 规则内容、等级或适用范围；
- 知识库来源、切分或检索策略；
- 模型或模型参数；
- Prompt；
- 输出Schema；
- 结果合并和路由规则；
- 关键业务上下文或产品事实来源。

# 十二、人工复核与异常处理

## 12.1 人工复核触发条件

- 命中高风险确定性规则；
- 大模型识别到高风险语义问题；
- 判断信息不足；
- 规则、知识或模型依据冲突；
- 模型结果不确定；
- 模型无法稳定定位风险；
- 结构化输出校验失败且安全重试后仍失败；
- 规则、RAG或模型调用失败且重试后仍未恢复；
- 运营人员对机器结论发起申诉；
- 业务规则要求必须由责任人确认。

## 12.2 人工工作台信息

人工审核人员至少能够看到：

- 原始内容、当前版本和业务上下文；
- 产品事实和相关材料；
- 规则原始命中结果；
- RAG检索依据及版本；
- 模型原始输出；
- 合并后的风险列表；
- 转人工原因；
- 历史内容版本和处理记录；
- 系统版本与调用状态。

## 12.3 人工处理动作

| 动作 | 说明 | 必填记录 |
|---|---|---|
| 复核通过 | 人工确认内容可以进入后续流程 | 结论、人员、时间 |
| 驳回修改 | 存在需由运营修正的问题 | 风险、原因、修改要求 |
| 调整机器结果 | 修改风险类型、等级或处理动作 | 原机器结果、人工结果、改判原因 |
| 升级处理 | 需要规则、法务、业务或其他责任主体确认 | 升级对象、原因和上下文 |

## 12.4 最小追溯要求

- 机器原始结果和人工最终结果同时保留；
- 人工改判必须记录原因、人员和时间；
- 内容发生实质修改后生成新版本并重新审核；
- 审核完成后能够关联内容、规则、知识、模型、Prompt和Schema版本；
- 人工不得直接覆盖机器原始日志；
- 机器失败不得默认通过。

## 12.5 降级策略

| 故障 | 降级策略 |
|---|---|
| 大模型不可用 | 运行可用规则检查；整体状态转人工，不给出完整机器通过 |
| RAG不可用 | 不允许模型编造依据；涉及依据的任务转人工 |
| 规则服务不可用 | 暂停机器完整审核或转原人工流程 |
| 人工工作台不可用 | 暂停高风险任务流转，不自动放行 |
| 版本服务异常 | 停止生成正式审核结论，避免不可追溯结果 |

## 12.6 人工服务指标

以下指标由试点团队确认后补充：

- 人工复核任务优先级；
- 高风险任务响应SLA；
- 普通复核任务响应SLA；
- 单人日承载量；
- 升级处理时限；
- 超时任务处理方式。

# 十三、风险与待确认项

## 13.1 项目风险

| 编号 | 风险 | 影响 | 缓解措施 | 责任人 |
|---|---|---|---|---|
| R-01 | 业务基线不完整 | 无法判断效率收益 | 在PoC前补充近3个月基线 | 业务负责人 |
| R-02 | 历史标签质量不稳定 | 评测结论失真 | 抽样复核；高风险和争议逐条确认 | 规则负责人 |
| R-03 | 规则版本或适用范围不清 | 模型依据错误、结果难追溯 | 建立最小规则版本字段和责任人 | 规则负责人 |
| R-04 | 产品事实未结构化或过期 | 模型无法判断夸大和失实 | 确认事实来源、有效期和更新机制 | 业务负责人 |
| R-05 | 模型输出波动或结构错误 | 产品流程无法稳定使用 | Schema校验、有限重试、失败转人工 | 算法＋研发 |
| R-06 | 转人工率过高 | 没有产生效率价值 | 调整范围、阈值和风险分工 | 产品＋审核负责人 |
| R-07 | 人工过度依赖机器结果 | 可能放大机器偏差 | 明确人工责任、展示原文和依据、抽样质检 | 审核负责人 |
| R-08 | 知识检索召回错误或依据冲突 | 解释和结论失真 | 版本过滤、依据展示、冲突转人工 | 算法＋规则负责人 |
| R-09 | 敏感内容发送至不合适模型服务 | 数据与合规风险 | 安全评审、脱敏、供应商条款确认 | 安全/法务 |
| R-10 | 试点范围持续扩大 | 延期且无法验证核心假设 | 通过范围变更评审管理MVP | 产品负责人 |

## 13.3 范围变更规则

以下变更需要产品、业务、规则和技术负责人共同评审：

- 新增内容模态；

- 允许机器自动放行或执行外部动作；
- 取消人工复核；
- 引入Agent自主决定审核路径；
- 使用未经安全确认的新模型或外部数据源；
- 修改高风险等级和路由规则；
- 在验收前更换评测口径。
