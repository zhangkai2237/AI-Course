# FDE：产品经理在AI时代的全栈化生存

## 老师版完整讲义 v1.0

> 课程类型：第二阶段专题课  
> 面向学员：已经具备产品经理基础、完成过至少一个 AI 项目，希望提升个人构建能力或探索 FDE 方向的学员  
> 建议时长：180分钟，含两次10分钟休息  
> 更新日期：2026年10月29日

---

## 一、课程定位

这节课不把 FDE 当成一个突然流行的岗位名，也不从招聘要求开始逐条解释。

整节课讲一个与学员本人有关的故事：

> 我原来是一名产品经理。过去我的主要工作是理解需求、设计方案、协调设计和开发。进入 AI 时代以后，只会写需求和协调资源的价值正在被压缩。为了继续成长，我需要主动扩大自己的能力范围，把设计、前端、后端、AI 构建和运营验证逐步拿进来，从需求管理者重新变成产品构建者。FDE，是这种全栈化演进的一种职业形态。

本课的重点不是鼓励学员一个人长期承担五个人的工作，而是帮助学员获得一种新的能力：

> 在没有完整团队、资源不足、问题仍然模糊的时候，自己也能把一个 AI 产品从想法推进到可运行、可测试、可使用的第一版。

---

## 二、全课核心结论

教师可以在开场写下这三句话，并在结尾重新回看：

```text
AI正在压缩纯协调型产品经理的价值。

AI也在降低产品经理跨越设计、开发和运营边界的成本。

产品经理的下一次进化，是从需求管理者走向全栈产品构建者。
```

全课不主张：

- 所有产品经理都必须转行做程序员；
- 产品经理可以完全取代专业设计师和工程师；
- 一个人长期承担所有岗位是合理的组织方式；
- 学会几个 AI 编程工具就已经成为 FDE；
- 未来只剩下全栈人才，不再需要专业分工。

全课真正主张的是：

> 产品经理应当获得相邻职能的第一版独立完成能力。自己做过完整闭环，才会拥有更强的判断、协作和领导能力。

---

## 三、教学目标

完成本课后，学员应当能够：

1. 解释为什么 AI 会压缩纯需求传递和资源协调型产品岗位的价值；
2. 理解“扩大 Scope”与“无限增加工作量”的区别；
3. 说清产品经理可以逐步拿进来的设计、前端、后端、AI 和运营能力；
4. 理解 FDE 与传统产品经理、全栈工程师、售前和项目经理的区别；
5. 判断自己当前距离 FDE 型人才还缺少哪些关键能力；
6. 制定一条从“会定义产品”到“能独立做出产品”的学习路径；
7. 选择一个适合自己的全栈 AI 项目，并明确第一版交付标准。

# 开场：如果AI能写需求、画原型和写代码，产品经理还剩下什么（00—10分钟）

## 1. 开场提问

教师先不要解释 FDE，直接向学员提问：

> 如果 AI 已经可以帮我们整理访谈、生成 PRD、画页面、写前端、写后端、接模型、做数据分析，那么产品经理未来最不可替代的部分到底是什么？

让学员自由回答2—3分钟。

常见答案可能包括：

- 更懂用户；
- 更懂业务；
- 会判断方向；
- 会沟通和协调；
- 会提出好问题；
- 会承担结果；
- 会创新。

教师不要急着否定，而是继续追问：

> 如果你判断出了一个好方向，但没有设计和开发资源，你能不能在一周内把第一版做出来？

> 如果你做出了第一版，但不会部署、不会找用户、不会看运行结果，这个判断能不能变成真实价值？

## 2. 教师开场讲述

过去，产品经理的核心能力之一，是通过组织协作放大自己的判断。我们定义问题、设计方案，再让专业团队分别完成设计、前端、后端、测试和运营。

但这个模式有一个前提：公司愿意给你完整资源，而且资源能够及时配合。

现实中，很多产品经理会陷入一种状态：

```text
有想法
→ 写需求
→ 等设计
→ 等开发排期
→ 等测试
→ 等运营准备
→ 三个月后才能知道最初判断是否成立
```

AI带来的变化，不只是把某一步做得更快。它让一个产品经理第一次有机会跨过多个专业边界，直接把自己的判断变成一个可运行的产品。

所以今天我们讨论的不是“AI会不会替代产品经理”，而是另一个问题：

> 产品经理能不能借助AI，扩大自己的生产能力，重新成为一个能够亲手构建产品的人？

## 3. 开场板书

```text
以前：我提出方案，让团队完成

现在：我提出方案，也能先把第一版做出来

未来：我既能独立完成0—1，也能带专业团队完成1—100
```

# 第一节：产品经理原来的价值正在发生什么变化（10—35分钟）

## 1. 传统产品经理依赖什么产生价值（10—18分钟）

教师画出传统分工：

```text
业务 / 用户
    ↓
产品经理：理解问题、定义需求、设计流程、协调资源
    ↓
设计师：页面与交互
    ↓
前端：用户界面
    ↓
后端：数据、接口与业务逻辑
    ↓
测试：检查质量
    ↓
运营：找到用户、推动使用、收集反馈
```

传统产品经理的价值主要来自三类能力：

1. 信息整合：把业务、用户和技术信息放在一起；
2. 产品判断：决定做什么、不做什么和先做什么；
3. 组织推动：让不同角色共同完成一个结果。

这些能力今天依然重要，但其中一部分工作正在快速被 AI 辅助：

- 访谈内容整理；
- 竞品信息归纳；
- 用户故事和 PRD 初稿；
- 流程图与页面草稿；
- 数据查询与基础分析；
- 测试用例整理；
- 项目周报和沟通材料。

## 2. 真正危险的不是AI会写PRD（18—25分钟）

教师讲述：

如果一个产品经理的主要价值就是把别人的话整理成文档，那么 AI 的确会明显压缩这部分价值。

但产品经理真正面临的风险不是“AI把PRD写得更快”，而是组织可能开始追问：

- 为什么这个问题还需要这么多人才能验证？
- 为什么做一个简单原型仍要等两周？
- 为什么产品经理不能自己验证模型是否可用？
- 为什么上线以后没有人使用，却只能归因给运营？
- 为什么每一步都需要等待另一个角色？

因此，未来产品经理的竞争不只发生在“谁的文档写得好”，而会发生在：

> 谁能用更短的链路，把一个不确定想法变成可以被检验的真实产品。

## 3. 两种产品经理（25—32分钟）

教师展示对比：

| 情境 | 需求管理型产品经理 | 产品构建型产品经理 |
| --- | --- | --- |
| 有一个新想法 | 先写需求和申请资源 | 当天做出流程与页面草稿 |
| 不确定模型能否实现 | 询问算法团队 | 自己调用模型完成小测试 |
| 没有开发排期 | 等待或降低优先级 | 先搭建可运行的验证版本 |
| 用户不愿意使用 | 交给运营分析 | 直接观察使用过程并修改产品 |
| 项目失败 | 解释每个团队的问题 | 回看自己的判断与完整链路 |

教师强调：这不是道德判断。需求管理型产品经理在成熟大型组织中仍然可能非常有价值。但如果学员希望进入创新业务、创业公司、AI原生团队或FDE方向，产品构建能力会越来越重要。

## 4. 本节收束（32—35分钟）

```text
只会协调资源的人，必须依赖组织才能产生结果。

能够亲自构建的人，即使资源不足，也可以先验证自己的判断。
```

# 第二节：AI为什么让产品经理可以扩大Scope（35—60分钟）

## 1. AI降低了跨职能的启动成本（35—43分钟）

过去，产品经理不是不想自己做，而是跨越每个专业都需要较高成本：

- 设计工具需要训练；
- 前端需要掌握HTML、CSS、JavaScript和框架；
- 后端需要理解服务器、数据库和接口；
- AI应用需要理解模型、检索和评测；
- 运营需要持续生产内容、分析数据和维护用户。

AI没有消灭这些专业知识，但显著降低了从零到第一版的门槛。

今天，一个产品经理可以通过自然语言和AI工具：

- 快速探索多个页面方案；
- 生成和修改前后端代码；
- 调用模型与第三方接口；
- 搭建数据库和基础权限；
- 生成测试数据和分析脚本；
- 自动处理重复运营任务；
- 快速根据用户反馈修改系统。

## 2. Scope扩展不等于工作无限增加（43—50分钟）

教师重点纠偏：

“把设计、前端、后端和运营拿进来”很容易被理解成，公司少招四个人，让产品经理承担五个人的工作。

本课不是这个意思。

扩大Scope的目标是获得四种自主能力：

```text
不再等待设计，才能看见产品
不再等待开发，才能验证方案
不再等待算法，才能判断AI能力
不再等待运营，才能知道有没有人用
```

产品经理需要拿进来的，是相邻职能的“第一版独立完成能力”，而不是所有专业工作的最高水平。

## 3. “第一版能力”与“专业能力”的边界（50—56分钟）

| 方向 | 产品经理要拿进来的能力 | 不需要立刻达到的水平 |
| --- | --- | --- |
| 设计 | 能独立完成信息架构、核心交互和可用原型 | 完整品牌系统、复杂视觉表现 |
| 前端 | 能实现核心页面、状态和交互 | 大型前端工程与极致性能优化 |
| 后端 | 能打通数据、接口、模型和基本权限 | 高并发、复杂分布式架构 |
| AI | 能选择模型、搭建流程、测试结果和处理失败 | 训练基础模型与研究新算法 |
| 运营 | 能找到首批用户、观察使用、收集反馈和完成迭代 | 大规模增长与完整运营体系 |

## 4. 产品经理的三次进化（56—60分钟）

```text
第一阶段：我能说明白
会分析、会写需求、会设计方案

第二阶段：我能自己做出来
会设计、会编程、会接AI、会部署、会验证

第三阶段：我能带着专业团队做大
知道什么自己做、什么交给专家，以及怎样建立长期产品能力
```

教师收口：

> 全栈不是拒绝分工。全栈是因为自己完成过闭环，所以更清楚每个专业为什么存在，也更有能力与专业团队协作。

# 第三节：把设计、前端、后端和运营逐步拿进来（70—110分钟）

## 1. 第一层：把设计拿进来（70—78分钟）

### 产品经理需要做到什么

- 把业务流程变成页面结构；
- 设计用户从进入到完成任务的主要路径；
- 展示正常、加载、空状态、失败和人工接管；
- 建立信息层级；
- 制作可以点击的交互原型；
- 根据用户观察修改交互。

### AI可以怎样帮助

- 根据流程生成多个页面草案；
- 快速比较不同交互方案；
- 生成组件和状态；
- 将线框图转成真实页面；
- 根据反馈批量修改文案与布局。

### 学员最低交付标准

不是一张漂亮首页，而是至少三张能够说明完整任务的页面：

```text
任务入口
→ 核心处理页面
→ 结果与下一步
```

并至少包含一个异常状态。

## 2. 第二层：把前端拿进来（78—86分钟）

### 产品经理需要做到什么

- 理解页面、组件、状态与事件；
- 能修改HTML、CSS和基础JavaScript或前端框架代码；
- 实现表单、列表、弹窗、上传和结果展示；
- 调用后端或模型接口；
- 处理加载、失败、重试和空状态；
- 使用AI编程工具定位和修改问题。

### 最低交付标准

页面不是静态图，而是可以：

- 输入真实内容；
- 点击执行任务；
- 展示运行状态；
- 返回真实结果；
- 修改后重新运行。

教师强调：复制AI生成的代码不代表掌握前端。学员至少要能解释页面状态、接口调用位置和发生错误时怎样排查。

## 3. 第三层：把后端与AI构建拿进来（86—98分钟）

### 产品经理需要掌握的后端基础

- API请求与响应；
- 数据库中的基本数据对象；
- 文件上传和存储；
- 用户、角色和基础权限；
- 任务状态；
- 日志与错误信息；
- 开发环境与生产环境的区别。

### 产品经理需要掌握的AI应用能力

- 模型API调用；
- Prompt与结构化输出；
- RAG与企业资料检索；
- Workflow与分支；
- 工具调用；
- 人工确认节点；
- 测试集、坏案例与回归；
- 成本、时延和失败处理。

### 最低交付标准

学员应该能够独立画出并解释：

```text
用户输入
→ 前端提交
→ 后端创建任务
→ 调用模型 / 规则 / 资料
→ 校验输出
→ 保存结果
→ 返回页面
→ 用户处理或转人工
```

## 4. 第四层：把运营验证拿进来（98—106分钟）

产品经理做出产品以后，还要亲自完成第一轮采用验证。

需要做到：

- 找到5—10名目标用户；
- 设计一条明确试用任务；
- 观察用户是否能独立完成；
- 记录用户中断和困惑的位置；
- 区分产品问题、模型问题和材料问题；
- 统计完成率、使用时长、人工修改和重复使用；
- 根据结果修改产品，而不是只收集满意度。

教师强调：

> 上线只是技术事件，采用才是产品事件。

## 5. 五层能力连起来（106—110分钟）

```text
业务：找到值得解决的问题
  ↓
产品：限定范围并设计流程
  ↓
设计：让用户看见并操作方案
  ↓
技术：让方案真实运行
  ↓
运营：确认用户是否采用并产生结果
```

这五层能够独立跑通，就形成了全栈产品构建能力。

# 第四节：FDE是一种怎样的全栈形态（110—135分钟）

## 1. 从全栈产品经理进入FDE（110—116分钟）

教师讲述：

如果一个产品经理不仅能定义和构建自己的产品，还能进入一家客户企业，在对方的业务、系统、数据和组织条件下完成同样的闭环，他就开始接近FDE。

本课给FDE的定义是：

> FDE是以工程能力为底座，进入客户现场，独立完成业务发现、产品设计、系统构建、生产部署和采用验证的全栈落地者。

更口语的表达是：

> 客户提出一个模糊问题，FDE自己调研、自己定方案、自己做产品、自己写关键代码、自己测试、自己部署，再推动客户真正使用。

## 2. 三个单词分别意味着什么（116—122分钟）

### Forward

进入客户现场，不等待一份已经写好的需求。

面对的往往是：

- 问题没有定义；
- 工作流不透明；
- 规则存在于人的经验中；
- 数据和系统条件不明确；
- 不同角色对成功的理解不同。

### Deployed

不止完成Demo，而是继续处理：

- 企业接口与权限；
- 测试与回归；
- 日志与监控；
- 失败和人工接管；
- 业务人员采用；
- 客户团队接管。

### Engineer

不能只负责协调。必须具备直接构建和排查系统的能力。

## 3. FDE与其他角色的区别（122—128分钟）

| 角色 | 主要价值 | 是否必须亲自构建 |
| --- | --- | --- |
| 产品经理 | 定义产品与优先级 | 不一定 |
| 项目经理 | 范围、进度、资源和风险管理 | 通常不需要 |
| 售前 / 解决方案顾问 | 解释能力、设计方案、支持商业推进 | 部分岗位需要 |
| 全栈工程师 | 完成前端、后端和系统实现 | 需要 |
| FDE | 从模糊客户问题一直负责到生产采用 | 需要 |

教师可以用一句话区别项目经理和FDE：

```text
项目经理：让正确的人把不同工作完成。

FDE：自己有能力把关键工作直接完成。
```

## 4. FDE不是永久单打独斗（128—132分钟）

“都是自己干”主要发生在0—1阶段。

### 0—1阶段

```text
调研 → 范围 → 原型 → 开发 → 测试 → 部署 → 试用
```

FDE可能亲自完成大部分关键工作。

### 1—10阶段

- 产品团队接管标准功能；
- 平台团队提高稳定性；
- 专业工程团队重构系统；
- 实施和客户成功团队扩大部署；
- 客户团队承担日常使用与维护。

FDE重新进入下一个高不确定问题。

## 5. 行业岗位标准提醒（132—135分钟）

教师必须诚实说明：

FDE不是给产品经理换一个更高级的名字。当前典型FDE岗位普遍强调真实工程能力、客户协作和生产系统交付。

产品经理可以沿着全栈构建方向向FDE靠近，但在正式投递FDE之前，需要达到能够独立开发和调试AI应用的工程门槛。

> 如果明天让你独立为一家企业完成一个AI应用，你会最先卡在哪里？

# 第五节：从产品经理走向FDE的能力路线（145—165分钟）

## 1. 八项能力自测（145—151分钟）

让学员按0—3分自评：

- 0分：不了解；
- 1分：学习或跟做过；
- 2分：可以独立完成小项目；
- 3分：在真实或高仿真项目中完整完成过。

| 能力 | 自测问题 |
| --- | --- |
| 业务发现 | 能否通过访谈重新定义客户问题 |
| 产品范围 | 能否把大需求收缩成可交付的第一版 |
| 交互设计 | 能否独立完成完整任务原型 |
| 前端构建 | 能否实现可操作页面并调用真实接口 |
| 后端与集成 | 能否处理数据、任务、权限和外部接口 |
| AI应用 | 能否搭建模型、检索、工具和人工节点 |
| 测试与部署 | 能否建立测试并部署一个可访问版本 |
| 用户采用 | 能否找到用户、观察使用并推动迭代 |

教师强调：不要追求所有项平均。先找到最阻碍自己完成闭环的短板。

## 2. 三类学员的不同路径（151—156分钟）

### 产品能力强、代码较弱

优先顺序：

```text
前端基础
→ 模型API
→ 简单后端与数据库
→ 部署
→ 企业系统集成
```

### 开发能力强、业务较弱

优先顺序：

```text
用户访谈
→ 业务流程还原
→ 问题定义
→ MVP取舍
→ 采用验证
```

### 运营或行业背景强

优先顺序：

```text
产品流程
→ 交互原型
→ AI工作流
→ AI辅助编程
→ 完整应用构建
```

## 3. 90天行动路线（156—163分钟）

### 第1—30天：完成一个单点AI应用

要求：

- 有真实输入；
- 有结构化输出；
- 有可以操作的页面；
- 有模型API；
- 有异常处理；
- 有10—20条测试样本；
- 部署为可访问版本。

选题示例：

- 客服会话质检器；
- 合同条款初步检查器；
- RFP要求提取器；
- 用户反馈归类助手。

### 第31—60天：完成一个企业工作流应用

要求：

- 至少两个业务角色；
- 接入知识库或模拟业务接口；
- 包含规则、模型和人工节点；
- 包含状态、权限和失败处理；
- 保留运行记录；
- 展示一次修改和回归。

### 第61—90天：完成一次前线部署型项目

要求完整记录：

```text
客户最初提出了什么
→ 通过调研发现的真实问题是什么
→ 为什么收缩项目范围
→ 第一版怎样构建
→ 测试暴露了什么问题
→ 怎样修改
→ 哪些部分属于客户特例
→ 哪些能力可以沉淀为通用模块
```

## 4. 什么时候可以开始投递（163—165分钟）

不是所有技术都学完以后才可以投递。至少应能够：

- 独立讲清一个企业问题；
- 现场拆解业务流程；
- 判断AI是否适合介入；
- 写出并解释完整技术链路；
- 独立构建可运行原型；
- 解释测试结果和失败案例；
- 说明怎样接入企业系统；
- 展示一次范围收缩或方案取舍；
- 区分客户定制与通用能力；
- 面对代码、数据、部署与业务结果的追问。

# 第六节：用一个客户项目跑通全栈闭环（165—175分钟）

## 1. 客户最初提出的需求

> 我们想做一个AI自动写标书系统，希望上传招标文件后直接生成整本标书。

教师提问：如果你是传统产品经理，你会怎么做？

可能答案：

- 整理需求；
- 画系统架构；
- 设计功能模块；
- 找算法团队确认；
- 安排开发排期。

## 2. FDE型产品经理怎样开始

第一步不是写PRD，而是进入现场追问：

- 谁负责阅读招标文件？
- 最耗时的环节是什么？
- 丢标最常见的原因是什么？
- 哪些要求一旦遗漏就无法参与？
- 企业资质和产品资料放在哪里？
- 哪些内容可以自动生成？
- 谁承担最终确认责任？

## 3. 发现真实问题

调研后可能发现：

- 真正昂贵的不是写作速度，而是强制要求容易遗漏；
- 同一要求会出现在多个章节；
- 资质、案例和产品材料分散；
- 内容与评分标准无法逐项对应；
- 最后阶段才发现某个资格不满足。

## 4. 收缩第一版

不先做整本标书生成，而是：

```text
上传招标文件
→ 提取强制要求和否决项
→ 保留原文位置
→ 生成要求与响应矩阵
→ 匹配企业现有材料
→ 标记材料缺口
→ 交投标负责人确认
```

## 5. 一个人怎样把第一版做出来

| 工作 | FDE型产品经理亲自完成的第一版 |
| --- | --- |
| 业务 | 访谈投标负责人，还原人工流程 |
| 产品 | 确定要求提取与响应矩阵的MVP |
| 设计 | 设计上传、解析、矩阵和详情四个页面 |
| 前端 | 实现文件上传、任务状态和矩阵交互 |
| 后端 | 完成文档处理、任务保存和结果接口 |
| AI | 完成切分、要求抽取、分类、去重和材料匹配 |
| 测试 | 用多份招标文件检查漏项、误报与来源位置 |
| 运营 | 让投标人员使用，记录人工修改与完成时间 |

## 6. 案例收束

这个案例不是要证明一个人可以长期维护完整招投标平台，而是证明：

> 在项目最不确定的时候，一个产品经理可以借助AI跨越多个职能边界，自己完成足够真实的第一版，用运行结果决定下一步。

# 全课收束与作业（175—180分钟）

## 1. 回看开场问题

开场我们问：如果AI可以写需求、画原型和写代码，产品经理还剩下什么？

现在的回答不是“产品经理只剩下判断”，而是：

> 产品经理既要保留判断能力，也要获得把判断直接变成产品的能力。

## 2. 最终板书

```text
传统产品经理
定义需求 + 协调资源

AI全栈产品经理
业务 + 产品 + 设计 + 技术 + 运营验证

FDE型人才
进入客户现场，把模糊问题亲手变成生产系统
```

## 3. 教师结束语

AI时代对产品经理最大的威胁，不是AI能够生成一份PRD，而是有人能够用AI更快地完成从问题到产品的整条链路。

但这同样是产品经理重新发扬光大的机会。

产品经理本来就站在业务、用户和技术的交叉点。过去我们受限于专业工具和开发成本，只能通过协调团队实现产品。现在AI正在降低每一道边界的跨越成本。

不要守住原来的岗位边界。先把设计拿进来，再把前端拿进来，再理解后端、模型、部署和运营验证。不是为了一个人永远干所有事情，而是为了不再把自己的创造力交给资源和排期决定。

最终，我们要从“我能把产品说明白”，走向“我能把产品做出来”，再走向“我能进入真实业务，把它变成持续运行的结果”。

## 4. 课后作业

### 必做一：能力边界盘点

对八项能力进行0—3分自评，并回答：

1. 我当前最强的两项能力是什么；
2. 最阻碍我完成独立闭环的能力是什么；
3. 接下来30天只补一项，我应该补什么；
4. 我准备通过什么具体项目验证这项能力。

### 必做二：选择一个全栈AI项目

项目需要满足：

- 有明确用户和真实任务；
- 一个人可以在30天内完成第一版；
- 需要至少一个模型能力；
- 有可操作页面；
- 有数据保存或业务接口；
- 有测试样本；
- 能找到至少3名目标用户试用。

提交内容：

```text
项目名称
目标用户
当前工作方式
最值得解决的问题
第一版范围
主要页面
技术链路
测试方法
用户来源
30天计划
```

### 选做：制作第一天可运行版本

不追求完整，只需要完成：

```text
一个输入
→ 一次真实模型调用
→ 一个结构化结果
→ 一个可以打开的页面
```

# 教师备课补充

## 一、容易讲偏的地方

### 1. 不要讲成岗位追热点

FDE只是全栈化故事的一个职业出口，课程主线始终是产品经理能力边界的变化。

### 2. 不要贬低专业分工

设计师、工程师、测试和运营依然有不可替代的专业深度。本课强调的是第一版独立完成能力，不是所有岗位都不再需要。

### 3. 不要把过度工作包装成成长

如果公司只是减少人员，让产品经理长期承担多个岗位，却不给工具、时间、权限和收益，这不属于本课倡导的全栈成长。

### 4. 不要降低FDE的工程门槛

学员能够使用AI编程工具完成Demo，只能说明开始具备构建能力。正式FDE岗位通常仍要求真实代码、系统集成、部署和生产排障能力。

### 5. 不要只讲工具清单

工具会快速变化。课程重点是能力闭环：能否把问题变成运行结果，而不是使用了多少AI工具。

## 二、建议课堂互动

### 互动一：我的工作中有多少是需求转述

让学员写下最近一周完成的工作，分别标记：

- 只有我能判断的；
- AI可以辅助的；
- 我可以借助AI独立完成的；
- 必须由专业团队完成的。

### 互动二：我最想拿进来的一个能力

学员在设计、前端、后端、AI构建和运营验证中选一项，说明：

- 为什么是它；
- 它解决了当前什么依赖；
- 怎样在30天内完成一次真实交付。

### 互动三：这个需求应该先做什么

使用智能标书案例，让学员判断第一版应该做整本生成、要求抽取、企业材料库还是协作管理，并说明取舍。
