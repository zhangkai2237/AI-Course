# 模块五：先在纸面上设计一个可控的 Agent

## 一、模块定位

- 建议时长：18 分钟
- 对应总课时：70—88 分钟
- 模块作用：把前面的概念转化为一张可以评审的产品设计稿
- 教学方式：个人填写、小组互查、老师讲评

这一部分不要求学员立即进入 Coze，也不要求零基础学员编写 API 文档。重点是让学员先回答清楚：Agent 要完成什么目标、可以使用什么工具、哪些事情不能自己决定。

## 二、教学目标

完成本模块后，学员应当能够：

1. 用一句话写清 Agent 的服务对象和任务目标；
2. 为 Agent 配置必要而非越多越好的工具；
3. 区分普通输入、工具返回结果和最终输出；
4. 写出确认点、异常处理和停止条件；
5. 初步判断一个方案是否具备“受控执行”能力。

## 三、练习案例

### 案例背景

某本地生活平台希望为连锁餐饮商家提供一个“门店经营助手”。

店长可以向助手提问：

> 最近门店新客下降了，帮我看看可能是什么原因，并给一个活动建议。

系统已经准备了三个能力：

1. `query_store_metrics`：查询门店经营指标，并返回已经由数据规则判断好的异常标签和依据；
2. `search_activity_rules`：查询平台活动规则、门槛和限制；
3. `create_campaign_draft`：根据确认过的信息生成活动草稿，但不能直接发布。

### 为什么使用这个案例

这个案例同时具备：

- 用户目标明确，但执行路径不能完全提前写死；
- 需要先查数据，再决定是否查规则；
- 存在“建议”和“创建草稿”两个不同风险等级；
- 可以演示缺少信息、工具失败、权限不足和人工确认。

## 四、练习纸结构

老师向学员发放一张半成品设计表，学员补充以下内容：

| 设计项 | 学员需要填写的内容 |
|---|---|
| 服务对象 | 谁会使用这个 Agent |
| 任务目标 | Agent 最终要帮助用户完成什么 |
| 必要输入 | 最少需要哪些信息才能开始 |
| 可用工具 | 每个工具解决什么问题 |
| 工具顺序 | 哪些步骤固定，哪些由 Agent 判断 |
| 最终输出 | 用户最终会看到什么 |
| 确认点 | 哪些动作必须由用户确认 |
| 异常处理 | 缺参数、查不到、工具失败时怎么办 |
| 停止条件 | 什么情况下任务应该结束 |
| 人工接管 | 什么情况下必须交给人工 |

## 五、课堂流程

### 第一步：个人填写，8 分钟

老师提醒学员：

- 不需要写技术实现；
- 不要给 Agent 添加案例之外的新工具；
- 工具数量不是越多越好；
- 重点写清楚“何时调用”和“何时不能调用”。

### 第二步：两人互查，4 分钟

两人交换设计表，使用下面四个问题检查：

1. Agent 是否知道任务完成的标准？
2. 每个工具的用途是否清晰、是否存在重复？
3. 高风险动作前是否设置了确认？
4. 工具失败后是否仍然有可执行的处理方式？

### 第三步：老师公布参考设计，6 分钟

## 六、老师参考答案

### 1. 服务对象

连锁餐饮门店的店长或区域运营。

### 2. 任务目标

基于指定门店和指定时间范围的经营数据，识别已经被规则系统标记的主要异常，结合平台活动规则生成可供店长确认的改善建议；如用户同意，再创建活动草稿。

### 3. 必要输入

- 门店 ID；
- 分析时间范围；
- 用户希望关注的问题，例如新客、复购或交易额。

如果缺少门店或时间范围，Agent 应先追问，不能自行猜测。

### 4. 工具及用途

| 工具 | 用途 | 不负责什么 |
|---|---|---|
| `query_store_metrics` | 查询门店指标、异常标签和规则依据 | 不负责决定活动方案 |
| `search_activity_rules` | 查询可用活动规则及限制 | 不负责判断门店数据是否异常 |
| `create_campaign_draft` | 使用已确认的活动参数创建草稿 | 不直接发布活动；未确认时不得执行 |

### 5. 可能的执行路径

正常路径：

> 补全门店与时间 → 查询经营数据 → 读取异常标签 → 查询相关活动规则 → 输出建议 → 用户确认 → 创建草稿 → 返回草稿编号

动态路径：

- 信息不完整：先追问，不调用工具；
- 数据未发现明显异常：直接解释结果，不必查询活动规则；
- 规则不适用：说明限制，不创建草稿；
- 用户只要分析：输出建议后结束；
- 用户要求直接发布：说明当前没有发布权限，只能创建草稿。

### 6. 确认点

分析和读取规则可以直接进行；创建活动草稿前必须让用户确认：

- 活动目标；
- 人群范围；
- 优惠力度；
- 活动时间；
- 预计预算；
- 当前动作只是创建草稿，不是发布。

### 7. 异常与停止

- 缺少必要信息：追问；
- 门店不存在：提示核对门店；
- 工具超时：说明失败，可重试或稍后再试；
- 规则冲突：停止创建，提示人工核对；
- 草稿创建成功：返回草稿编号并结束；
- 用户取消：立即结束。

## 七、讲解重点

老师要强调：

> 一张合格的 Agent 设计表，不是只写“它会调用哪些工具”，而是同时写清目标、工具、边界、异常和停止条件。

如果学员只画出一条成功路径，要追问：

- 用户少说一个参数怎么办？
- 工具没有返回结果怎么办？
- 用户要求越权操作怎么办？
- Agent 什么时候知道自己已经完成任务？

## 八、常见误区

### 误区一：把 Prompt 当作完整方案

Prompt 只能告诉模型如何理解和表达，无法替代工具权限、执行结果和系统状态。

### 误区二：把所有步骤都交给 Agent 决定

固定规则、权限校验和高风险确认应由系统控制，不应只依赖模型“自觉”。

### 误区三：只设计成功路径

真实产品中，缺参数、超时、查不到和用户反悔都很常见。

## 九、承上启下

完成纸面设计后，下一模块专门讨论其中最容易被忽略的部分：

> Agent 做错、工具失败或用户要求越权时，系统如何停止、解释和转交人工？
