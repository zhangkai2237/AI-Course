# 01 开场与承接（0-8分钟）

## 教学目标

让学员看见本课与第03课的直接关系：上一课已经解决“问题走哪条路”，但`RULE`分支仍没有一套可维护、可验证的知识获取机制。

## 开场回放

先展示上一课的四路Workflow：

```text
用户问题
  ↓
意图分类
  ├─ RULE → 固定规则卡
  ├─ DATA → 提示查询业务系统
  ├─ COMPLAINT → 转人工
  └─ OTHER → 追问澄清
```

老师提问：

> 如果活动规则从一页变成100份文档，每周都有人更新，而且不同商家看到的规则还不一样，继续把规则全文写在Prompt里行不行？

让学员先回答，再归纳三个问题：

1. **放不下**：规则越来越多，上下文会膨胀；
2. **改不动**：规则变更后，需要到多个Prompt或流程节点中修改；
3. **查不清**：回答出错时，很难知道依据来自哪份文档、哪个版本。

因此，本课不是重新搭一个新产品，而是升级已有产品：

```text
RULE → 检索商家规则知识库 → 基于依据回答
```

## 本课结束时要做到什么

学员应能：

- 用产品语言说明RAG在解决什么问题；
- 画出离线建库和在线问答两条链路；
- 判断哪些信息能进知识库，哪些必须查询业务系统；
- 设计知识来源、版本、权限和更新规则；
- 在平台中导入教学文档并接入`RULE`分支；
- 用5条问题区分检索失败和生成失败。

## 必须提前说清的三句话

1. RAG不是“上传文件后，大模型自动学会了”；
2. RAG不是数据库，不能拿来查询实时订单和经营数据；
3. RAG能减少无依据回答，但不能消除幻觉。

## 与第0课案例的差别

第0课的销售拜访记录助手用于第一次识别AI机会；本课案例用于学习“企业知识如何进入AI产品”。两者教学目标不同，不重复做场景价值分析。
