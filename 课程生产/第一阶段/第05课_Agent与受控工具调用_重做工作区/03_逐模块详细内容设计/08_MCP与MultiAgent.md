# 模块八：MCP 与 Multi-Agent 延伸

## 一、模块定位

- 建议时长：10 分钟
- 对应总课时：126—136 分钟
- 教学目标：知道它们解决什么问题，避免概念混淆
- 本课要求：不安装 MCP Server，不搭建 Multi-Agent

这部分只放在课程结尾作为能力地图。学员应先掌握单 Agent、工具调用和控制边界，再理解更复杂的连接和协作方式。

## 二、Function Calling 与 MCP 的区别

### Function Calling 解决什么问题

Function Calling 让模型用结构化方式表达：

- 想调用哪个工具；
- 要传入哪些参数。

应用程序接收调用请求，真正执行工具，再把结果返回给模型。

### MCP 解决什么问题

MCP 是一种标准化协议，用于让 AI 应用以相对统一的方式连接外部工具、资源和上下文。

可以用“接口标准”来理解：

- 没有统一标准时，每个系统都要分别适配；
- 有标准后，不同客户端和能力提供方可以按协议连接；
- MCP 负责连接和能力暴露，不负责替 Agent 决定任务目标。

### 两者的关系

| 概念 | 主要回答的问题 |
|---|---|
| Function Calling | 模型怎样表达“调用哪个工具、传什么参数” |
| MCP | AI 应用怎样用标准方式发现和连接外部能力 |
| Agent | 面对目标时，怎样判断下一步并完成任务 |

需要强调：

- MCP 不是 Agent；
- MCP 不是决策者；
- 接入 MCP 不代表自动获得可靠的任务规划；
- Function Calling 和 MCP 不是简单的替代关系。

## 三、回到门店经营助手

当前课堂 Demo 只有三个预先配置的工具，因此不需要为了使用 MCP 而使用 MCP。

未来出现以下情况时，MCP 的价值会变得更明显：

- 需要连接多个外部系统；
- 工具和资源经常变化；
- 不同 AI 客户端需要复用同一组能力；
- 希望减少每个客户端的重复适配工作。

产品经理此时仍需关注：

- 暴露了哪些能力；
- 每项能力需要什么权限；
- 返回结果是否可信；
- 哪些动作允许写入或执行；
- 调用过程是否可以审计。

## 四、什么是 Multi-Agent

Multi-Agent 是由多个承担不同角色或子任务的 Agent 协同完成一项复杂任务。

例如，一个复杂的经营方案可能拆成：

- 数据分析角色；
- 活动规则角色；
- 方案审核角色；
- 最终汇总角色。

但“角色多”不等于“效果一定好”。

## 五、什么时候才考虑 Multi-Agent

可以考虑的情况：

- 子任务高度专业化；
- 不同角色需要不同知识、工具或权限；
- 任务可以明确拆分并校验；
- 并行协作带来的收益高于额外成本。

不建议使用的情况：

- 一个 Agent 加几个工具就能完成；
- 只是想让产品听起来更先进；
- 角色之间边界不清；
- 无法判断每个角色的输出质量；
- 时延和成本要求很严格。

本课默认设计原则：

> 先用一个 Agent 加少量工具跑通闭环；只有单 Agent 出现明确瓶颈时，再考虑拆成多个 Agent。

## 六、两道快速判断题

### 情境一

门店助手需要读取指标、查询规则和生成草稿。

建议：先采用单 Agent 加三个工具，没有必要立即拆成 Multi-Agent。

### 情境二

集团级经营系统需要多个行业专家分别分析财务、供应链、营销和合规，而且各自使用不同的数据权限与审核标准。

建议：可以进一步评估 Multi-Agent，但仍要验证拆分收益、协作成本和责任边界。

## 七、本模块结论

学员只需带走三句话：

1. Function Calling 让工具调用结构化；
2. MCP 让外部能力的连接更标准化；
3. Multi-Agent 解决的是复杂任务中的角色协作，但不应成为默认方案。
