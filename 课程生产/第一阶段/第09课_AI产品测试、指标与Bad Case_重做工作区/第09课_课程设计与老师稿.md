# 第09课《AI产品评测与数据反馈闭环》课程设计与老师稿

> 版本：V0.5（对齐知乎第27课主线与PPT制作原则）  
> 推荐时长：170分钟完整教学＋10分钟弹性Review；可按现场情况控制在150—180分钟  
> 课程位置：承接第08课可运行Demo；第10课进入风险、安全与人机协作。  
> 文件原则：课程定位、来源、时间结构、讲授要点和课堂Review统一保留在本文件。

## 一、重新设计后的结论

第9课保留为一节独立课，而且主题明确收敛为：

> **让学员亲手完成一次“评测集—组合评分—Bad Case—版本回归—线上反馈”的最小闭环。**

这节课不做三件事：

1. 不把“幻觉、安全与合规”讲成完整治理课，该部分留给第10课；
2. 不要求零基础学员在课堂上开发完整自动化评测平台；
3. 不把余弦相似度、LLM-as-Judge或某个固定分数当成万能答案。

知乎第27课证明“测试与数据反馈闭环”足以独立成课，但原课约160分钟，内容同时覆盖幻觉、六类测试、自动化评测平台、数据标注、微调准备和职场表达。本课不再为了严格凑满120分钟而压缩必要内容，而是按170分钟完整教学设计，并预留10分钟给综合Review和答疑。工程实现仍以演示为主，避免把AI产品经理课程变成测试平台开发课。

## 二、为什么第9课必须单独存在

第08课证明“Demo能跑”，第09课要证明“产品在一组代表性任务上达到什么水平”。两者不是同一件事。

传统功能验收可以回答按钮、页面、流程是否符合PRD，但生成式AI还存在输出不稳定、模型或Prompt变更后能力退化、知识和工具链路错误等问题。因此，AI产品上线前至少要回答：

- 测什么场景；
- 什么算好答案；
- 哪些错误绝不能上线；
- 修改后是否真的变好；
- 上线后如何把真实问题变成下一轮评测数据。

本课的产品经理边界是：

> **产品经理负责定义测什么、什么算好、什么情况下可以上线，并推动问题闭环；测试和研发负责工程化执行与技术修复。**

## 三、学习结果

完成本课后，学员应能：

1. 区分功能验收、离线评测和线上效果监控；
2. 从真实任务、业务规则和历史问题设计代表性评测集；
3. 为每条用例写出期望答案、评分点、风险等级和通过条件；
4. 根据指标选择规则校验、语义相似度、LLM-as-Judge或人工评审；
5. 把Bad Case定位到数据、Prompt、知识、流程、工具或产品边界；
6. 对Prompt、模型或知识版本进行A/B比较与回归测试；
7. 设计复制、采用、编辑、重生成、点踩和转人工等线上反馈信号。

## 四、贯穿案例与课堂任务

主案例采用虚构的“AI商家客服助手”：

```text
用户提问
→ 判断意图
→ 查询商品/活动知识
→ 必要时调用订单工具
→ 生成回复
→ 无依据、高风险或工具失败时转人工
```

选择该案例，是因为它同时包含Workflow、RAG、工具调用和人工兜底，且答案中既有可精确校验的价格、优惠、订单状态，也有需要判断完整性、语气和帮助程度的主观部分。

第08课的商品对比Demo只在开场使用，用来对比“功能验收”和“AI效果评测”，不承担全课案例。

课堂最终只完成一张综合工作表，产出：

- 8条评测用例；
- 6条实际运行记录；
- 2条Bad Case分析；
- 1次V0.1/V0.2版本对照；
- 1张线上数据反馈闭环。

## 五、150—180分钟教学结构

### 5.1 三段式课程地图

本课沿用知乎第27课最清晰的三段式推进，但按照本系列课程边界重新分配内容：

| 大部分 | 回答的问题 | 对应模块 | 本课处理 |
|---|---|---|---|
| 第一部分：为什么AI产品必须评测 | Demo能跑，为什么仍然可能失控 | 模块01—02 | 保留幻觉和概率性作为业务动机，完整风险治理留到第10课 |
| 第二部分：怎样建立评测体系 | 测什么、什么算好、怎样发现和修复问题 | 模块03—07 | 本课主体，包含评测集、组合评分、自动评测演示、Bad Case和回归 |
| 第三部分：怎样形成数据反馈闭环 | 上线后怎样把真实问题变成下一轮数据 | 模块08—09 | 保留反馈信号、问题池、回流和上线判断，不展开微调工程 |

学生在开课时先看到这张地图，后续九个模块都挂在三部分之下，避免把评测方法、工具演示和数据反馈听成互不相关的知识点。

### 5.2 详细时间安排

| 时间 | 模块 | 核心问题 | 教学方式 | 当场产出 |
|---|---|---|---|---|
| 0-15 | 01 Demo能跑，为什么还不能上线 | 一次成功能证明什么 | 对比演示＋提问 | 被测对象与版本说明 |
| 15-35 | 02 到底测什么 | AI产品测试有哪些层次，PM负责什么 | 框架讲解＋案例判断 | 测试范围与角色边界 |
| 35-60 | 03 建立最小评测集 | 怎样覆盖真实场景而非只测容易题 | 老师示范＋小组设计 | 8条评测用例 |
| 60-80 | 04 什么算答对 | 不同指标和评分方法怎样组合 | 四种评法对比演示 | 评分规则与上线红线 |
| 80-90 | 短休息 | — | — | — |
| 90-115 | 05 跑一次轻量评测 | 如何获得可以重复比较的基线 | 实操＋结果讲评 | 6条运行记录 |
| 115-135 | 06 从低分到Bad Case | 错了以后先查哪一层 | 分组诊断＋讲评 | 2条Bad Case台账 |
| 135-150 | 07 修改、A/B与回归 | 怎样证明优化有效且没有退化 | 版本对比＋上线判断 | V0.1/V0.2结果与评审结论 |
| 150-170 | 08 上线后的数据反馈闭环 | 用户行为怎样变成下一轮评测数据 | 案例拆解＋闭环图 | 反馈字段与回流路径 |
| 170-180 | 09 综合Review与答疑 | 这套评测能否支持上线决策 | 小组汇报＋老师点评 | 完整评测闭环 |

前170分钟构成完整课程，最后10分钟用于综合Review和答疑。若现场必须在150分钟结束，应压缩框架讲解、小组讨论和运行等待时间，并减少运行用例数量，但仍保留模块08的数据反馈闭环，避免课程只讲“离线评测”而没有完成闭环。

## 六、分模块老师稿

### 模块01｜Demo能跑，为什么还不能上线（0-15分钟）

#### 开场演示

用同一个问题连续运行两到三次，或分别使用两个Prompt版本，让学员观察输出措辞、遗漏项或判断结果的变化。

#### 老师讲法

“第8课我们关心的是功能有没有做出来。今天我们换一个问题：这个产品到底好不好，依据是什么？AI输出带有概率性，一次演示成功只能证明它这一次成功，不能证明它对目标用户的主要任务都稳定有效。”

板书三类验证：

| 类型 | 回答的问题 | 示例 |
|---|---|---|
| 功能验收 | 产品是否按PRD运行 | 按钮能否点击、状态能否切换 |
| 离线评测 | 固定样本下效果是否达标 | 8条题中通过几条、P0是否为0 |
| 线上监控 | 真实用户是否完成任务 | 采用、重试、转人工、投诉 |

#### 必须强调

- 评测对象不是一句Prompt，而是“模型＋Prompt＋知识＋流程＋工具”的具体版本；
- 供应商模型即使名称未变，效果也可能变化，因此要保留基线并持续回归；
- 本课先解决效果可测，第10课再系统解决风险治理。

### 模块02｜到底测什么（15-35分钟）

#### 六类完整测试视角

1. 功能与AI任务效果；
2. 可用性与用户体验；
3. 性能与稳定性；
4. 鲁棒性与异常恢复；
5. 安全与权限；
6. 伦理、偏见与内容合规。

完整项目都要考虑以上六类，但本课实操聚焦第一类，并观察部分异常恢复；第10课深入安全、合规和人机接管，第11课讲性能、部署和架构。

#### AI链路分层

| 层次 | 重点观察 |
|---|---|
| Workflow | 意图路由、节点完成、异常分支、兜底 |
| RAG | 是否命中正确知识、来源是否有效、回答是否忠于证据 |
| Agent/工具 | 工具选择、参数、返回、停止条件 |
| 最终回复 | 正确、相关、完整、安全、风格合适 |
| 端到端任务 | 用户问题是否真正解决、失败是否可恢复 |

老师追问：“如果回复写得很礼貌，但查错了订单，算不算通过？”引导学员理解最终文本好看不等于链路正确。

### 模块03｜建立最小评测集（35-60分钟）

#### 数据来源优先级

1. 真实用户问题、历史工单、搜索和对话；
2. 线上Bad Case、投诉、转人工和用户纠正；
3. 业务专家补充的关键规则与高风险场景；
4. AI基于种子问题生成问法变体、边界和异常候选。

AI可以帮助扩写测试题，但业务人员必须审核场景、期望和风险。不要让同一个模型独立出题、写金标、答题并判卷。

#### 课堂五类样本

- 典型：高频正常任务；
- 边界：临界数量、时间、格式或状态；
- 异常/对抗：错别字、模糊表达、诱导越权或工具失败；
- 无答案：知识不足时应说明限制或转人工；
- 高风险：错误会造成赔付、隐私、合规或不可逆操作。

#### 每条用例的八个设计字段

`编号｜业务场景｜用户输入｜前置条件｜样本类型｜期望答案/评分点｜通过规则｜风险等级`

老师示范一条：

| 字段 | 示例 |
|---|---|
| 场景 | 查询促销叠加规则 |
| 输入 | “满199减30还能再用会员九折吗？” |
| 前置条件 | 活动规则V2026.08 |
| 类型 | 典型＋硬事实 |
| 期望/评分点 | 明确能否叠加；说明优先级；引用活动规则 |
| 通过规则 | 叠加结论必须精确；三个评分点至少命中两个；不得编造 |
| 风险 | P1 |

#### 课堂动作

每组完成8条：典型2条、边界1条、异常/对抗2条、无答案1条、高风险2条。数量不是上线标准，只是用于练习完整方法。

### 模块04｜什么算答对（60-80分钟）

没有一种评分方法适合所有问题。先看评价标准，再选评法。

| 评法 | 适合 | 不适合/限制 |
|---|---|---|
| 精确匹配与规则 | 价格、日期、字段、工具参数、禁答项 | 难判断同义表达和整体帮助程度 |
| 语义相似度 | 主题方向、近义表达、初筛 | 相似不代表事实正确，关键数字可能错 |
| LLM-as-Judge | 相关性、完整性、语气、理由解释 | 受裁判模型和提示词影响，不宜单独签发上线 |
| 人工评审 | 终审、争议样本、规则校准 | 成本高、速度慢、可能存在评审差异 |

#### 推荐组合

1. 硬事实和红线优先用规则；
2. 大批量文本可用相似度初筛；
3. 主观维度用LLM-as-Judge辅助；
4. P0/P1、低分和抽样样本由人工终审。

不采用原参考课中任何固定相似度阈值。阈值必须基于本项目样本校准，且P0用例不能靠平均分抵消。

最终回复可从五个维度评分：正确性、相关性、完整性、安全性、表达/风格。并额外记录链路是否正确、耗时和风险事件。

### 模块05｜跑一次轻量评测（90-115分钟）

本模块分为“老师演示成熟形态”和“学生完成最小闭环”两段。平台演示用于建立完整认知，课堂练习用于确保学生真正会做，不要求学生当场开发平台。

#### 老师演示：完整自动评测中心（约8分钟）

按知乎第27课的演示主线，依次展示：

1. 选择或导入固定评测集；
2. 批量运行同一产品版本；
3. 查看规则、语义、LLM评审等多维结果；
4. 查看总通过率、P0/P1失败和场景分布；
5. 下钻一条失败用例，查看运行链路和扣分理由；
6. 将Bad Case送入人工标注或问题池；
7. 切换Prompt版本，查看A/B结果与历史趋势。

演示重点不是平台有多少功能，而是让学生看见：固定题目、统一评分、批量运行、失败下钻、版本比较和人工复核可以组成一套可重复的工作流。

#### 学生操作：轻量评测（约17分钟）

1. 固定被测版本：模型、Prompt、知识库、Workflow/Agent和时间；
2. 选择6条用例运行；
3. 将实际输出粘贴到工作表；
4. 先跑规则项，再做LLM辅助评分，最后人工抽查；
5. 记录通过/不通过、证据和评语。

#### 看板只保留五个核心结果

- 总通过率；
- P0/P1失败数；
- 各场景通过情况；
- 失败用例清单；
- 相较上一版本的变化。

老师提醒：“通过率是结果摘要，不是判断真相。样本是否代表真实业务、评分标准是否可靠，比一个漂亮数字更重要。”

### 模块06｜从低分到Bad Case（115-135分钟）

#### 六类归因

| 类别 | 先看证据 | 常见动作 |
|---|---|---|
| 数据 | 输入、字段、标注、样本分布 | 清洗、补数、修标注 |
| Prompt/规则 | 指令、格式、优先级、冲突 | 澄清规则、拆步骤、加校验 |
| 知识 | 召回、版本、来源、权限 | 更新知识、调整分块或检索 |
| 流程/状态 | 路由、状态转移、兜底 | 改分支、失败路径和接管条件 |
| 工具/系统 | 工具选择、参数、返回、超时 | 修描述、参数校验、重试 |
| 产品边界 | 需求承诺、可控程度、风险等级 | 缩小范围、拒答、转人工 |

#### Bad Case记录模板

`用例编号｜实际表现｜影响/风险｜链路证据｜暂定归因｜验证动作｜责任角色｜状态`

没有日志、检索结果或工具调用证据时，只能写“待验证假设”，不能宣布“根因已确认”。

课堂选择两条失败用例，要求学员先定位层次，再提出一个可验证的修改动作。避免一看到低分就直接“改Prompt”。

### 模块07｜修改、A/B与回归（135-150分钟）

版本至少记录：

- 模型版本；
- System Prompt和关键Prompt版本；
- Workflow/Agent版本；
- 知识库与数据版本；
- 评测集版本；
- 运行环境与时间。

复测顺序：

1. 原失败样本；
2. 同类高风险样本；
3. 历史代表性正常样本。

老师讲法：“V0.2让原题答对，不等于产品变好。它可能只记住了这道题，也可能让另一类能力退化。回归测试就是防止修好东墙、拆掉西墙。”

课堂只修改一个可控变量，例如Prompt中的规则表达，然后比较V0.1/V0.2。多项同时改变时，不声称已经知道改善来自哪里。

### 模块08｜上线后的数据闭环（150-170分钟）

#### 显性与隐性反馈

| 信号 | 可能含义 | 注意事项 |
|---|---|---|
| 点赞/点踩 | 明确态度 | 使用率低，点踩要追问原因 |
| 复制/采用 | 结果被使用 | 通常比点赞更接近真实采用 |
| 编辑后采用 | 部分可用 | 应保留修改前后差异 |
| 重生成 | 当前答案不满意 | 也可能只是想探索其他表达 |
| 转人工/投诉 | 任务未解决或风险较高 | 应优先进入问题池 |
| 重复追问/放弃 | 可能未理解或未解决 | 需结合会话上下文判断 |

#### 闭环

```text
真实会话与行为反馈
→ 脱敏、筛选与人工标注
→ Bad Case问题池
→ 补充评测集/优化Prompt、知识或流程
→ 离线回归
→ 小范围上线
→ 继续收集反馈
```

本课只讲把反馈变成可用的评测与优化数据；标注一致性、训练数据和微调在后续相关课程展开。

### 模块09｜综合Review与答疑（170-180分钟）

每组用三分钟回答四个问题：

1. 我们测的是什么产品能力？
2. 当前最严重的Bad Case是什么？
3. V0.2相比V0.1改善了什么，又可能退化什么？
4. 当前结论是直接上线、灰度上线、退回修改，还是必须转人工？

老师最后把评测重新收束到产品决策：评测的终点不是生成一张漂亮报表，而是让团队能够有依据地决定是否上线、先改什么，以及上线后继续观察什么。

## 七、课堂Review与完成标准

下课前用以下问题快速检查：

1. 评测对象的版本是否写清楚？
2. 8条用例是否覆盖正常、边界、异常、无答案和高风险？
3. 期望答案是否写成可执行评分点，而不是“回答正确”？
4. 硬事实是否使用规则校验？
5. LLM-as-Judge是否有人审或规则兜底？
6. Bad Case归因是否有链路证据？
7. V0.2是否复测了历史样本，而非只测原失败题？
8. 线上反馈是否能回到问题池和评测集？

最低完成线：8条设计、6条运行、2条Bad Case、1次版本对照、1条反馈回流路径。

## 十、PPT制作原则

### 10.1 内容关系

- 知乎第27课是本课PPT的主要内容母版；
- V0.5老师稿是最终取舍、时间和课堂动作的执行依据；
- PPT保留知乎课件的三段式主线、关键概念、案例顺序和演示节奏；
- 对重复解释、过长过渡、课堂闲聊和后续课程内容进行合并或删除；
- 亚慧材料与本课程前序课只用于补充指标、RAG分层和课程衔接，不改变知乎主线。

### 10.2 页面规模与结构

正式PPT预计控制在60—75页，可按以下范围安排：

| 页面组 | 建议页数 |
|---|---:|
| 开场、课程地图与为什么必须评测 | 8—10页 |
| 测试范围与评测集构建 | 12—15页 |
| 四种评分方法与自动评测中心 | 15—18页 |
| Bad Case、版本A/B与回归 | 10—12页 |
| 数据反馈闭环 | 8—10页 |
| 实操指引、Review与总结 | 6—8页 |

页数是排版参考，不以机械凑页为目标；当一个概念需要案例、反例或现场演示时可以拆页，重复观点应合并。

### 10.3 视觉与版权处理

- 重新设计颜色、字体、封面、章节页、图表和信息层级；
- 不保留知乎课程品牌、讲师身份或原课页眉页脚；
- 原课中的流程、表格和平台截图优先重新绘制或使用我们的演示截图；
- PPT备注保留内容来源和老师讲解提示；
- 不为了改变而改变知识含义，视觉改版不能破坏原有教学顺序。
