> 课程暂定名：**大模型基础、上下文与 Prompt 产品化设计**  
> 当前阶段：只确认教学定位、知识边界与来源，不提前编写讲义和 PPT。  
> 核心原则：正式讲授的知识点必须能定位到现有参考课程的具体段落或课件页；只有标题、没有详细内容的材料，不能作为老师备课的唯一依据。

## 一、本课在课程体系中的定位

### 1. 前后衔接

- 第0课已经用“销售拜访记录助手”让学员第一次思考 AI 场景，但没有系统解释大模型如何处理输入、为什么结果会波动，以及产品经理如何设计模型所需的信息。
- 第1课解决“AI 产品经理是什么、有哪些方向、个人如何转型”。
- 第2课开始补第一组 AI 产品基础：让学员能用产品语言解释大模型、上下文和 Prompt，并能把一段个人提示词改造成可复用的产品方案。
- 第3课再讨论产品形态和场景判断；后续课程分别展开 Workflow、RAG、Agent、评测和成本等内容。

### 2. 本课核心问题

本课只集中解决四个问题：

1. 大模型为什么能够生成内容，为什么同一输入的结果可能不同？
2. Token 和上下文窗口会怎样限制产品设计？
3. Prompt 在 AI 产品中到底控制什么，结构化 Prompt 应包含哪些信息？
4. 如何把“用户自己写 Prompt”变成由产品承担的模板、字段、默认值和交互？

### 3. 本课结束时的最低可验收结果

学员应能：

- 用“基于上下文预测后续 Token”解释大模型生成，而不是把模型理解成数据库或真人专家；
- 识别一个任务所需的目标、背景、输入材料、约束、输出格式等上下文；
- 写出一版结构化 Prompt；
- 区分用户输入与产品内部指令；
- 把一段完整 Prompt 拆成“信息供给方式＋风险处理＋产品交互”；
- 对一个 Bad Case 做第一层定位：是任务没说清、上下文不足、约束缺失，还是输出格式不可验收。

### 4. 本课不承担的任务

- 不讲 Transformer、Self-Attention、Embedding 的推导和实现细节；
- 不系统讲幻觉治理，留到后续可靠性相关课程；
- 不展开 Workflow、RAG、Agent 的架构和搭建，只说明它们与 Prompt 的边界；
- 不做完整模型评测体系；
- 不展开模型选型和成本核算；
- 不把课程变成“Prompt 技巧大全”或某个平台的工具操作课。

## 三、原始材料萃取卡

## 3.1 A1 亚慧：可直接支撑的内容

### A1-1 大模型生成的最低必要心智模型

- 录音 P481—P490：预训练的核心任务是预测下一个词；模型根据已经出现的内容继续生成，输出呈逐 Token 产生的形态。
- 录音 P499—P526：用“今天阳光明媚，小明在公园里……”的候选词概率举例，解释模型如何依据概率逐步生成。
- 课件第14—15页：模型输出概率分布，不必永远选择最高概率结果。
- 可转化讲法：大模型不是先在脑中写好完整答案，也不是从答案库中检索固定答案，而是在当前上下文基础上逐步生成。
- 使用提醒：原录音中“完全没有理解能力”等绝对化表述不直接照搬；课堂使用更谨慎的“生成机制不同于人类理解，也不同于数据库查答案”。

### A1-2 为什么同一个问题可能得到不同答案

- 录音 P517—P532：模型会按概率采样，不总选最高概率 Token；Temperature 可影响输出多样性与随机性。
- 课件第14—15页：概率采样与 Temperature。
- 可转化讲法：生成结果存在非确定性；产品不能只看一次 Demo，需要用多组输入和多次运行观察稳定性。
- 本课深度：只讲现象、原因和产品含义，不讲采样算法。

### A1-3 Token 及其成本含义

- 录音 P265—P298：输入先被拆成 Token；Token 是模型处理信息的基本单位；输入与输出都会消耗 Token，并对应算力和调用成本。
- 录音 P337—P340：过长 Prompt、长文档和多模态输入都会占用上下文并增加成本。
- 可转化讲法：用户输入、产品内部指令、历史对话、检索内容和模型输出都不是“免费空间”。
- 本课深度：建立概念和产品意识；具体计价、预算和模型成本比较留到后续课程。

### A1-4 上下文窗口及产品影响

- 录音 P301—P340：上下文长度是一次处理的 Token 容量，可理解为短期记忆；超出后可能截断或丢失信息；长对话、长文档、图片和长 Prompt 都会占用窗口。
- 课件第9—10页：Context Length 定义、超出窗口后的截断、对产品设计的影响。
- 可转化讲法：模型一次回答所依据的信息有容量边界，产品经理必须决定“给什么、不给什么、先给什么、何时压缩或另存”。
- 使用提醒：课件中“1 Token≈0.75个汉字”等换算只适合作为特定 tokenizer 下的粗略示意，不能讲成跨模型固定公式。

### A1-5 能力边界只做轻量铺垫

- 录音 P91—P136：生成、理解、问答、推理、数学、代码等任务及例子。
- 录音 P142—P223：幻觉、个性化、知识更新等局限，Prompt、RAG、Agent 是不同层次的补充手段。
- 起点大纲第57—73行也覆盖 AI 使用模式、幻觉和能力边界。
- 本课用途：只用于解释 Prompt 不能解决所有问题，不在本课系统讲幻觉治理或产品形态选择。

## 3.2 A2 知乎：可直接支撑的内容

### A2-1 从产品目标反推输入和处理

- 录音 P520—P553：构建产品不应从技术框开始，应先确认用户需要的输出，再确认输入，最后设计核心处理。
- 课件第100—103页：输入—核心处理—输出，以及“先确认输出、再确认输入、再设计 LLM 处理”。
- 可转化讲法：Prompt 不是脱离需求写文案；先定义可用结果和验收标准，才知道模型需要哪些信息和约束。

### A2-2 System Prompt 与 User Prompt 的分工

- 录音 P565—P568：System Prompt 越专业，User Prompt 越可能简单；提示词承担激活、引导和约束作用。
- 课件第105—109页：System Prompt 是让 User Prompt 简单的关键；提示词用于激活、引导和约束；简单词语与结构化任务描述的对比。
- 可转化讲法：用户不应该每次重写完整说明书。固定角色、业务规则和输出规范应由产品内部承载，用户只补充本次任务变量。
- 使用提醒：具体产品中的系统消息、开发者消息和用户消息会因模型平台而异；本课先使用产品层的简化分工，不展开 API 消息协议。

### A2-3 结构化 Prompt 框架

- 录音 P571—P595：角色/能力、背景洞察、任务、风格、实验迭代、响应格式；并强调 Prompt 的前提是明确用户、输入和输出。
- 课件第113页：完整示例。
- 课件第118—119页：CRISPE 框架，包括 Capacity & Role、Insight、Statement、Personality、Experiment、Response。
- 可转化讲法：本课不要求学员死记缩写，统一转译为六类产品信息：**角色与能力、任务目标、业务背景与输入、规则与约束、输出格式与标准、示例与迭代要求**。
- 使用提醒：本课程加入“约束”和“示例”属于对原框架的产品化重组；讲义中要明确是课程整理版本，不能伪装成原课逐字结论。

### A2-4 Prompt 产品化的核心价值

- 录音 P418—P484：图像生成产品从复杂 Prompt、负向词和大量参数，演进到更简单的描述、选项和产品交互；“用户说得越简单、输出越专业，产品价值越高”。
- 录音 P601—P622：自然语言输入之所以简单，是产品和技术在内部做了 System Prompt、工作流、RAG、接口调用等大量设计。
- 课件第82页：不再强调“提示词”，改成“描述你脑海中的画面”，并通过提示词优化等功能降低门槛。
- 课件第89页：Prompt 优化、自建模型、产品化经验共同支撑“低门槛、较准确”的核心需求。
- 可转化讲法：产品化不是让用户更会写 Prompt，而是把专业要求封装为默认模板、结构化字段、选择项、校验和结果交互。

### A2-5 Prompt 与 Workflow、RAG、Agent 的边界

- 录音 P625—P646：大模型、Prompt、Workflow、RAG、Function Call、Agent 的关系类比；Prompt 只是整体的一部分。
- 课件第121—125页：LLM、Prompt、Workflow、Agent、RAG、Function Calling 的关系与“大学毕业生”类比。
- 可转化讲法：Prompt 主要解决“这次任务要模型怎么回答”；当问题来自多步骤流程、私有知识或外部动作时，需要其他机制。
- 本课深度：只用一张边界图和反例完成预告，不讲搭建方法。

## 五、案例如何复用，避免与第0课重复

本课继续使用“销售拜访记录助手”，但教学任务必须变化：

| 第0课已经完成 | 第2课新增任务 |
|---|---|
| 识别销售拜访中的问题与价值 | 明确模型最终要输出什么、谁来使用、怎样算可用 |
| 判断AI在场景中可以承担什么 | 盘点模型完成任务需要的上下文信息 |
| 讨论人与AI的分工和风险 | 分别设计产品固定、用户提供、系统获取，以及结果检查和确认 |
| 形成初步方案 | 写出内部结构化Prompt，并把它拆成产品字段与交互 |

### 建议课堂任务

给学员同一份未经整理的拜访转写文本，先后完成三轮：

1. 只输入“帮我整理一下”，观察结果为什么不可验收；
2. 补齐任务、背景、约束和输出格式，形成结构化 Prompt；
3. 把结构化 Prompt 拆成产品方案：哪些内容由产品固定、用户提供或系统获取；哪些结果普通展示、建议检查或必须确认。

这样，案例的作用不再是证明“AI产品经理做什么”，而是让学员看见：**Prompt 产品化的本质，是把业务判断和专业要求变成系统可重复执行的上下文与交互。**

## 六、本课教学决策

### T1. 课程名称统一

建议正式名称采用：**《大模型基础、上下文与 Prompt 产品化设计》**。

原因：

- 比原大纲《大模型基础与 Prompt 产品化设计》更准确地体现上下文窗口和上下文设计；
- 第1课结尾预告已统一为《大模型基础、上下文与Prompt产品化设计》；
- “Prompt 产品化”仍是本课区别于普通工具课的核心卖点。

### T2. 技术内容只讲到能支持产品判断

大模型部分只保留四个概念：生成机制、非确定性、Token、上下文窗口。Transformer、Embedding、预训练细节不进入主线。

### T3. Prompt结构采用课程自己的产品化六要素

本课不要求背 CRISPE 缩写，而采用：

1. 角色与能力；
2. 任务目标；
3. 业务背景与输入材料；
4. 规则与约束；
5. 输出格式与验收标准；
6. 示例与迭代要求。

该结构由知乎 CRISPE 框架与完整课程大纲中的“角色、任务、背景、约束、格式、示例”合并整理而成。后续讲义必须如实标明“本课程整理”，避免错误归因。

### T4. 产品化使用两个维度，至少落到四个可操作动作

**维度一：信息怎样进入产品**

1. **产品固定**：角色、业务规则、输出结构由产品统一承载；
2. **用户提供**：只有用户知道或必须主动选择的信息才让用户填写；
3. **系统获取**：系统已有且有权使用的信息自动带入并允许修正。

**维度二：结果怎样处理风险**

4. **分档处理**：区分普通展示、建议检查和必须确认；高风险结论或外部动作明确证据、权限和确认点。

信息供给与风险处理不是互斥分类。例如客户资料可以由系统获取，同时在高风险使用或写入前要求用户确认。

模板版本号、AB实验、批量评测和回归机制暂不作为本课正式知识点。

### T5. Prompt与其他技术的关系只做边界识别

- 任务说不清：先改 Prompt / 上下文；
- 缺少企业知识：记录知识供给问题；
- 需要多个稳定步骤：记录流程拆分问题；
- 需要查询、写入或发送：记录外部连接、权限和确认问题；
- 上游数据错误或持续不达标：评估数据、模型、方案或场景。

本课只识别“可能超出单次Prompt”的信号，不要求学员掌握RAG、Workflow、Agent、Function Calling或MCP定义，也不进行技术选型，以免提前侵入后续课程。

### T6. 课后产出控制为一个闭环

建议不同时布置四份相互割裂的作业，而合并为一份《Prompt产品化设计单》，至少包含：

- 场景与目标用户；
- 目标输出和验收标准；
- 所需上下文清单；
- 结构化 Prompt；
- 固定项、变量项、自动获取项；
- 产品界面字段草图；
- 一条 Bad Case 及初步修正。
