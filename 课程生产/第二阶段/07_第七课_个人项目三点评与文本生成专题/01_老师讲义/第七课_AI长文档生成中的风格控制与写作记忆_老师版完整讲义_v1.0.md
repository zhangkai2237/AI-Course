# AI长文档生成中的风格控制与写作记忆

## 老师版完整讲义 v1.0

> 课程位置：第二阶段第七课·个人项目三点评与迭代中的文本生成专题  
> 承接项目：项目三“智能标书助手”  
> 面向学员：已经完成智能标书项目学习，正在制作长文档、专业内容生产或知识库类个人项目的学员  
> 专题建议时长：105分钟  
> 更新日期：2026年11月9日

---

## 一、课程定位

项目三已经讲过招标要求拆解、响应矩阵、企业资料调用、目录生成、分章节写作和风险检查。这一节不重复完整的标书生成流程，集中处理四个更细、也更接近日常使用的问题：

1. 模型生成的文字为什么经常出现固定句式，怎样在生成前减少这些表达；
2. 企业已经有很多历史标书，怎样只学习其中的结构、文案组织和语言风格；
3. 多个章节分别生成时，怎样统一项目名、产品名、角色名和专业术语；
4. 人工已经修改过一遍，怎样让后续章节少犯同样的问题。

这四个问题都与“写得更好”有关，但解决位置不同：

```text
通用风格约束
→ 历史写法参考
→ 当前项目称呼控制
→ 人工修改沉淀
```

教师在全课中要不断提醒学员：一个笼统的“写得专业一点”很难稳定执行。产品需要把写作要求拆成模型能够遵守、用户能够确认、系统能够保存的具体规则。

本专题只讨论文本生成中的风格、称呼和写作规则，不扩展到完整的事实核验、商务承诺审核、招标响应完整性和全文业务逻辑校验。这些能力可以继续存在于智能标书助手中，但不进入本次专题的主要教学范围。

---

## 二、教学目标

完成本专题后，学员应当能够：

1. 识别专业文档中常见的AI固定句式；
2. 将“去除AI味”转化为具体提示词约束；
3. 使用频率限制、替代规则、正反例和生成前自检控制文风；
4. 区分历史标书中的结构、文案模式、风格与项目事实；
5. 将历史标书处理成不携带案例、数据和承诺的写作参考；
6. 建立一张精简的全局变量表，统一名称、简称和专业术语；
7. 从人工修改中识别可复用的候选写作规则；
8. 判断一条规则应当只用于当前句段、当前章节、当前项目还是企业长期规范；
9. 将四类控制组合成一套可以落入产品的文本生成流程。

# 话题一：通过提示词减少固定句式和AI味（00—25分钟）

## 1. 从一段AI味明显的文字开始（00—05分钟）

教师展示下面这段文字，不先解释问题：

> 接下来，我们将用最直白、最不绕弯子的方式，一步一步拆解智能标书系统的设计逻辑。真正重要的不是生成速度，而是生成质量。那么问题来了，怎样才能保证生成质量？答案其实很简单。首先要拆解要求，其次要检索企业资料，最后要进行风险检查。归根结底，智能标书系统的核心价值，是让标书生成更加智能、高效和可靠。

请学员在一分钟内圈出“读起来像AI”的表达。

教师邀请2—3位学员回答。常见答案包括：

- “接下来，我们将……”；
- “最直白、最不绕弯子”；
- “一步一步拆解”；
- “真正重要的不是……而是……”；
- “那么问题来了”；
- “答案其实很简单”；
- “首先、其次、最后”；
- “归根结底”；
- “智能、高效、可靠”。

教师继续追问：

> 这段话有没有明显的语法错误？

> 如果一句一句拆开看，为什么每句话似乎都说得通，放在一起却很像模型生成？

教师讲述：

这里说的AI味，主要指模型反复使用的一组表达习惯。它喜欢先报幕，再制造对立，接着自问自答，最后总结升华。这些句式单独出现不一定有问题，连续出现就会形成明显的模板感。

我们今天不讨论如何通过所谓的AI检测，也不追求把文字伪装成人工创作。课程处理的是更具体的问题：如何减少机械表达，让专业文档直接传递信息。

## 2. AI固定句式的六种类型（05—10分钟）

教师展示下表：

| 类型 | 常见表达 | 主要问题 |
| --- | --- | --- |
| 报幕型 | 接下来我们将、下面逐一分析 | 标题已经说明结构，句子没有新增信息 |
| 自我评价型 | 最直白、最实用、不绕弯子 | 作者先评价自己的表达方式 |
| 强行对立型 | 不是A而是B、真正重要的不是A | 容易把并列、因果或轻重关系写成二选一 |
| 机械设问型 | 那么问题来了、答案很简单 | 在没有悬念的地方制造悬念 |
| 伪洞察型 | 本质上、底层逻辑、真正的核心 | 先宣布深刻，再给出普通结论 |
| 重复收束型 | 归根结底、如果只记住一句话 | 段尾、小节末和全文末反复总结 |

教师说明：

判断一句引导语有没有价值，可以做一个小测试：删掉它，后面的句子是否仍然完整？

例如：

> 需要明确的是，AI检测结果不能证明文本一定由AI生成。

删掉前半句以后：

> AI检测结果不能证明文本一定由AI生成。

信息没有损失，前面的引导语就可以删除。

再看一个对比句：

> 重点不是生成速度，而是内容准确性。

这句话可以根据真实关系改成：

> 在专业文档场景中，内容准确性比生成速度更重要。

后一句表达的是轻重关系，不需要制造二元对立。

## 3. 为什么“写得自然一点”很难执行（10—13分钟）

教师展示四条常见要求：

```text
请写得自然一点。
请去除AI味。
请写得更像人。
请写得专业、有深度、有温度。
```

教师提问：

> 如果你是模型，看到“自然一点”，具体应该改什么？

教师讲述：

这些要求描述的是读者感受，没有定义可以执行的语言行为。模型可能删除一两个连接词，也可能换一套新的套话。要提高稳定性，需要把“AI味”拆成几类明确动作：

```text
不报幕
不评价自己的表达
减少固定对比句
减少假设问答
不机械排列
不重复总结
```

## 4. 一条有效风格提示词的四个组成部分（13—19分钟）

### 4.1 规定怎样开始

```text
直接进入正文，不介绍你将如何回答。
不要使用“接下来我将”“下面我们来”“我会用最直白的方式”等开场。
```

### 4.2 限制高频句式

```text
“不是……而是……”全文最多出现一次。
不使用“真正的核心”“底层逻辑”“归根结底”“说白了”等空泛引导语。
不使用“那么问题来了”“答案其实很简单”等假设问答。
```

教师提醒：完全禁止所有对比句容易让语言变得僵硬。更稳妥的方式是设置频率限制，并告诉模型何时可以保留。

### 4.3 提供替代规则

```text
根据内容的实际关系组织句子：
- 并列关系直接写A和B；
- 轻重关系直接说明A比B更重要；
- 因果关系直接说明A导致B；
- 范围关系直接说明包含什么、不包含什么；
- 只有确实需要纠正误解时才使用对比句。
```

### 4.4 要求生成前检查

```text
输出前在内部检查：
- 是否使用报幕式开场；
- 是否评价了自己的表达方式；
- 是否频繁使用固定对比句；
- 是否有可以改成陈述句的假设问答；
- 是否机械使用“首先、其次、最后”；
- 是否重复总结或强行升华。

发现问题后先修改，只输出最终正文。
```

## 5. 完整提示词示例（19—22分钟）

教师展示：

```text
请根据提供的材料撰写标书中的“项目价值”章节。

语言要求：
1. 使用自然、克制、正式的专业中文。
2. 直接进入正文，不介绍你将如何回答。
3. 不评价自己的表达方式。
4. “不是……而是……”全文最多出现一次。
5. 不使用“真正的核心”“底层逻辑”“说白了”“归根结底”等表达。
6. 不使用“那么问题来了”“答案其实很简单”等假设问答。
7. 不机械使用“首先、其次、最后”，不为了形式整齐强行凑成三点。
8. 需要表达关系时，准确区分并列、因果、轻重、条件和范围。
9. 优先写清角色、动作、对象和结果。
10. 内容讲清楚后直接结束，不追加口号和升华。

输出前静默检查以上要求，修改后只输出正文。
```

教师补充一组正反例：

```text
不要这样写：
“真正重要的不是生成速度，而是生成质量。”

可以这样写：
“在专业文档场景中，内容准确性比生成速度更重要。”

不要这样写：
“那么问题来了，企业应该如何落地？答案其实很简单。”

可以这样写：
“企业落地前需要先确定使用场景、输入材料、审核责任和最低可用标准。”
```

教师说明：模型对具体示例通常比对抽象形容词更敏感。企业可以把经过确认的正反例直接纳入写作规则。

## 6. 现场练习与收束（22—25分钟）

请学员将下面的提示词改写成可执行版本：

> 请根据材料写一段专业、自然、有深度、没有AI味的项目介绍。

要求至少补充：

- 两条开场或句式限制；
- 一条替代规则；
- 一条输出前检查；
- 一条内容保护要求。

教师用一句话收束本节：

> “自然”是一种结果。提示词需要描述模型在句子层面应该做什么，以及哪些表达应该减少。

### 过渡到话题二

控制固定句式，只能解决通用AI腔。企业真正希望得到的结果，往往还要接近自己过去标书的结构和表达习惯。接下来讨论历史标书应该怎样提供给模型。

---

# 话题二：从历史标书中提取结构、文案和企业风格（25—50分钟）

## 1. 历史标书应该发挥什么作用（25—29分钟）

教师提问：

> 如果企业已经有几十份历史标书，是不是全部上传给模型，生成效果就会更好？

邀请学员回答后，教师说明本课的限定：

历史标书只用于三件事：

1. 学习文档结构；
2. 学习文案组织方式；
3. 学习企业语言风格。

历史标书不作为当前项目的事实依据，不向新标书提供：

- 历史客户和项目案例；
- 历史产品参数；
- 历史资质；
- 历史报价；
- 历史团队人数；
- 历史交付周期；
- 历史效果数据；
- 历史商务和服务承诺。

教师板书：

```text
招标文件：决定必须响应什么
当前企业资料：决定有哪些事实可以写
历史标书：决定怎样组织和表达
```

## 2. 为什么不直接上传完整历史标书（29—33分钟）

教师讲述：

直接把完整历史标书交给模型，容易出现四类问题：

1. 模型将旧客户、旧数据和旧承诺带进当前项目；
2. 不同标书中的名称、数字和写法互相冲突；
3. 大量无关内容占据上下文，真正需要参考的风格被稀释；
4. 模型大段复制历史文案，当前项目只是替换了几个名称。

所以历史标书需要先变成一个“写作参考库”。这项工作可以由模型完成初步整理，人工负责确认边界。

## 3. 从历史标书提取三类资产（33—40分钟）

### 3.1 结构模板

结构模板回答：一类标书通常由哪些章节组成，每一章负责什么。

示例：

```text
章节：项目实施方案

章节目的：
说明项目如何从启动进入交付和验收。

推荐结构：
1. 实施原则
2. 实施阶段
3. 里程碑计划
4. 交付物清单
5. 确认与验收节点

推荐形式：
- 阶段说明使用正文；
- 里程碑使用表格；
- 交付物使用清单。
```

结构模板中不保留原项目的90天、12人或某个客户名称。

### 3.2 文案模式

文案模式回答：一类内容通常按照什么顺序展开。

例如实施方案可以抽象为：

```text
阶段目标
→ 输入条件
→ 主要工作
→ 交付物
→ 责任角色
→ 确认方式
```

产品能力介绍可以抽象为：

```text
使用场景
→ 用户操作
→ 系统处理
→ 输出结果
→ 异常或限制
```

教师说明：文案模式保存的是组织方法，不保存原文句子。

### 3.3 企业风格规范

风格规范回答：企业希望文本呈现怎样的语言特征。

示例：

```text
- 使用正式、克制的书面语；
- 每段集中说明一个问题；
- 产品能力优先写成用户操作和系统响应；
- 表格前说明用途，表格后不重复复述全部内容；
- 不使用自媒体式设问；
- 不使用“赋能、引领、颠覆”等宣传词；
- 避免连续使用固定对比句；
- 不以口号结束章节。
```

## 4. 历史事实怎样退出参考材料（40—43分钟）

教师展示原句：

> 我司将组建12人的实施团队，在合同签订后90日内完成某市政务服务平台建设。

如果只做简单脱敏，可能得到：

> 我司将组建[团队人数]的实施团队，在合同签订后[项目周期]内完成[项目名称]建设。

这已经比保留原始事实安全，但仍然过于接近原句。进一步抽象后可以得到：

```text
表达模式：
实施主体＋团队配置原则＋时间要求＋交付目标
```

历史标书中的具体内容可以统一替换为：

```text
[客户名称]
[项目名称]
[产品名称]
[产品参数]
[项目周期]
[团队配置]
[案例材料]
[项目成果]
[资质材料]
```

教师强调：本课设定下，历史案例和历史事实不进入新项目的事实库。即使信息已经脱敏，也只用来分析结构和表达方式。

## 5. 历史标书结构化提示词（43—47分钟）

教师展示：

```text
请将以下历史标书处理成“结构与写作参考材料”。

使用边界：
历史标书只用于学习文档结构、文案组织方式和语言风格。
不得将客户、案例、数据、参数、资质、周期、人员、报价、成果或承诺提取为当前事实。

请完成：

一、提取结构模板
- 识别标题层级和章节顺序；
- 说明每个章节承担的写作任务；
- 总结每章推荐包含的内容；
- 记录适合使用正文、列表还是表格。

二、提取文案模式
- 分析每类章节的信息展开顺序；
- 将具体句子抽象为可复用的表达框架；
- 不大段保留历史标书原文。

三、提取风格规范
- 分析标题、句子、段落和表格的风格；
- 总结正式程度、术语习惯和语气特点；
- 识别重复、空泛、夸张和固定AI句式。

四、清除事实信息
- 删除客户、案例、数字、周期、参数、资质和承诺；
- 必要时使用通用占位符；
- 检查是否仍有可以识别原项目的信息。

输出：
1. 通用目录模板；
2. 章节写作卡；
3. 文案组织模式；
4. 企业写作风格规范；
5. 禁用或慎用表达；
6. 仍需人工检查的内容。
```

## 6. 小型演示（47—50分钟）

教师准备一段历史实施方案，分别让模型执行：

1. “参考这段文字写一段新项目实施方案”；
2. “先提取结构与文案模式，再根据当前项目资料生成”。

让学员比较：

- 哪一版更容易复制旧句子；
- 哪一版容易带入历史数字和承诺；
- 哪一版更容易替换成当前项目事实；
- 抽象后的模式是否仍保留了企业写法。

教师收束：

> 历史标书提供写法，当前企业资料提供事实。两者在产品中应当分开存放、分开调用。

### 过渡到话题三

即使企业风格已经确定，多个章节分别生成时，产品名称、模块名称和角色名称仍可能不断变化。下一步用一张精简的全局变量表控制称呼。

---

# 话题三：用全局变量表统一名称、称呼和术语（50—65分钟）

## 1. 三段文字中的称呼问题（50—53分钟）

教师展示：

> 启明智能服务平台采用私有化部署方式。

> AI客服系统包括智能问答、知识中心和运营分析能力。

> 机器人平台部署完成后，管理员可以在后台维护知识内容。

教师提问：

- 三个产品称呼是否指向同一个产品？
- “知识中心”是否就是“知识库管理模块”？
- “管理员”是否就是“平台运营人员”？
- 哪些词可以直接统一，哪些需要人工确认？

教师说明：

普通文章会主动寻找近义词，减少重复。专业文档中的项目名、产品名、模块名和角色名需要保持稳定。模型为了语言丰富而替换名称，反而会增加歧义。

## 2. 建立精简全局变量表（53—57分钟）

教师展示：

| 对象 | 标准写法 | 允许简称 | 禁止或待确认写法 |
| --- | --- | --- | --- |
| 招标人 | 某市政务服务管理局 | 招标人、贵方 | 甲方、客户、业主方 |
| 投标人 | 启明数科有限公司 | 启明数科、我方 | 乙方、供应商 |
| 项目名称 | 某市政务服务智能客服与知识库平台建设项目 | 本项目 | 政务AI项目 |
| 产品名称 | 启明智能服务平台 | 智能服务平台、本平台 | AI客服系统、机器人平台 |
| 核心模块 | 知识库管理模块 | 知识库模块 | 知识中心、知识中台 |
| 用户角色 | 平台运营人员 | 运营人员 | 管理员、后台人员 |
| 文档名称 | 技术投标文件 | 本文件 | 技术方案书、项目建议书 |
| 部署方式 | 私有化部署 | 无 | 本地化部署、云端部署 |

教师说明：

“禁止或待确认写法”表示这些表达在当前项目中可能引起歧义，不代表它们在所有项目中都错误。

全局变量表只承担称呼和术语统一。本节不要求它维护所有事实、数字和业务逻辑。

## 3. 全局变量表怎样建立（57—59分钟）

可以先让模型从招标文件和当前企业资料中提取候选项：

```text
请从材料中提取全文需要统一的名称和术语，包括：
- 招标人和投标人名称；
- 项目名称；
- 产品名称；
- 系统与模块名称；
- 用户角色；
- 文档名称；
- 部署方式；
- 重要专业术语。

输出：
| 对象类型 | 材料中的写法 | 建议标准写法 | 建议简称 | 其他写法 | 是否存在冲突 |

不要自行合并含义不明确的名称。
存在多个版本时标记为【待确认】。
```

模型提取候选项，项目负责人确认标准名称和允许简称，确认后的表格再进入生成流程。

## 4. 生成时怎样使用（59—62分钟）

教师展示使用规则：

```text
全文称呼必须遵守全局变量表。

1. 对象第一次出现时使用标准全称。
2. 后续只能使用标准全称或允许简称。
3. 不要为了避免重复而自行创造同义词。
4. 标题、正文、表格和图注使用同一套称呼。
5. 材料中的其他写法统一转换为标准写法。
6. 无法判断两个名称是否指向同一对象时，标记为【称呼待确认】。
7. 输出前检查本章中的名称和术语。
```

变量较多时，可以拆成：

- 每章都携带的公共变量；
- 只在相关章节使用的专业术语。

项目名、招标人、投标人和产品名属于公共变量；模块名和技术术语可以只传入相关章节。

## 5. 合并后的检查与练习（62—65分钟）

教师展示检查提示词：

```text
请检查以下文档中的名称和术语是否符合全局变量表。

检查范围：标题、正文、表格、图注和页眉页脚。

输出：
| 位置 | 当前写法 | 标准写法 | 修改建议 | 是否需要人工确认 |

规则：
1. 只检查名称、称呼和术语；
2. 不检查事实和内容逻辑；
3. 不修改名称和术语以外的内容；
4. 无法确定是否指向同一对象时，标记为【称呼待确认】；
5. 先输出问题清单，确认后再统一替换。
```

教师提醒：不要直接做简单的全文查找替换。“客户案例”中的“客户”不一定要改成“招标人”。模型需要结合上下文提出修改建议，含义不明确时交给人工确认。

教师收束：

> 先确定标准称呼，再把它作为公共变量带入每一次章节生成，最后进行一次全局检查。

### 过渡到话题四

前三个方法解决了生成前的控制。实际工作中，人工仍然会修改初稿。如果这些修改只留在当前段落，下一章还会重复同样的问题。接下来讨论怎样把修改经验变成后续生成规则。

---

# 话题四：把人工修改沉淀为后续生成规则（65—90分钟）

## 1. 为什么人工改过，模型下次还会再犯（65—68分钟）

教师展示：

### 模型初稿

> 通过引入先进的大模型技术，本平台将全面赋能招标人的知识服务体系。真正重要的不是简单提升问答效率，而是构建一个智能、高效、可持续演进的知识服务新模式。

### 人工修改

> 本平台使用大模型完成用户问题理解和候选答案生成，并通过企业知识库提供回答依据。知识库管理员负责审核和发布知识内容。

教师让学员说出人工做了哪些修改。

可能的答案：

- 删除“先进”“全面赋能”；
- 删除固定对比句；
- 删除多个抽象形容词；
- 将价值口号改成处理流程；
- 增加具体系统动作；
- 增加责任角色。

教师说明：

如果系统只保存修改后的段落，它知道最后写成了什么，却不知道用户为什么这样改。下一章仍可能生成“全面赋能”和“真正重要的不是”。

更有价值的做法是从修改前后提取候选规则：

```text
- 标书中不使用“赋能、引领、颠覆”等宣传词；
- 减少固定对比句；
- 描述产品能力时优先写用户动作、系统处理和责任角色；
- 避免连续使用多个抽象形容词。
```

## 2. 四种不同范围的写作记忆（68—73分钟）

教师展示：

| 范围 | 说明 | 示例 |
| --- | --- | --- |
| 单次修改 | 只影响当前位置 | 当前段落压缩到200字 |
| 章节规则 | 只适用于某类章节 | 实施方案按阶段、工作、交付物展开 |
| 项目规则 | 适用于当前标书 | 全文使用“招标人”，不使用“客户” |
| 企业规则 | 可用于后续多个项目 | 标书不使用“赋能、引领、颠覆” |

教师逐项解释：

### 单次修改

“把这一段缩短一半”通常只是当前编辑动作，不值得永久保存。

### 章节规则

“实施方案必须写清阶段、工作、交付物和确认节点”适用于实施方案，不一定适用于公司介绍。

### 项目规则

当前招标文件要求统一使用“招标人”，这是当前项目规则。换到商业客户方案时，可能仍然使用“客户”。

### 企业规则

企业长期不使用宣传性词汇，可以保存为标书写作规范，后续项目继续应用。

教师提醒：一次修改不一定代表长期偏好。系统应提出候选规则，由用户选择适用范围。

## 3. 哪些修改值得沉淀（73—76分钟）

教师展示分类：

| 修改类型 | 示例 | 建议处理 |
| --- | --- | --- |
| 风格偏好 | 删除“赋能” | 可形成候选规则 |
| 术语统一 | “客户”改成“招标人” | 进入项目规则或变量表 |
| 项目事实 | 周期从120日改为90日 | 更新项目资料，不作为风格规则 |
| 单句语病 | 调整一个句子的语序 | 通常不沉淀 |
| 临时要求 | 本章压缩到500字 | 只作用于当前任务 |
| 风险修正 | 删除无依据的强承诺 | 可形成风险写作规则 |
| 内容补充 | 增加当前项目验收要求 | 进入当前项目资料 |

教师提问：

> “增加知识库管理员负责审核”能不能直接变成企业长期写作规则？

教师说明：这更可能是当前方案中的角色事实。只有当企业希望所有能力描述都写清责任角色时，才可以抽象成“描述流程时说明责任角色”这类写作规则。

## 4. 从人工修改提取候选规则（76—81分钟）

教师展示另一组对比：

### 修改前

> 我司将为客户提供全面、高效、智能的知识服务能力。

### 修改后

> 我方将为招标人提供知识检索、知识审核和知识发布功能。

系统可以识别：

| 变化 | 可能原因 |
| --- | --- |
| 我司 → 我方 | 统一投标主体称呼 |
| 客户 → 招标人 | 统一招标文件术语 |
| 删除全面、高效、智能 | 删除无依据的连续形容词 |
| 知识服务能力 → 三项具体功能 | 使用具体功能替代抽象能力 |

对应的候选规则是：

```text
1. 当前项目使用“我方”，不使用“我司”。
2. 当前项目使用“招标人”，不使用“客户”。
3. 避免连续使用没有具体依据的抽象形容词。
4. 描述产品能力时优先列出具体功能或动作。
```

教师说明：前两条更适合进入项目变量表，后两条可以成为企业标书规则。一次修改同时可能产生不同类型的结果。

## 5. 候选规则提取提示词（81—84分钟）

```text
请比较人工修改前后的文本，分析修改者想解决什么问题，并提取可能复用的候选规则。

修改前：
【原文】

修改后：
【修改稿】

所在章节：
【章节名称】

当前已有规则：
【规则列表】

请完成：
1. 列出具体修改；
2. 判断每项修改的可能原因；
3. 将修改归类为：
   - 单次修改
   - 章节规则
   - 项目规则
   - 企业长期规则
   - 项目资料或变量更新
4. 只有具有复用价值的修改才生成候选规则；
5. 不要把具体项目事实错误地抽象成长期规则；
6. 一次修改不足以确定长期偏好时，标记为“建议观察”；
7. 检查候选规则是否与已有规则重复或冲突。

输出：
| 修改内容 | 修改原因 | 修改类型 | 候选规则 | 建议范围 | 置信度 | 是否需要确认 |
```

## 6. 用户确认与规则优先级（84—87分钟）

系统识别候选规则后，应让用户选择：

- 只修改当前位置；
- 应用于当前章节；
- 应用于当前项目；
- 保存为企业写作规范；
- 不保存。

教师说明规则优先级：

```text
当前章节明确要求
> 当前项目规则
> 文档类型规则
> 企业长期规则
> 通用语言规则
```

例如企业平时使用“客户”，当前招标文件要求使用“招标人”，当前项目规则优先。

再如企业要求段落尽量不超过150字，但法律条款必须完整引用。当前章节的完整引用要求优先。

## 7. 规则治理与课堂收束（87—90分钟）

规则库不能无限增长。系统需要定期处理：

- 重复规则；
- 含义相同但措辞不同的规则；
- 新旧冲突规则；
- 已经过期的称呼；
- 只发生一次的低价值偏好；
- 用户经常撤销的规则。

规则应当具体、可执行。

无效规则：

> 写得更自然。

可执行规则：

> 不使用自问自答式开场，直接陈述结论和依据。

教师用流程收束：

```text
人工修改
→ 比较修改前后
→ 分析修改原因
→ 提取候选规则
→ 用户确认适用范围
→ 用于后续生成
→ 根据后续修改继续校准
```

这项能力可以称为“项目级写作记忆”。它让系统逐渐适应企业的称呼、风格和表达习惯，同时保留人工控制。

# 综合练习：组合四种文本控制（90—100分钟）

## 1. 练习材料

教师提供：

1. 一段当前项目说明；
2. 一段历史标书样例；
3. 一份包含多种称呼的模型初稿；
4. 一份人工修改稿。

## 2. 学员任务

每组完成：

1. 写出三条减少AI固定句式的生成规则；
2. 从历史标书中提取一个章节结构和一个文案模式；
3. 建立至少五项全局变量；
4. 从人工修改中提取两条候选规则；
5. 标明候选规则属于章节、项目还是企业范围；
6. 使用以上材料重新生成一段150—250字的项目方案。

## 3. 展示与点评

教师点评时重点检查：

- 风格规则是否具体可执行；
- 历史参考中是否仍夹带旧项目事实；
- 全局变量是否区分标准名称和允许简称；
- 人工修改是否被错误抽象成长期偏好；
- 新生成内容是否同时遵守四类约束。

# 全课收束与作业（100—105分钟）

## 1. 回看四层控制

| 控制层 | 解决的问题 | 主要产物 |
| --- | --- | --- |
| 固定句式控制 | 减少机械AI表达 | 风格提示词 |
| 历史写法参考 | 继承企业结构和表达习惯 | 结构模板、文案模式、风格规范 |
| 全局变量控制 | 统一名称、简称和术语 | 全局变量表 |
| 写作规则记忆 | 减少重复人工修改 | 项目规则与企业规则 |

教师板书完整流程：

```text
从历史标书提取写法
→ 建立当前项目全局变量
→ 使用风格提示词生成内容
→ 人工修改
→ 提取并确认候选规则
→ 后续章节自动应用
```

## 2. 课后作业

学员回到自己的个人项目三，提交以下材料：

1. 一份适用于项目的风格提示词；
2. 一份历史写作参考，至少包含一个结构模板和两条风格规范；
3. 一张包含5—10项内容的全局变量表；
4. 一组人工修改前后对比；
5. 从修改中提取的两条候选规则；
6. 使用新规则生成的一段修改后内容。

## 3. 作业验收标准

| 维度 | 验收问题 |
| --- | --- |
| 风格规则 | 是否具体到句式和行为，而非只写“自然、专业” |
| 历史参考 | 是否只保留结构、文案模式和风格 |
| 事实边界 | 是否清除了历史案例、数据和承诺 |
| 全局变量 | 是否定义标准写法、简称和待确认写法 |
| 规则提取 | 是否解释了人工修改的原因 |
| 适用范围 | 是否区分单次、章节、项目和企业规则 |
| 生成结果 | 后续内容是否明显减少同类问题 |

## 4. 教师结束语

模型生成专业长文档时，质量控制不应只发生在最后一次人工校对。企业可以在生成前定义语言风格，使用历史标书提供写法，用全局变量稳定称呼，再把人工修改逐步沉淀成规则。

这样做的目标很实际：同一个问题不需要人工反复修改，后续章节能够逐渐接近企业已经确认的写作方式。
