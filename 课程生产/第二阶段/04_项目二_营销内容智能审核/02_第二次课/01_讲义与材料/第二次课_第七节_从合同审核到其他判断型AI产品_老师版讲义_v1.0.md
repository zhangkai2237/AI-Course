# 从合同审核到其他判断型 AI 产品

建议用时25分钟。先用法律合同审核还原一套完整的企业内部 AI 项目方法，再现场迁移到客服会话质检，最后让学员把方法迁移到招聘信息、发票报销或金融营销场景。本节讲产品设计与工作流拆解，不提供法律、财务或金融专业结论。案例、角色和业务数据均用于课堂推演。

## 本节任务

完成本节后，学员应当能够：

1. 说明合同审核案例为什么不是“上传文件后让模型看一遍”；
2. 从人工工作中拆出输入、输出、并行任务和异常分支；
3. 区分通用模型能力与企业内部业务能力；
4. 使用同一套方法迁移到另一个判断型业务场景；
5. 说明哪些环节可以由系统辅助，哪些环节必须保留人工责任。

## 时间安排

| 时间 | 内容 | 课堂产出 |
| --- | --- | --- |
| 0—2分钟 | 从本项目过渡到合同审核 | 明确为什么要学习迁移 |
| 2—10分钟 | 合同审核母案例 | 一条完整项目主线 |
| 10—13分钟 | 提取迁移方法 | 十一步迁移框架 |
| 13—19分钟 | 现场迁移客服质检 | 一张迁移后的流程草图 |
| 19—24分钟 | 小组迁移练习 | 招聘、报销或金融场景方案 |
| 24—25分钟 | 收束 | 判断型 AI 产品的共同结构 |

## 一 从营销审核过渡到合同审核（0—2分钟）

### 教师讲述

前面两次课，我们一直围绕营销内容智能审核展开。我们先理解业务流程，再定义审核点，分配规则、模型、业务资料和人工的职责，最后把系统放进自检、正式审核和历史巡检三个环节。

现在要回答一个更重要的问题：如果离开营销审核，这套方法还能不能使用？

如果只能把“营销文案”换成“招聘文案”，把页面标题改一下，这不叫迁移。真正的迁移，是进入另一个业务以后，仍然能够重新完成业务分析、任务拆解、能力分工、异常设计和试用判断。

我们先不直接列举行业。先看知乎第5课中的合同审核案例，因为它完整展示了一项企业内部 AI 产品怎样从一个小问题开始，逐步变成可以运行的工作流。

### 课堂提问

> 如果让你做一个“AI法务”，你会从哪里开始？

学员可能会回答：建立法律知识库、做合同审核、做法律咨询、查询案例或生成合同。

### 教师收束

这些都可能成立，但范围太大。产品真正开始时，要先选择一个足够具体、能够验证的任务。合同案例没有试图做完整法律系统，而是选择企业里高频、结构相对明确的合同初步审核。

板书：

```text
不是先问 AI 能做什么
而是先问企业中哪一段工作值得被重新设计
```

## 二 合同审核母案例（2—10分钟）

### 1 为什么企业需要合同审核工具（2—3分钟）

### 教师讲述

很多企业都需要处理合同，但不同企业的法务能力差异很大。小公司不一定愿意承担完整法务团队和长期外部顾问的成本；已经有法务的公司，也可能面对合同数量多、基础审核重复、外部信息查询容易遗漏等问题。

这不意味着模型可以替代专业律师。它说明的是：合同审核中存在一部分结构相对明确、重复出现、适合先做辅助处理的工作。

因此，项目边界可以写成：

> 面向企业内部业务人员和法务人员，为常规业务合同提供初步检查、问题定位和修改建议；复杂争议、重大风险与最终决定仍由专业人员负责。

这里已经完成了第一个重要判断：不做诉讼、不做完整法律咨询，也不把系统包装成自动作出最终法律决定的工具。

### 2 人工原来怎样审核合同（3—4分钟）

先跟法务人员了解，一份合同通常需要关注什么。

| 人工审核对象 | 要回答的问题 |
| --- | --- |
| 合同主体 | 和谁签约，主体信息是否完整，对方公司是否存在异常 |
| 合同条款 | 权利义务是否清楚，付款、交付、验收和违约条款是否合理 |
| 法律引用 | 合同引用的规范是否仍然适用，引用是否准确 |
| 履约方式 | 交付时间、付款条件、验收标准和责任是否能够实际执行 |
| 周边风险 | 对方历史履约、企业异常、内部关联和其他业务风险 |

教师强调：这一阶段还没有讨论模型、知识库或者工作流节点。先把人类工作说清楚。

### 课堂提问

> 如果只把合同全文交给模型，并要求“全面审核”，最容易出现什么问题？

教师参考：输出标准不稳定；不同类型问题混在一起；遗漏外部公司信息；不知道使用哪个版本的内部要求；结果看起来专业，但很难确认是否覆盖了需要检查的内容。

### 3 从最终输出反推输入（4—5分钟）

合同审核最终不能只输出“有风险”或者一个总分。业务人员和法务需要看到：

- 问题所在条款；
- 问题类型；
- 为什么需要关注；
- 可能产生的业务影响；
- 建议怎样修改；
- 哪些内容仍需人工确认。

要得到这些输出，输入也不能只有合同文件。

| 输入 | 作用 |
| --- | --- |
| 合同正文 | 确定本次审核对象 |
| 本次审核重点 | 告诉系统本次特别关注付款、交付、知识产权或其他部分 |
| 企业合同规则 | 提供公司内部可接受的条款范围与模板要求 |
| 对方企业信息 | 辅助判断签约主体和外部风险 |
| 业务上下文 | 说明交易关系、合作历史、时间要求和谈判空间 |

教师讲述：这一步是“以终为始”。先决定最终需要怎样的审核意见，再反推每一项判断需要什么输入。

### 4 先做基础能力验证（5—6分钟）

在搭建完整工作流之前，可以先选择一份已脱敏合同，用能力较强的模型完成一轮快速测试，再请法务人员评价输出。

测试重点不是看文字是否流畅，而是看：

- 能否定位到真实条款；
- 能否发现付款、交付、验收等明显矛盾；
- 修改建议是否可以理解；
- 有没有把正常商业安排一律判成风险；
- 有没有编造不存在的内容；
- 对不确定问题是否知道交给人工。

合同案例中，一个很有价值的评价是：模型像一个认真、基础能力不错，但缺少实际商业经验的法务实习生。

### 教师收束

这个评价不是否定项目。它帮助我们准确确定产品位置：

> 模型可以先完成覆盖面较广的初步检查，但不能直接替代熟悉公司业务和谈判背景的法务负责人。

### 5 把人工分工拆成并行流程（6—8分钟）

当基础能力可用后，再把任务拆成多个清晰分支。

```text
上传合同与本次审核要求
          ↓
读取文件并确认是可处理的合同
          ↓
 ┌────────┼────────┐
 │        │        │
常规条款  法律引用  签约主体与企业风险
审核      检查      查询
 │        │        │
 └────────┼────────┘
          ↓
问题合并、去重与分级
          ↓
形成审核意见和修改建议
          ↓
法务人员确认
```

这三条路线模拟的是一个团队的分工：

- 一个人负责合同条款；
- 一个人负责法律引用；
- 一个人负责查询对方企业；
- 最后由负责人汇总。

教师强调：并行拆分不是为了让工作流看起来复杂，而是为了让每条路线目标明确、输入明确、结果可以单独检查。

### 6 补齐边界条件（8—9分钟）

正常合同只是其中一种输入。系统还要处理：

| 边界情况 | 产品动作 |
| --- | --- |
| 上传的不是合同 | 终止审核，提示重新上传正确文件 |
| 合同无法读取 | 标记解析失败，保留原文件并给出下一步 |
| 缺少签约主体 | 形成明确缺项，不继续猜测主体身份 |
| 企业名称查询不到 | 显示“暂未查询到”，不直接判断对方为虚假企业 |
| 外部接口失败 | 保留其他已完成结果，该分支进入重试或人工查询 |
| 多路结果重复 | 按条款位置和问题类型合并，保留各分支原始记录 |
| 结果发生冲突 | 标记冲突并交给法务确认 |

### 教师讲述

边界条件决定了产品是否可以交给真实用户。系统不能因为平时很少收到缺主体合同，就假设这种输入永远不会出现。

### 7 从通用能力升级为企业能力（9—10分钟）

如果产品只检查通用法律和条款，它很难超过市场上的专业工具。企业内部项目的特殊价值来自与本公司业务连接。

例如把合同交付条款连接到：

- ERP订单；
- 库存和生产排期；
- 资金计划；
- 历史履约记录；
- 供应商名录；
- 内部黑名单和关联关系。

一份合同要求30天交付，单看条款可能没有明显问题。但如果生产线已经接近满负荷，原材料也无法按时到货，这项条款就可能带来实际履约风险。

合同案例最终给出的启发是：

> 企业内部 AI 产品不一定要比专业垂直模型更懂法律，而要比通用工具更懂这家公司的业务。

## 三 提取十一项迁移框架（10—13分钟）

教师把合同案例收束成一套可以带走的方法。

| 步骤 | 要回答的问题 |
| --- | --- |
| 1 业务问题 | 企业为什么现在需要解决它 |
| 2 小场景 | 从大业务中先选择哪一段 |
| 3 人工工序 | 人原来按什么顺序完成 |
| 4 最终输出 | 用户最终需要看见什么并执行什么动作 |
| 5 输入来源 | 完成判断需要哪些文件、数据和上下文 |
| 6 快速验证 | 当前模型是否具备基础能力 |
| 7 并行拆分 | 哪些工作适合分开执行 |
| 8 边界分支 | 缺项、失败、冲突和版本变化怎样处理 |
| 9 结果合并 | 多路结果怎样去重、分级并交给人 |
| 10 企业连接 | 接入哪些内部系统才能形成特殊价值 |
| 11 运行验证 | 用什么结果决定继续、修改或缩小范围 |

### 板书

```text
业务问题
→ 人工工序
→ 输出与输入
→ 能力验证
→ 并行流程
→ 异常分支
→ 企业系统
→ 运行验证
```

### 教师过渡

接下来不再重新发明一套方法。我们直接把这十一项迁移到客服会话质检。

## 四 现场迁移到客服会话质检（13—19分钟）

### 1 先给出业务问题（13—14分钟）

某电商平台每天产生大量售后对话，主管只能抽查少量会话。部分客服存在错误承诺、没有核对订单状态、前后口径不一致或服务态度不当等问题。

第一版不做完整客服管理系统，只选择：

> 售后退款会话的智能质检。

### 2 给出一段对话（14—15分钟）

> 客户：退款什么时候能到账？  
> 客服：肯定今天到账，您放心。  
> 客户：昨天另一个客服说需要三个工作日。  
> 客服：反正系统已经处理了，具体您自己等着吧。

课堂提问：如果你是质检主管，会检查哪些内容？

教师参考：是否完成身份或订单核验；是否错误承诺到账时间；是否查询当前订单状态；是否解释口径差异；是否存在推诿；客户情绪是否升级。

### 3 按合同案例的方式完成迁移（15—17分钟）

| 合同审核 | 客服质检 |
| --- | --- |
| 合同文件 | 对话文本或通话录音 |
| 法务人员 | 质检主管 |
| 合同条款 | 客服话术与处理动作 |
| 法律引用 | 服务制度和标准口径 |
| 企业信息 | 订单、退款和客户状态 |
| 审核意见 | 质检问题、等级和改进建议 |
| 法务确认 | 主管复核与客服申诉 |

需要的输入包括：

- 会话内容和说话人角色；
- 订单与退款状态；
- 当前服务政策；
- 本次质检规则；
- 客服所属团队和必要的历史记录。

并行流程可以拆成：

```text
导入会话或录音
       ↓
转写、分句与角色区分
       ↓
┌────────┼────────┐
│        │        │
流程规则  多轮语义  订单与政策
检查      判断      核对
│        │        │
└────────┼────────┘
       ↓
问题合并与风险分级
       ↓
主管复核、客服确认或申诉
       ↓
进入培训与规则改进
```

### 4 补齐客服场景的边界条件（17—18分钟）

| 边界情况 | 产品动作 |
| --- | --- |
| 录音无法转写 | 标记转写失败，不能继续假装完成质检 |
| 客户与客服角色混淆 | 暂停对应判断，允许人工修正角色 |
| 订单接口没有返回 | 保留话术检查结果，业务事实检查待完成 |
| 否定句被关键词误报 | 引入上下文确认并进入测试样本 |
| 主管与机器结论不同 | 保留双方结论及调整理由 |
| 客服提出申诉 | 进入复核流程，不直接覆盖原始记录 |

### 5 接入企业内部系统（18—19分钟）

通用模型能够判断语气和语义，但真正的企业能力来自：

- CRM；
- 订单系统；
- 工单系统；
- 客服知识库；
- 投诉记录；
- 培训和质检系统。

教师收束：合同案例里连接ERP、财务和供应商数据，客服场景里连接订单、工单和服务政策。变化的是业务对象，不变的是产品方法。

## 五 小组迁移练习（19—24分钟）

### 练习要求

全班分成三组，每组选择一个场景。3分钟设计，2分钟快速分享。每组只回答八个问题：

```text
1 业务问题是什么
2 第一版选择哪个小场景
3 人工原来怎样完成
4 最终输出是什么
5 需要哪些输入和业务资料
6 可以拆成哪几条并行路线
7 哪些情况必须转人工
8 接入什么企业系统后才有特殊价值
```

### A组 招聘信息审核

课堂材料：

> 高薪招聘运营经理，月入2万元起。限男性，30岁以下，本地户口。无经验也可以，面试通过即可入职。需先参加公司指定培训，培训费用可以办理分期。

教师参考：

| 项目 | 参考方向 |
| --- | --- |
| 业务问题 | 招聘信息数量多，完整性、真实性和发布质量难管理 |
| 小场景 | 企业发布岗位前的信息审核 |
| 人工工序 | 查企业、查岗位、查薪资、查必填项、查限制条件 |
| 输出 | 缺项、问题位置、风险类型、修改要求和是否转人工 |
| 输入 | 招聘文案、企业信息、岗位编制、薪酬范围、有效期 |
| 并行路线 | 文案与必填项、企业资质、岗位资料一致性 |
| 人工条件 | 企业或岗位无法确认、信息冲突、疑似异常引流 |
| 企业连接 | 招聘系统、企业名录、岗位编制、薪酬系统、投诉记录 |

### B组 发票与报销审核

课堂材料：

> 技术部门员工提交一张周末产生的高额休闲服务发票，备注为客户招待；报销金额在个人权限内，但OA中没有对应招待申请，部门预算也接近用完。

教师参考：

| 项目 | 参考方向 |
| --- | --- |
| 业务问题 | 财务需要反复核票、查预算、查合同和查审批流程 |
| 小场景 | 员工费用报销初步审核 |
| 人工工序 | 验票、核科目、核金额、查人员、查预算、查审批 |
| 输出 | 通过、驳回、待补材料、等待预算或人工复核 |
| 输入 | 发票、报销单、员工、部门、预算、合同和OA记录 |
| 并行路线 | 票据验真、报销政策、预算、合同与审批核对 |
| 人工条件 | 科目与业务矛盾、异常人员、预算冲突或多路结论不一致 |
| 企业连接 | 财务系统、OA、预算、合同系统和付款系统 |

### C组 金融营销材料审核

课堂材料：

> 稳健理财，年化收益6%。本金安全，无需承担市场风险。历史表现优秀，适合所有投资者。

教师参考：

| 项目 | 参考方向 |
| --- | --- |
| 业务问题 | 宣传内容需要与正式产品材料、风险提示和适用人群保持一致 |
| 小场景 | 一类理财产品宣传材料发布前审核 |
| 人工工序 | 查宣传表达、查产品文件、查风险提示、查适用人群和版本 |
| 输出 | 问题位置、缺失信息、风险等级、修改要求和人工结论 |
| 输入 | 宣传材料、正式产品文件、风险提示、目标人群和渠道要求 |
| 并行路线 | 明确表达检查、产品事实核对、风险披露完整性 |
| 人工条件 | 高风险承诺、材料冲突、适用人群不清或系统结论冲突 |
| 企业连接 | 产品中心、合规系统、客户分层、渠道发布和版本管理 |

### 教师点评原则

不要只评价学员是否想到了很多功能。重点检查：

1. 场景是否足够小；
2. 人工工序是否具体；
3. 输出是否能够推动下一步动作；
4. 输入是否包含业务事实，而不只有待审核文本；
5. 并行路线是否来自真实分工；
6. 人工接管条件是否明确；
7. 企业内部连接是否真的改变判断质量。

## 六 本节收束（24—25分钟）

### 教师讲述

今天不是让大家记住四个行业案例，而是掌握一套迁移方法。

合同审核告诉我们：先理解法务怎样工作，再把条款、法律引用和企业风险拆开处理；客服质检告诉我们：同样的方法可以迁移到多轮对话、订单和服务政策；招聘、报销和金融材料则进一步说明，不同行业的输入、责任人和自动化边界都不同。

真正可迁移的不是页面，而是下面这条主线：

```text
理解业务问题
→ 拆解人工工序
→ 定义输出与输入
→ 验证基础能力
→ 设计并行工作流
→ 补齐异常和人工承接
→ 连接企业内部系统
→ 用实际运行决定下一步
```

最后强调两句话：

1. 通用模型提供基础判断能力，企业数据和业务流程决定产品是否真正可用。
2. 迁移不是更换行业名称，而是在新业务中重新完成一次完整的产品判断。

## 教师备课补充

### 授课边界

- 合同、报销、招聘和金融案例用于产品设计教学，不作为相应专业意见；
- 不让学员讨论某个具体条款最终是否合法，重点讨论系统需要什么输入、怎样分工和何时交人；
- 合同案例中的模型定位是初步审核助手，不能替代法务负责人；
- 高风险业务中，系统可以辅助定位和核对，但最终责任仍需明确到人。

### 节奏控制

- 合同案例最多讲8分钟，重点是项目方法，不展开法律专业知识；
- 客服质检必须现场完成一次映射，让学员看到迁移过程；
- 小组练习不追求完整PRD，每组只回答八个问题；
- 如果时间不足，金融营销组可以作为教师口头补充，保留招聘和报销两个小组；
- 如果学员讨论技术实现过多，立即拉回“人工原来怎样做、最终谁使用结果”。

### 参考材料

主要参考知乎AI课程正课第5课关于企业内部降本增效、合同审核工作流、招聘和发票审核的讲解。合同案例迁移框架、客服质检案例与本节课堂活动为本课程重新组织的教学内容。

### 本节课堂产出

学员应当至少完成一张业务迁移草图，包含：

- 一个具体业务问题；
- 一个第一版小场景；
- 三至五步人工工序；
- 输入和输出；
- 两至三条并行路线；
- 两个异常分支；
- 一个人工承接点；
- 一个需要连接的企业系统。
