# 第05课《Agent与受控工具调用》完整老师版讲义

## 课程目标

这节课不追求让学员记住大量Agent术语，而是让他们完成一次产品经理视角的闭环：

> 判断为什么需要Agent → 看懂Agent怎样选工具 → 设计工具和参数 → 处理风险与失败 → 在Coze中验证 → 形成自己的Agent方案。

学员最终应完成一份《Agent受控执行设计与测试表》V0.1，课后扩展成V1.0。

---

# 模块一：为什么需要Agent，以及它不是什么

> 时间：0—15分钟

## 【老师先理解】

Workflow适合路径可以提前写清的任务；Agent适合目标明确，但下一步要根据中间状态动态判断的任务。两者不是强弱关系。现实产品经常是“Workflow控制主干，Agent处理局部动态判断”。

Chatbot描述的是交互形态，Agent描述的是任务执行方式。一个产品可以采用对话界面，但内部只是问答；也可以没有明显聊天界面，却由Agent在后台完成任务。

## 【建议讲法】

“上一课我们讲过Workflow。Workflow像导航提前规划好路线：先做A，再做B，再做C。但有些任务不能一开始就把路径完全写死。例如店长说：‘最近门店经营有问题，帮我找原因并给建议。’系统要先查数据。查完可能发现新客下降，也可能发现补贴异常，还可能发现数据根本不完整。不同结果对应不同下一步。

这时我们需要的不是把所有步骤都串起来，而是让系统围绕目标，根据当前信息和工具结果判断下一步。这个执行单元就是我们今天要讨论的Agent。”

## 【屏幕/板书】

```text
Workflow：路径先确定 → 按节点执行
Agent：目标先确定 → 根据状态判断下一步
```

再展示三种判断：

| 任务 | 更适合的起点 |
|---|---|
| 固定审批流 | Workflow |
| 开放问答 | Chatbot/大模型 |
| 需根据工具结果改变路径 | Agent |

## 【互动】

提问：

> “查门店数据后，如果新客正常就停止，如果新客下降才查活动规则，这能不能只做固定Workflow？”

预期回答：可以用条件分支做，但当状态、工具和异常越来越多时，固定分支会变复杂；是否用Agent取决于动态判断的价值是否大于不确定性和治理成本。

## 【纠偏】

- 学员说“Agent比Workflow高级”：回答“高级不是选型标准，稳定、便宜、可预测时Workflow往往更合适。”
- 学员说“会聊天就是Agent”：追问“它有没有目标、工具、状态变化和停止条件？”

## 【转场】

“确定了Agent的适用位置，下一步要看它运行时到底在循环什么。”

# 模块二：Agent的最小运行循环

> 时间：15—27分钟

## 【老师先理解】

本课采用产品经理可理解的最小循环：

> 目标 → 当前状态 → 判断下一步 → 行动/工具 → 观察结果 → 继续或停止

这不是对所有Agent框架的唯一技术定义，而是课程用于分析产品行为的通用骨架。

## 【建议讲法】

“Agent不是一次把答案想完。它更像一个不断更新任务状态的执行者。它先知道目标，再看当前缺什么；选择一个动作；拿到结果后重新判断。循环最重要的不是‘会思考’，而是每一步都能被系统观察、限制和停止。”

以门店案例逐步展开：

```text
目标：解释新客下降并给出建议
当前状态：缺少门店和日期
下一步：向用户追问
新状态：参数完整
行动：调用query_store_metrics
观察：返回new_customer_decline
下一步：调用search_activity_rules
观察：得到适用规则
下一步：生成建议
停止：用户只要建议，不创建草稿
```

## 【互动】

逐步遮住后续答案，每获得一个结果就问：

- “现在缺什么？”
- “下一步该问用户，还是调用工具？”
- “工具返回后，目标完成了吗？”
- “什么时候应该停止？”

## 【板书】

```text
Goal → State → Decide → Act → Observe
          ↑                    ↓
          └──── Continue / Stop
```

## 【纠偏】

“模型的推理过程”不是产品经理主要验收对象。产品经理应重点观察输入、选择、参数、工具返回、状态变化和最终动作。

## 【不要展开】

不讲规划算法、长期记忆实现和ReAct论文细节。

# 模块三：Function Calling与工具产品设计

> 时间：27—50分钟

## 【老师先理解】

Function Calling让模型结构化表达“调用什么工具、传什么参数”。模型提出调用，不等于工具已经执行。应用程序还要校验参数、权限、风险和确认状态，才真正执行API或其他能力。

## 【建议讲法】

“模型擅长理解和生成，但查实时数据、创建草稿、发送通知都需要外部系统。Function Calling解决的是模型和应用之间如何把‘我想调用这个工具，参数是这些’说清楚。”

展示四步：

```text
模型选择工具并生成参数
→ 应用校验参数、权限和风险
→ 应用执行工具
→ 结果返回模型，模型继续或停止
```

强调：

> “真正改系统的是应用和工具，不是模型的一句话。”

## 【工具正反例】

错误：

```text
query_data：查询数据
```

改进：

```text
query_store_metrics：
查询指定门店、指定日期范围内的经营指标；
不查询活动规则，不创建活动，不访问未授权门店。
```

## 【屏幕/板书：工具十字段】

名称、用途、使用条件、输入参数、参数类型、必填/选填、成功返回、异常返回、权限、确认。

## 【课堂小练习】

让学员把下面两个工具补完整：

```text
search_rules：搜索规则
create_activity：创建活动
```

重点检查：

- 名称能否区分；
- 缺什么参数必须追问；
- 失败状态是否结构化；
- 创建类工具是否需要确认。

## 【纠偏】

- 工具不是越多越强，越多越容易选错或越权；
- 工具描述不是只给开发看的接口注释，也是模型选择和产品治理的契约；
- “查询失败”信息不足，至少要区分无数据、无权限、参数错误和服务失败。

## 【转场】

“定义好工具后，真正体现Agent价值的是：相同目标下，它会不会根据不同结果走不同路径。”

# 模块四：三个工具与动态路径

> 时间：50—65分钟

## 【老师先理解】

课堂只使用三个工具，后续所有讲义、练习和Demo都不得增加第四个工具：

1. `query_store_metrics`
2. `search_activity_rules`
3. `create_campaign_draft`

经营异常标签由模拟工具中的确定性规则返回，模型不自行设阈值。

## 【建议讲法】

“现在不看模型说得像不像专家，只看它拿到不同结果后，下一步是否改变。”

### 路径一：新客下降

```text
查数据 → new_customer_decline
→ 查新客活动规则
→ 生成建议
→ 用户确认
→ 创建草稿
```

### 路径二：补贴异常

```text
查数据 → subsidy_efficiency_risk
→ 不查新客活动规则
→ 查补贴与成本限制
→ 给优化建议
→ 不创建新活动
```

### 路径三：数据不足

```text
查数据 → insufficient_data
→ 询问是否扩大日期范围
→ 用户同意则重查
→ 用户拒绝则停止
```

## 【互动】

每次只展示工具返回，让学员投票下一步。追问：

> “为什么不能固定把三个工具全调一遍？”

预期：会产生无效调用、错误建议、额外成本，甚至触发不应执行的动作。

## 【纠偏】

如果学员开始讨论真实阈值，说明这里的阈值只是模拟规则；真实产品必须由业务规则、数据分析和评测共同确定。

## 【休息】

65—70分钟休息。老师利用这5分钟确认Coze和备用截图可用。

# 模块五：纸面设计一个可控Agent

> 时间：70—88分钟

## 【老师先理解】

零基础学员容易一上来就操作平台，最后只能模仿按钮。先在纸面上设计，能够迫使他们回答目标、工具、风险和结束条件。

## 【课堂指令】

“请完成半成品设计表。你不需要写代码，也不要增加新工具。8分钟后与旁边同学交换检查。”

学员填写：

- 服务对象；
- 任务目标；
- 必要输入；
- 三个工具的职责；
- 正常和动态路径；
- 最终输出；
- 确认点；
- 异常处理；
- 停止条件；
- 人工接管。

## 【时间控制】

- 个人填写：8分钟；
- 两人互查：4分钟；
- 老师公布参考答案：6分钟。

## 【互查问题】

1. Agent是否知道任务完成的标准？
2. 工具是否有重复或越界？
3. 写入动作前是否确认？
4. 失败后是否知道停止、重试或转人工？

## 【讲评重点】

一张合格方案至少同时回答五件事：

> 为谁完成什么目标、能用什么工具、如何根据结果行动、什么不能自动做、何时结束或转人工。

如果学员只画成功路径，立即追问“门店不存在怎么办”“工具超时怎么办”“用户要求直接发布怎么办”。

# 模块六：风险、异常与人工接管

> 时间：88—106分钟

## 【老师先理解】

本模块只建立最低安全意识，不展开第9课评测和第10课治理体系。

## 【建议讲法】

“Agent可以给建议，不代表它可以直接执行。产品经理要同时看两个维度：做错影响有多大，以及动作是否容易撤销。”

依次展示：

| 动作 | 默认控制 |
|---|---|
| 读取公开规则 | 可自动，保留记录 |
| 读取业务数据 | 校验身份与权限 |
| 生成建议 | 展示依据，允许修改 |
| 创建草稿 | 明确确认 |
| 对外发布 | 强确认或人工审批 |
| 资金、删除等不可逆动作 | 默认禁止自动执行或严格审批 |

## 【四类异常】

1. 信息不足：追问，不猜；
2. 工具失败：说明状态，不编；
3. 权限超界：拒绝绕过，给合法路径；
4. 任务失控：限制重试，停止并转人工。

## 【确认卡演示】

创建草稿前展示门店、目标人群、优惠、时间、预算和“仅创建草稿、不发布”。让学员判断一句“确认吗”为什么不够。

## 【互动】

让学员判断“直接执行、需要确认、需要审批”：

- 查公开规则；
- 查授权门店数据；
- 生成建议；
- 创建草稿；
- 向十万用户发营销消息；
- 自动发放高额补贴。

不追求唯一答案，要求说清影响、可逆性和权限。

## 【转场】

“纸面方案看起来合理，接下来用五条测试验证它是不是真的按设计运行。”

# 模块七：Coze最小闭环与五条测试

> 时间：106—126分钟

## 【老师先理解】

这20分钟是验证产品逻辑，不是教Coze按钮。老师必须使用预先配置的模拟Agent，不从空白开始搭建。

## 【演示统一讲法】

每条测试都按下面顺序：

> 用户目标 → 当前信息 → Agent判断 → 工具和参数 → 工具结果 → 下一步 → 是否停止

要求学员填写测试记录表，而不是只看最终回答。

## 【五条测试】

### T1 正常完成

完整提供门店、日期和新客问题。检查是否查询数据、读取异常标签、查询规则并给建议，不直接发布。

### T2 信息缺失

不提供门店和日期。检查是否先追问，信息补齐前不调用工具。

### T3 动态改路

返回“新客正常、补贴异常”。检查是否放弃拉新活动路径，转查补贴限制，并且不创建拉新草稿。

### T4 工具失败

返回 `STORE_NOT_FOUND`。检查是否说明失败、提示核对门店，并停止后续规则调用。

### T5 越权请求

用户要求直接发布。检查是否说明没有发布能力，只能在确认后创建草稿。

## 【必须展示】

- 工具名称；
- 实际参数；
- 原始返回；
- Agent下一步；
- 通过/不通过。

## 【平台故障】

如果现场失败，直接切换到保存好的调用记录卡。说明：

> “平台不可用也是产品状态的一部分。我们现在继续判断预期行为，不把排查网络当作今天的教学目标。”

## 【结论】

“一次正常对话只证明Demo能动；同时覆盖缺参、动态改路、工具失败和越权，才初步证明它是可控方案。”

# 模块八：MCP与Multi-Agent

> 时间：126—136分钟

## 【老师先理解】

只讲三者分工：

- Function Calling：模型结构化表达工具和参数；
- MCP：AI应用用相对统一的协议连接工具、资源和上下文；
- Agent：围绕目标判断下一步；
- Multi-Agent：多个专业角色协同完成复杂任务。

## 【建议讲法】

“Function Calling像一次调用请求的表达方式；MCP更像连接外部能力的标准接口；Agent才是围绕目标做下一步判断的执行者。它们解决的问题不同。”

再补充：

“当前案例只有三个工具，没有必要为了使用MCP而使用MCP。当前任务一个Agent就能完成，也没有必要拆成多个Agent。”

## 【快速判断】

- 一个门店助手调用三个工具：单Agent优先；
- 集团级任务涉及财务、供应链、营销和合规，不同角色使用不同权限：可以进一步评估Multi-Agent。

## 【纠偏】

- MCP不是Agent；
- 接入MCP不代表自动获得可靠规划；
- 多Agent会增加成本、时延、协作错误和责任划分问题；
- 没有明确瓶颈时，默认单Agent。

## 【不要展开】

不安装MCP Server，不配置Multi-Agent，不比较具体框架。

# 模块九：总结与课后作业

> 时间：136—138分钟

## 【四句话收口】

1. Agent不是更会聊天，而是围绕目标判断下一步并使用工具；
2. 工具不是越多越好，职责、参数、权限和异常必须明确；
3. 能执行就必须能受控，高风险动作要确认或审批；
4. 先跑通单Agent最小闭环，再判断是否需要MCP或Multi-Agent。

## 【作业说明】

“请把今天的V0.1扩展成自己的Agent方案V1.0。选择一个真实但已脱敏的场景，设计2—4个工具，并写出五条测试：正常、缺参、冲突、工具失败和越权。最后回答：为什么需要Agent；是否需要MCP；是否需要Multi-Agent。”

提醒：

- 不上传真实客户信息；
- 不提交内部账号、Token、密钥或接口地址；
- 没必要实际搭建MCP或Multi-Agent；
- 复杂不是加分项，能解释、能控制、能测试才是。

## 【下节课预告】

“下一课我们会反过来审视今天的方案：这个问题第一版真的需要Agent吗？Workflow、RAG或普通AI功能是否已经够用？然后再确定MVP边界。”

# 课后老师自检

上完课后记录：

1. 学员在哪个概念上最容易混淆；
2. 哪条测试与预期不一致；
3. Coze是否出现平台或配置问题；
4. 纸面练习是否在18分钟内完成；
5. 哪个模块超时；
6. 是否误讲了真实业务或敏感信息；
7. 下次应更新工具描述、固定返回还是讲解话术。
