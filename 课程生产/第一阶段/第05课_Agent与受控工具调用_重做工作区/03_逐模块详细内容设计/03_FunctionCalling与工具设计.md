# 模块03｜Function Calling与工具设计

> 建议时长：23分钟  
> 核心问题：模型怎样提出工具调用，谁真正执行？

## 一、教学目的

让产品经理理解工具调用的系统分工，并能设计一份模型容易理解、应用可以校验的工具说明。

本模块不要求编写接口代码。

## 二、从“说”到“做”

大模型擅长：

- 理解；
- 分类；
- 生成；
- 总结。

真实任务还可能需要：

- 查询实时经营数据；
- 查询订单状态；
- 创建草稿；
- 提交审批；
- 发送通知。

这些动作需要外部系统或工具。

## 三、工具调用四步图

```text
1 模型根据用户问题和工具描述
  输出工具名称＋结构化参数

2 应用程序校验
  参数、格式、权限、风险、确认状态

3 应用程序真正执行
  API、数据库、Workflow或其他工具

4 工具结果返回模型
  模型根据结果回答、继续调用或停止
```

核心结论：

> 模型通常不直接访问数据库或修改业务系统；模型提出调用，应用系统负责校验和执行。

## 四、Function Calling解决什么

课堂表达：

> Function Calling让模型能够用结构化方式表达“要调用哪个工具，以及需要提供哪些参数”。

不需要展开JSON Schema和代码实现，但学员必须理解：

- 工具名称影响选择；
- 工具描述影响理解；
- 参数定义影响能否执行；
- 返回状态影响下一步判断。

## 五、工具描述正反例

### 错误版本

```text
名称：query_data
描述：查询数据
```

问题：

- 查询什么；
- 什么时候用；
- 与其他工具有什么区别；
- 必须提供什么；
- 哪些数据不能查询；
- 失败时返回什么。

### 优化版本

```text
名称：query_store_metrics

用途：
查询指定门店在指定日期范围内的经营指标，
用于分析门店经营表现。

必填：
门店ID、开始日期、结束日期、指标名称。

不适用：
不查询活动规则，不查询其他无权限门店，
不用于创建或发布活动。
```

## 六、工具十字段

| 字段 | 产品问题 |
|---|---|
| 名称 | 模型和系统怎样唯一识别 |
| 用途 | 这个工具解决什么问题 |
| 使用条件 | 什么时候应该调用 |
| 输入参数 | 执行需要哪些信息 |
| 参数类型 | 日期、数字、枚举还是文本 |
| 必填/选填 | 缺少什么必须追问 |
| 返回结果 | 成功时返回哪些字段 |
| 异常结果 | 失败、无数据、冲突怎样表示 |
| 权限 | 谁可以查询或执行 |
| 确认 | 调用前是否需要用户确认 |

## 七、参数示例

用户：

> 看看门店10086最近30天的新客表现。

模型提出：

```text
tool: query_store_metrics
store_id: 10086
start_date: 2026-06-27
end_date: 2026-07-26
metrics:
  - new_customer_count
```

应用校验：

- 用户是否能访问门店10086；
- 日期是否有效；
- 时间范围是否超限；
- 指标是否在允许枚举内。

## 八、错误返回也要结构化

不推荐：

```text
查询失败
```

建议：

```text
status: failed
error_code: STORE_NOT_FOUND
message: 门店ID不存在
retryable: false
next_action: ask_user_to_check_store_id
```

这样Agent才能判断：

- 是否重试；
- 是否追问；
- 是否换工具；
- 是否停止。

## 九、课堂练习：改工具说明

给学员两个模糊工具：

```text
search_rules：搜索规则
create_activity：创建活动
```

要求8分钟内补充：

- 用途；
- 必填参数；
- 成功返回；
- 两类异常；
- 权限；
- 是否确认。

两人互换检查：

> 一个没看过这个工具的人，能否仅根据描述判断何时调用、传什么和失败后怎么办？

## 十、教师动作

- 强调工具设计不是接口文档抄写，而是模型选择、应用执行和产品风险共同使用的契约；
- 对“工具越多越强”进行纠正：工具越多，选择冲突和权限成本越高；
- 不现场讲代码。

学员能够解释：

2. 应用负责什么；
3. 一个工具为什么必须有明确参数和异常结果。
